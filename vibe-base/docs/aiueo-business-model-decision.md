## 2. なぜ B モデルか（意思決定の根拠）

### 起点となった問い

「このアプリが実際に売れたとして、どうやって渡すの？クライアントはどうやって使用開始するの？」
— この問いに対し、**現状その仕組みがゼロ**であることが判明した。

### 3つの選択肢

| モデル | 概要 | 開発コスト | スケール性 |
|--------|------|-----------|-----------|
| **A. セルフサーブ SaaS** | 客が自分で登録→設定→即利用 | 大（認証+テナント分離+権限+課金+ウィザード） | 高 |
| **B. 手動プロビジョニング** | 問い合わせ→こちらで環境構築→トークン納品 | 小（PBインスタンス作成スクリプト程度） | 低〜中（月5-10件） |
| C. テンプレ納品 | ZIP渡し→客が自分でデプロイ | ほぼゼロ | 非現実的（ターゲットにVPS知識なし） |

### B を選んだ理由

1. **売れるか未検証の段階で A をフル開発するのが最大のリスク。** 認証・テナント分離・権限モデル・Stripe 課金を先行投資しても、客が来なければ全て無駄になる
2. **B で 5-10 店舗に手動導入 → 実運用フィードバック → A の設計に反映** が手戻り最小
3. **C はターゲット（カフェ・居酒屋・開業準備層）に技術力を求めるため非現実的**
4. Airレジも初期は手動セットアップ支援付きで開始している（業界の定石）

### A モデルに必要な開発（B では不要）

| 必要なもの | 内容 | 重さ |
|-----------|------|------|
| ユーザー認証 | メール登録・ログイン・パスワードリセット | 中 |
| マルチテナント | 全コレクションに store_id + データ隔離 | 重 |
| 権限モデル | 「自分の店のデータだけ見える」保証 | 重 |
| オンボーディング UI | 登録ウィザード（店舗情報→メニュー→QR生成） | 軽 |
| 課金 | Stripe 連携、プラン管理 | 中 |

ウィザード自体は軽いが、その前提条件（認証・テナント・権限）が全体の 8 割。

## 3. B モデルの具体的な納品フロー

```
1. クライアントが LP から問い合わせ
2. こちらで PB インスタンス + Vercel フロント作成（目安30分）
3. 管理者トークンを発行・納品
4. メニュー登録は Zoom 併走 or 代行
5. QR コード印刷データを納品
6. 利用開始
```

### B モデルの限界

| 店舗数 | 状態 |
|--------|------|
| 1-3 店舗/クライアント | 問題なし |
| 10 店舗 | メニュー一括変更不可、売上の横断確認不可 → きつい |
| 100 店舗 | 完全に破綻（100 PB インスタンス管理不能） |

**B → A 移行時の作業:**
- 各 PB の products/orders/settings を store_id 付きで 1 DB に統合
- 新 URL を 1 つ渡す（旧 URL からリダイレクト）
- 移行スクリプトは 1 回書けば他クライアントにも再利用可能

## 4. インフラ容量の試算（2026-03-15 時点）

> **注意:** 以下の数字はこの日時点のインフラ構成に基づく試算。インフラ変更時は再計算のこと。

### 現構成

| 項目 | 内容 | 月額 |
|------|------|------|
| Backend | PocketBase (SQLite) on Oracle Cloud Free Tier (2GB RAM) | ¥0 |
| Tunnel | Cloudflare Tunnel（オーナー PC 経由） | ¥0 |
| Frontend | Vercel 無料枠 | ¥0 |
| DB 容量 | 168 KB（ほぼ空） | — |

### ボトルネック別の限界

**注文処理能力:** ボトルネックにならない（SQLite 100-500 writes/sec、飲食店ピークは 0.3 writes/sec 程度）

**同時接続:** PB 2GB RAM で約 500 WebSocket。1 店舗 3-5 本消費 → 理論上限 100 店舗、安全圏 50 店舗

**DB 容量:** 1 店舗 100 注文/日 → 15MB/月。SQLite 快適上限 1GB で 1 店舗 5 年分、10 店舗 6 ヶ月分（クリーンアップなし）

**最大リスク:** PB がオーナー PC + Cloudflare Tunnel 依存 → PC ダウンで全店舗停止（単一障害点）

### 売上換算（客単価 ¥2,000 × 100 注文/日 前提）

| 店舗数 | 月商 | 現インフラ | 必要な対応 |
|--------|------|-----------|-----------|
| 1 店舗 | ~¥600 万 | 動く | なし |
| 5 店舗 | ~¥3,000 万 | 動く | Tunnel → VPS 移行推奨 |
| 10 店舗 | ~¥6,000 万 | 要移行 | PB を VPS 常駐化（$5-15/月）+ DB 定期クリーンアップ |
| 50 店舗 | ~¥3 億 | SQLite 限界 | PostgreSQL 移行（$15-50/月） |

## 5. #27 複数店舗管理の開発計画

### Phase 1（B モデルでも有用な土台）

- `stores` コレクション新設
- 全コレクションに `store_id` 追加（products, orders, coupons, role_tokens, settings, images）
- `client.js` のクエリに store_id フィルタ追加
- 既存データに default store_id 付与
- **コスト:** レジ改修の半分以下

### Phase 2（A モデル移行時）

- Admin UI に店舗セレクター + 店舗 CRUD
- PB コレクションルールを店舗単位に設定（現在全公開 → 店舗隔離）
- ユーザーモデル導入（現在トークンベースのみ）
- 店舗間データ隔離の検証
- **コスト:** 横断的変更（DB + API + 全 layout + 認証 + 権限）

## 6. 議論の経緯（なぜこの結論に至ったか）

1. **#27 開発コストの質問** → 調査の結果、単なる UI 追加ではなく全レイヤー横断の変更と判明
2. **Phase 1/2 分割を提案** → store_id だけ入れておく（Phase 1）のは低コスト
3. **P2 のインフラキャパの質問** → 具体的な売上換算で限界値を提示
4. **「売れたらどう渡すの？」** → 納品フローが未設計であることが判明（本質的な問い）
5. **3 モデル比較** → B が初期戦略として最適と合意
6. **「B の客が 100 店舗になったら？」** → 1→100 は一晩で起きない。3→10 で A 移行判断
7. **マスター「B でいこ」** → 確定
