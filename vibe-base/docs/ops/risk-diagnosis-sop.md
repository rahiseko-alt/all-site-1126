# リスク診断SOP v4.0

> プロダクトライフサイクル全体を通じたリスク管理の手順書。
> 新規product立ち上げ時に全件検知 → マイルストーン完了ごとにタグ消化 → 本フィルターで最終判定。

## 目的

プロダクトが引き起こしうるダメージを「出口」（誰に何が起きるか）で機械的に検知し、
**設計段階で致命的リスクを弾く**ことで手戻りコストを最小化する。

---

## 全体フロー

```
新規product立ち上げ時 全件フィルター（タグ付け）
    ↓
各マイルストーン完了時: タグ再評価 → 解消できたものからクリアに
    ↓
本フィルター: 残存グレータグの最終判定（存在/量トリガー確定）
    ↓
リリース前バックストップ: 最終確認
```

---

## §1. タグ体系（4種）

| タグ | 意味 | 付与条件 | 次のアクション |
|------|------|---------|---------------|
| **アウト** | 明確にダメージが発生する | 規約違反・法令違反が確定 | 立ち上げ時点で弾く。技術選定やり直し |
| **グレー** | 調べたが白黒つかない | 規約の解釈が割れる / 条件次第で変わる | 持ち越し。競合ToS調査・利用条件で判定を詰める |
| **判定不能** | まだ判定材料がない | コードが存在しない等、情報不足 | 情報が揃うフェーズまで持ち越し。構造問題シグナルの対象外 |
| **クリア** | 問題なし | 検査済みで該当なし / 対処済み | タグ除去 |

### タグと最終判定（存在/量トリガー）の関係

- タグはフェーズ進行中の**状態管理**
- 存在/量トリガーは本フィルター時の**最終判定**
- グレータグ → 本フィルター → 存在トリガー or 量トリガー or クリア に確定
- 判定不能タグ → 情報が揃った時点でグレー or クリア に遷移 → 必要なら本フィルターへ

## §2. 出口フィルター（16項目）

「何のリスクがあるか」（入口）ではなく「誰にどんなダメージが起きるか」（出口）で検知する。

### A. 事業者へのダメージ

| # | 検知項目 | 確認内容 |
|---|---------|---------|
| A1 | 法的責任 | 法令違反・利用規約違反により訴訟・行政処分・罰金が発生しうるか |
| A2 | 金銭損害（コスト暴走含む） | 不正利用・APIコスト暴走・課金ミスで想定外の出費が発生しうるか。**予算アラート未設定による無制限コスト発生**も含む（→ `docs/ops/cost-budget-sop.md`） |
| A3 | 信用毀損 | 誤情報の拡散・データ漏洩・品質問題で評判が毀損しうるか |
| A4 | 事業継続不能 | 外部サービス凍結・アカウントBAN・規約変更等でサービスが停止しうるか |

### B. 顧客へのダメージ

| # | 検知項目 | 確認内容 |
|---|---------|---------|
| B1 | 金銭損害 | 誤課金・二重払い・返金不能が発生しうるか |
| B2 | 個人情報漏洩 | 顧客の個人情報・行動データが意図せず第三者に露出しうるか |
| B3 | サービス不能 | 使えない・データ消失・機能不全で顧客の業務に支障が出うるか |
| B4 | 誤情報による損害 | AI生成コンテンツ・集約データの誤りで顧客が誤った判断をしうるか |

### C. 第三者へのダメージ

| # | 検知項目 | 確認内容 |
|---|---------|---------|
| C1 | 著作権・知的財産侵害 | 他者のコンテンツを無断利用・翻案・転載していないか |
| C2 | プライバシー侵害 | 第三者の個人情報・レビュー・投稿等を同意なく収集・表示していないか |
| C3 | 迷惑行為 | スパム送信・過剰なAPI呼び出し・スクレイピング等に該当しうるか |
| C4 | 不正競争 | 外部サービスの利用規約に違反する使い方をしていないか（商用利用禁止等）。**ホスティング・API提供者・データソースの3層で確認** |

### D. 運用品質ダメージ（v3.0 新設）

> 事業者・顧客・第三者の3軸では捕捉しきれない、運用ノウハウ不足由来のリスクを独立カテゴリ化。

| # | 検知項目 | 確認内容 |
|---|---------|---------|
| D1 | バックアップ・リストア未整備 | バックアップ取得・世代管理・リストア検証が未実施で、データ消失時に復旧不能となりうるか（→ `docs/ops/backup-strategy-sop.md`） |
| D2 | 冪等性未設計 | 決済・通知・DB書込・外部API呼出に冪等性キー/トランザクション境界が未設計で、リトライ時に二重処理が発生しうるか（→ `docs/standards/checklists/idempotency-checklist.md`） |
| D3 | ライブラリ実在性未検証 | npm/pip 等で実在性・最終更新日・タイポスクワッティング・脆弱性スキャン未確認のパッケージが混入していないか（→ `docs/standards/checklists/library-verification-checklist.md`） |
| D4 | 障害対応プロトコル未整備 | runbook.md（障害検知→停止判断→ユーザー告知→原因究明→再発防止）が未整備で、本番障害時に対応が場当たり的になりうるか（→ `docs/ops/incident-response-sop.md`） |

## §3. 判定補助: 利用条件マトリクス

同じ行為でも利用条件によってセーフ/アウトが変わる。タグ付け時に以下を確認する。

| 条件軸 | 例 | 判定への影響 |
|--------|-----|-------------|
| 無料 vs 有料 | Gemini無料枠＝学習に使用。有料枠＝使用しない | API規約上のリスクが変わる |
| 個人利用 vs 商用 | Vercel Hobby＝個人のみ。Pro＝商用OK | ホスティング規約の適用が変わる |
| 社内 vs 社外公開 | 社内ツール＝APPI第三者提供にあたらない場合あり | 法令上の義務が変わる |
| データ保存 vs 都度取得 | Google API＝保存NG、都度取得OK | API規約の適用が変わる |

### 情報の性質による重み付け

扱うデータの性質によってリスクの実質的な重さが異なる。

| 性質 | 例 | 扱い |
|------|-----|------|
| 公開＋自発的 | Googleクチコミ、SNS投稿、公開プロフィール | 規約準拠のみ確認。過剰防衛しない |
| 非公開＋自発的 | 会員登録情報、問い合わせ内容 | APPI準拠。同意取得が必要 |
| 非公開＋非自発的 | 行動ログ、IPアドレス、位置情報 | 最も慎重に扱う |

「個人情報」というラベルだけで一律に判定しない。公開情報と非公開情報を同じ深刻度で扱うとノイズが増え、本当に致命的なリスクが埋もれる。

## §4. 判定補助: 競合ToS参照

グレーゾーンの判定にマスターが毎回考える負荷をかけない。大手競合のToS/プライバシーポリシーを客観基準として使う。

### 判定ルール

- **大手競合が同じ行為をToSで明記して商用運用している → 業界標準として白寄り判定**
- **大手競合があえて避けている行為 → 黒寄り判定**（法務コストをかけてなお回避しているなら個人開発者が突っ込むべきではない）

### 手順

1. 当該プロダクトの大手競合3社以上のToS/プライバシーポリシーを調査
2. グレー項目と同じ行為を競合がどう扱っているか原文で確認（推測不可）
3. 調査結果を `products/{product}/risk-diagnosis.md` に記録
4. 業界標準ラインをvibe-baseに報告し、タグ判定の材料とする

### 実行タイミング

- 立ち上げ時の予備フィルターでグレーが出た時点で実施
- それ以降で未知のグレーが出た場合は追加調査

### 注意

- 調査結果はプロダクト固有の資産（クチコミの競合ToSはfoodeeには使えない）
- SOPに記載するのは手順のみ。調査結果は各プロダクトのrisk-diagnosis.mdに記録

## §5. 製品固有リスク注入

汎用12項目では拾えない製品特有のリスクを注入する仕組み。

### 注入元

各プロダクトの自治憲法（`products/{product}/CLAUDE.md`）に以下のセクションがある場合、その内容を出口フィルターに追加して検査する:

```markdown
## §X. リスク特性
- （製品固有のリスク項目を列挙）
```

### セクションがない場合

汎用12項目のみで実施。製品固有リスクが明白な場合はAIが自治憲法への追記を提案する。

## §6. 共有リスク台帳

**ファイル:** `docs/ops/risk-registry.md`

過去の全プロダクトの診断で検出されたリスクを蓄積する横断資産。

| 権限 | 対象 |
|------|------|
| **閲覧** | 全エージェント |
| **記入** | vibe-baseのみ（検知時にマスターに質問→承認後に記入） |

### 運用方針（v2.0 中央台帳駆動 3 段階設計・Session 292 マスター指示確立）

本台帳は **個別プロダクトの診断書ではなく「広く浅く・たくさん拾う」横断資産** として運営する。3 段階設計は以下:

1. **1 段階目（中央台帳の網羅性強化）**: 業界既知リスクを **100 件規模以上を恒常的に維持**。SaaS / API / 認証 / 決済 / 分析 / メール / LLM / ホスティング / 法令 / プラットフォーム規約 / 知財 等を網羅。「合う / 合わない」は中央台帳の段階では決めない。**広く浅く・たくさん拾うこと**
2. **2 段階目（担当 AI の照合判定が主作業）**: 各プロダクト担当 AI は中央台帳 N 件 × 採用サービス・実装で「**合う / 合わない / 一部合う / 該当なし**」を判定する。個別タグ付け作業（16 項目フルスキャン）は廃止（**v4.0 で §7 §8 改訂済・Session 293**）
3. **3 段階目（「一部合う」の中央逆登録）**: 担当 AI が「一部合う」を検知したら vibe-base 司令塔にエスカレーション → マスター承認後に中央台帳へ新規追加（既存 vibe-base 司令塔 + マスター承認フローと整合）。**結果として「一部合う」事例が減っていく = 資産形成ループ**

### 既存運用との互換

- 担当 AI は立ち上げ時のフィルター時に台帳を読み、既知リスクを把握した上でタグ付けする（既存）
- 台帳にあるリスクは再調査不要。対処パターンをそのまま適用（既存）
- 新規リスクが検出された場合: 担当 AI → vibe-base に報告 → vibe-base がマスターに質問 → 承認後に vibe-base が台帳に追記（既存）
- 上記既存運用は **v4.0（Session 293）で「合う / 合わない / 一部合う / 該当なし」判定フローへ刷新済**（§7 §8 参照）

## §7. 新規product立ち上げ時の中央台帳照合判定

> v4.0 改訂（Session 293・Option ε 2 段階目 SOP 整備）: 旧 v3.0 の「出口フィルター 16 項目フルスキャン」を廃止し、中央台帳（`docs/ops/risk-registry.md`・55 件以上）との照合判定に刷新。担当 AI 主作業 = 中央台帳照合 / vibe-base 主作業 = 照合の独立検証 + 「一部合う」「該当なし」の逆登録司令塔役。

### 実行手順（担当 AI）

1. 共有リスク台帳（`docs/ops/risk-registry.md`・現在 55 件以上）を全件読む
2. 採用サービス・実装（立ち上げ時に確定した技術スタック）ごとに台帳エントリ N 件と照合し、以下 4 値で判定:
   - **合う**: 適用される。台帳の対処パターンをそのまま採用
   - **合わない**: このプロダクトでは該当しない（skipReason 必須記録）
   - **一部合う**: 既存エントリと類似だが条件・対処に独自差異あり → 3 段階目逆登録ループ対象
   - **該当なし**: 中央台帳に既存エントリ無し・新規リスク候補 → vibe-base にエスカレーション
3. 「一部合う」または「該当なし」検知時は vibe-base へ報告（マスター承認後、中央台帳に逆登録 = 3 段階目資産形成ループ）
4. 製品固有リスクのみ独自タグ付け（自治憲法 `§X. リスク特性` セクション参照・§5 参照）
5. 利用条件マトリクス（§3）と情報の性質（§3）を判定に反映
6. グレー項目がある場合、競合ToS調査（§4）を実施
7. 判定結果を `products/{product}/risk-diagnosis.md` v4.0 フォーマット（§13参照）で記録
8. vibe-base に報告

### vibe-base 確認

1. **中央台帳照合の独立検証**（フルスキャン廃止・差異検出に絞る）: 担当 AI の判定（合う/合わない/一部合う/該当なし）と台帳エントリの照合関係を独立レビューし、判定漏れ・誤判定を指摘
2. 担当 AI の「該当なし」「一部合う」検知が妥当か照合判定 → 新規台帳追加候補をマスターに提示
3. マスター承認後、vibe-base が中央台帳に逆登録（3 段階目資産形成ループ・既存「新規リスク検知 → マスター承認 → vibe-base が台帳に追記」フローを継承）
4. `products/{product}/risk-diagnosis.md` に「vibe-base判定済/マスター承認済（日付）」を記入

### アウトタグが出た場合

- 技術選定をやり直す（立ち上げ時点で解決）
- やり直しても解消しない場合、マスターに報告

### 旧 v3.0 フルスキャン廃止理由

担当 AI による 16 項目フルスキャン + vibe-base 独立フルスキャンは「同じ作業の二重実行」だった。中央台帳が「広く浅く拾った既知パターン集」として 55 件以上整備されたため（Session 292・Option ε 1 段階目）、担当 AI は台帳との照合判定に集中し、vibe-base は照合の独立検証 + 「一部合う」「該当なし」を中央台帳に逆登録する司令塔役に専念する（§6 参照）。これにより:
- 担当 AI の作業負荷が「16 項目 × N サービス」から「N サービス × 台帳照合」に変化（軽量化は副次効果）
- 本質効果: 中央台帳の継続成長 = 全 product 横断資産形成ループの確立

## §8. マイルストーン完了時の再評価

> v4.0 改訂（Session 293）: 旧「P0 フィルター 16 項目全件再実行」を廃止し、中央台帳照合判定の再実行 + 新規採用サービスの照合追加に刷新。

### フロー（担当 AI）

各マイルストーン完了時に:

1. 全エントリの判定を再評価し、解消できたものをクリア（または「合わない」）に変更
2. その後新規採用したサービス・実装があれば中央台帳と照合し追加判定（合う/合わない/一部合う/該当なし）
3. 「一部合う」「該当なし」検知時は vibe-base にエスカレーション（3 段階目逆登録ループ）
4. 変更理由と新規判定を `products/{product}/risk-diagnosis.md` に記録
5. vibe-base に報告

### vibe-base 確認（毎回）

1. **中央台帳照合の独立検証を再実行**（フルスキャン廃止・差異検出に絞る）
2. 担当 AI の判定変更（特に「一部合う」「該当なし」の新規検知）をレビュー
3. サイクル途中で追加された技術・サービスは、ここで自動的に中央台帳と照合される（個別の追跡ルール不要）
4. 新規台帳追加候補をマスターに提示 → 承認後、vibe-base が中央台帳に逆登録（3 段階目資産形成ループ）
5. 判定状態をマスターに報告し承認を取得
6. **承認記録は risk-diagnosis.md 末尾に記入**（「vibe-base判定済/マスター承認済（日付）」）

### 構造問題シグナル

- マイルストーンが進んでもグレータグが減らないプロダクトは、設計に構造的な問題がある可能性
- 判定不能タグは情報が揃うまで減らないのが正常（シグナル対象外）
- 「該当なし」「一部合う」検知が継続的に多いプロダクトは、中央台帳に未収載の新領域に取り組んでいるシグナル → vibe-base 司令塔は中央台帳網羅性強化の優先順位を上げる
- vibe-baseがシグナルを検知した場合、マスターに報告

## §9. 本フィルター（最終判定）

### §7・§8・§9・リリース前バックストップの関係

各ステップの目的が異なる。二重実行ではない。

```
§7 立ち上げ時の予備フィルター
│  目的: アウトタグを弾く。技術選定の門番
│  vibe-base: 独立フルスキャン（新規リスクの検知）
│
§8 各マイルストーン完了時のタグ再評価
│  目的: タグの消化確認 + 途中追加技術の検知
│  vibe-base: フルスキャン（新規技術の自動検知 + タグ変更のレビュー）
│  ※ グレータグの最終判定はここではやらない
│
§9 本フィルター（グレータグの存在/量トリガー確定）
│  目的: 残存グレータグに白黒つける最終判定
│  タイミング: vibe-baseが「スルー不可」と判断した時点
│
リリース前バックストップ
   目的: §9がまだ実施されていない場合の最終関門
   ここまでにグレーが残っていれば§9を強制実施
```

### トリガー

グレータグが「これ以上スルーできない段階」に達した時点で実施。タイミングはプロダクトごとにvibe-baseが判断する。

**リリース前バックストップは全プロダクト共通。** ここまでに全グレータグが解消されていなければ、必ず本フィルターを実施する。

### 最終判定基準

| 分類 | トリガー条件 | 対応 | 例 |
|------|------------|------|-----|
| **存在トリガー** | 行為の存在自体がダメージを発生させる | **リリース前に修正必須** | 著作権侵害コンテンツが1件でもある / APIキーがクライアントに露出 |
| **量トリガー** | 一定量に達するとダメージが発生する | **リリース後に監視体制で対応** | APIコスト超過 / 無料枠上限到達 / アクセス集中 |

- **存在トリガーが1件でもある → リリース不可。** 修正してから該当項目のみ再判定
- **量トリガーのみ → リリース可。** 監視項目としてリリース後モニタリングに引き継ぎ

## §10. 検知後の対応フロー

検知結果が出た後の処理パイプライン:

```
1. 台帳照合 — 既知リスクか？
   ├─ 既知 → 対処パターン適用。判断不要
   └─ 未知 → 2へ

2. 利用条件判定 — 現プロダクトの条件でアウトか？（§3参照）
   ├─ 条件外 → 監視項目として記録。終了
   └─ 条件内 → 3へ

3. 情報の性質確認（§3参照）
   ├─ 公開＋自発的 → 規約準拠のみ確認
   └─ 非公開 or 非自発的 → 慎重に扱う

4. グレーゾーン → 競合ToS参照（§4）
   ├─ 業界標準として白 → クリア
   └─ 業界が回避 or 前例なし → 5へ

5. 対処方針の策定（担当AIが実施）
   - 問題箇所の特定（ファイル:行番号。コードがある場合）
   - 原因（どの規約のどの条文に違反/抵触）
   - 解決案（コード変更の方向性。複数案あれば比較表）
   → vibe-base経由でマスター判断を仰ぐ

6. 修正 → 該当項目のみ再判定 → 台帳に追記（vibe-base）
```

## §11. セカンドオピニオン

同一PC上の別AIに渡す前提。診断を実施したAI自身のバイアス・見落としを補完する目的。
vibe-baseが必要と判断した場合に実施する（立ち上げ時・マイルストーン完了時・本フィルターいずれのタイミングでも可）。

### 運用手順

1. 診断実施AIが `products/{product}/risk-diagnosis.md` に診断書を生成する
2. マスターが別AIに **パスだけ** 渡す: 「`products/{product}/risk-diagnosis.md` を読んでセカンドオピニオンを出せ」
3. 別AIが診断書内の照合材料パスから実装コード・自治憲法・規約を自分で読み、検証する

### 診断書の必須セクション

- **タグ一覧テーブル**（検知内容/フィルター番号/タグ/利用条件/情報の性質/根拠URL）
- **マイルストーン履歴**（各マイルストーンでのタグ変遷）
- **照合材料**（実装コード・自治憲法のフルパス + 適用法令 + 外部サービス規約URL）
- **読了証明**（3項目。自治憲法最終行/最も危険なコード1行/API呼び出しURLパターン）
- **依頼事項** + 制約

### 読了証明の検証手順

1. 読了証明3項目を実際のファイルと突き合わせる（1項目でも不一致なら回答を破棄）
2. 検知事項にコードの行番号引用があるか確認（行番号なし = 一般論の可能性大）
3. 検証OKなら結果をマスターに提示。NGなら「セカンドオピニオンAIが照合材料を読めていない」と報告

## §12. SOPバージョン照合

SOP更新時に既存プロダクトが置き去りにならない仕組み。

### 運用

- `products/{product}/risk-diagnosis.md` の冒頭に `sop-version: X.X` を記録する
- vibe-baseのマイルストーン確認時、プロダクトのsop-versionと本SOPのバージョンを照合する
- **バージョン一致:** 通常のタグ再評価のみ
- **バージョン不一致:** 本SOPの全文を読み込み、差分を確認した上でフルフィルターを再実施
- **sop-versionフィールドが存在しない場合:** risk-diagnosis.md に「sop-version未記載」と記録し、vibe-baseがフィールド追加または他の対応をマスターに確認する

### 既存プロダクトのSOP改訂時対応

SOP改訂により既存プロダクトのsop-versionが不一致になった場合、**現在の進行状況に関わらず立ち上げ時の予備フィルターから再チェックを実施する。** マイルストーンが進行中であっても例外なし。
