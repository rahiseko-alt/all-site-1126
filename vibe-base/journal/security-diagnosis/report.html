2. リスク中（△）の項目 詳細

A-1. 開発環境とプライベート利用の混在 △

何が問題か（一般語）

仕事用フォルダと個人用フォルダ（銀行・SNS 等の認証情報を含む可能性のある場所）が同じパソコンの同じデスクトップに同居しています。

最悪何が起こるか

AI エージェントが誤って仕事フォルダ外のファイルを編集したり、個人領域の認証情報をうっかり読み込んでログに残すリスクがあります。

たとえ話

机の上に仕事の書類と銀行通帳が並んで置いてあるようなもの。普段は触り間違えませんが、急いでいるときに混ざる可能性が残ります。

現状の対策（一定程度効いている）

  • AI エージェントの作業範囲は vibe-base フォルダ + 行動ログのみに運用ルールで制限済（Session 250 でマスター指示として確定）
  • MEMORY.md の P1 #8 に明記、memory/feedback_no-edit-outside-vibebase.md 詳細記載

改善後の状態

運用ルールが守られている限り実害は出ません。技術的に強制したい場合は別案を提示可能ですが、コストとのバランス次第です。

D-3. 既知の脆弱性チェック手段 △ 部分解消

何が問題か（一般語）

利用しているプログラム部品（npm パッケージ）に過去発見された欠陥が混ざっていないか、定期的にチェックする仕組みです。

現状（実施済 + 持ち越し）

  • Session 249 で全 12 プロジェクトに npm audit 実行 → critical 3 件すべて解消
  • Session 252 で review-app next 16.2.4 + nodemailer 8.0.7 / aiueo/lp nodemailer 8.0.7 解消
  • kobaraku exceljs: マスター承認で見送り（ダウングレードでコア機能破壊リスク）
  • aiueo/app/frontend vite-plugin-pwa: マスター見送り（メジャー後退罠）

最悪何が起こるか

持ち越し分は本番運用上の影響度を都度判定済。攻撃者がライブラリの既知の欠陥を狙ってリクエストを送るリスクは局所的です。

たとえ話

車の部品リコール通知。普段運転していて即座に故障するわけではないが、特定条件で問題が出る可能性がある状態の 2 件を、影響度を見てマスター承認のうえ持ち越し。

改善後の状態

致命傷はクローズ済。残 2 件は機能影響と引き換えのため運用判断で保留中。

E-3. インシデント追跡用ログ △

何が問題か（一般語）

Vercel デフォルトのログ保管期間が 約 1 時間（Hobby プラン）で、過去のエラーや不正アクセスを後から追えません。

最悪何が起こるか

不正アクセスが起きても気付くのが翌日以降になると、何が漏れたか / どこから侵入されたかを追跡できません。

たとえ話

監視カメラの映像が 1 時間で消える設定。事件が起きてから録画を見ようとしてもデータがない。

改善後の状態

  • Sentry 無料枠（5,000 イベント/月まで無料）の導入で 30 日保管
  • 導入 SOP は Session 253 で作成済（docs/ops/sentry-introduction-sop.md）
  • マスタープラン（Hobby/Pro）判断 + アカウント作成後、High 4 プロダクトに 1-2h ずつ導入

F-1. 入力バリデーション・サニタイズ △

何が問題か（一般語）

ユーザー入力（フォーム / API リクエスト）の中身チェックを、専用ライブラリ（zod 等）を使わずに「手書きの正規表現」で検査しています。

最悪何が起こるか

  • 想定外の形式の入力でサーバが意図しない動作をする可能性
  • HTML タグ混入時の XSS 対策がライブラリで担保されていない箇所がある可能性
  • SQL インジェクション（DB 攻撃）は ORM / Prisma / Supabase クライアント / PocketBase SDK が構造的に防御済（問題なし）

現状の対策（部分的）

  • Session 253 で .claude/rules/api-validation.md + docs/ops/zod-validation-sop.md 作成
  • review-app /api/contact に zod 雛形 1 ルート導入済
  • ai-concierge admin-login + master + chat-widget の rate-limit + XSS 対処完了
  • 残: review-app 19 ルート / ai-concierge 11 ルート / foodee 2 ルート / aiueo フロント form の段階展開（4-8h × 4 プロダクト）

たとえ話

郵便ポストの口に「手紙以外入れないでください」と貼り紙だけしている状態 → 1 個目のポストには専用フィルター設置完了。残ポストへの展開待ち。

3. 判定不能（?）の項目 詳細

C-1. API トークン・SaaS 連携の権限スコープ ?

なぜ判定できなかったか

マスターの各 SaaS 管理画面（OpenAI / Gemini / Stripe / Google Cloud / Replicate / Anthropic 等）で実際の権限スコープを目視確認する必要があり、Claude が直接判定できません。

マスターに確認してほしいこと

  1. OpenAI / Gemini / Anthropic API キーの「組織範囲・利用可能モデル制限」が必要最小限か
  2. Google Cloud Console の OAuth Client が「必要な scopes のみ」に絞られているか
  3. Stripe API キーが「読取専用 / 書込可能」のどちらか、用途と一致しているか
  4. Replicate の API キーが特定モデルのみに制限されているか

C-2. 本番 DB 書込権限の認証情報の開発端末配置 ?

なぜ判定できなかったか

review-app の .env に Neon 本番接続文字列（rotate 後の新パスワード）が配置されている状態は確定済。これが「開発端末に置くべきでない」かは運用判断（マスターが個人開発で 1 台運用のため、置かざるを得ない場合もある）。

マスターに確認してほしいこと

  • 本番 DB と開発 DB を分離するか（Neon は別ブランチで分離可能、追加コスト要）
  • 別端末でのみ本番 DB 触る運用にするか（現状 1 台運用のため非現実的）
  • 現状維持（個人開発許容範囲）と判断するか

A-3 / C-3 は確定済 処理済

  • A-3 WSL 権限境界: WSL 未使用 → N/A 確定（Session 250）
  • C-3 MCP サーバ・ツール権限: Session 251 公式仕様準拠化（19 項目自動判定）+ 共通憲法 §5.2 + check-settings-spec.mjs で実質完了
