# 自己検証 SOP v1.0

> **目的:** 構造改革（Session 213-222、共通憲法 v5.7）で組んだ「自走バックストップ体制」が、進行途中で機能不全に陥っていないかを毎ターン自己検証する仕組み。
>
> **背景:** 改革のゴールは「ルールが書いてある状態」ではなく「マスター/AI の見落としを hook/SOP/ゲート/rule 自動注入が機械的に検知してブロックする状態」。条文を書いただけで安心するアンチパターン（タグだけ進める / 書いてある≠効いている / 計画書≠現状）が改革プロジェクト自身でも複数再発したため、検証工程そのものを SOP 化する。

## §1. 自己検証 6 区切り

各区切りで「バックストップ自身が機能不全に陥っていないか」を機械検証する。

| # | 項目 | 検証方法 |
|---|------|---------|
| A-1 | 計画書スナップショット陳腐化検知 | 計画書記述（バージョン・パス・ファイル名）vs 現状ファイル照合 |

| A-3 | propagate-hooks 同期 | `node scripts/propagate-hooks.mjs` 実行、SYNC 件数を確認 |
| A-4 | memory.md 直近 Check-out 読了 | 未解決事項リストアップ |

> 注: 旧 A-1「PC 表バージョンタグ整合」は PC 表廃止（2026-06-06）で削除。後継の照合リスト（`/plan-finalize` Stage 0.5 経由）も 2026-07-18 に全廃し、バージョン照合機構自体を撤去した。

### B. タスク着手前

| # | 項目 | 検証方法 |
|---|------|---------|
| B-1 | 受入条件の項目別リストアップ | 計画書/指示書の「受入条件」を `- [ ]` 箇条書きに転記 |
| B-2 | 既存ファイルとの 1 対 1 照合 | 受入条件の各項目について該当ファイルを Read |
| B-3 | 純増判定（Refactor-on-Write） | 「参照」と「項目追加」を文言で機械区別。「○○ から参照」= `**必読:**` 行追加で十分。「項目数を N→M に拡張」のみ項目追加 OK |
| B-4 | 参照経路（hook/script/skill）の生存確認 | 二重正本・旧パス放置がないか grep |
| B-5 | スコープ外の明示 | 計画書「スコープ外」を読み、誘惑される作業を意識化 |

### C. 実装中（Edit/Write 各回）

| # | 項目 | 検証方法 |
|---|------|---------|
| C-1 | 直前 Edit と受入条件の紐付け | 各 Edit/Write 後に「受入条件 #X の対応」と内部宣言 |
| C-2 | paths glob の影響範囲 | 新規 rule の `paths:` に対し `git ls-files <glob>` で実件数確認、テスト/モック過剰捕捉なし |
| C-3 | スコープクリープ検知 | 受入条件にない作業に手を出していないか 1 Edit ごと自問 |
| C-4 | hook 並列発火順序 | 新規 rule → SOP のシリアル順 Write（Session 217 教訓） |

### D. 完了判定前

| # | 項目 | 検証方法 |
|---|------|---------|
| D-1 | 検証コマンド全件 EXIT 0 | 計画書記載コマンドを全実行、全 OK 出力 |
| D-2 | hook 発火確認 | 該当 hook（pre-edit / destructive 等）で EXIT 0、ブロックなし |
| D-3 | **実体ファイル存在** | rule/SOP を書いたなら対応する実体（runbook.md / backup-config.md 等）を `test -f` |
| D-4 | ブラウザ目視 | HTML 成果物変更時はレンダリング確認、エラー帯なし |
| D-5 | grep 整合（タグ ≠ 中身の最終チェック） | バージョン番号と内容の追従を再 grep |

### E. コミット前

| # | 項目 | 検証方法 |
|---|------|---------|
| E-1 | unstaged 漏れなし | `git status` で意図したファイルが全 staged |
| E-2 | 意図しない変更の混入なし | `git diff --cached` で xlsx・settings.local.json 等の恒常差分巻き込みなし |
| E-3 | plan / memory.md vs 実装一致 | plan の受け入れ基準・memory.md P1 の記述が実装と乖離していない |
| E-4 | memory.md vs git diff-stat 一致 | 「変更ファイル」リストが diff-stat と一致 |
| E-5 | コミットメッセージ規律 | `feat(scope):` 形式 + Co-Authored-By 行 |

### F. Check-out（セッション終了時）

| # | 項目 | 検証方法 |
|---|------|---------|
| F-1 | 次 AI が memory.md だけで再開可能か | 初見シミュレーション |
| F-2 | 未解決事項漏れなし | 司令塔作業 / マスター作業 / 後続フェーズ の 3 区分で記載 |
| F-3 | plan file 参照禁止遵守 | `~/.claude/plans/*.md` への参照を memory.md に書いていない |
| F-4 | エラー回数の正直記載 | 隠さない |

## §2. OK / NG 基準と NG 時即時対応

### OK / NG 一覧

| 区切り | OK | NG（再発パターン） |
|---|---|---|
| A | A-1〜A-4 全達成 | 計画書陳腐化 / バージョンタグだけ進めた（タグ≠中身） / 自己診断 1 件以上 Yes |
| B | 受入条件 1 対 1 対応 / 旧パス参照なし | 「参照」を「項目追加」と誤解 / 受入条件外を計画化 / 二重正本のまま着手 |
| C | 各 Edit が受入条件に紐付く / glob 想定通り | 「ついで」修正 / スコープクリープ / hook 迂回（`--no-verify`） |
| D | 検証コマンド全 EXIT 0 + 実体存在 + 発火確認 | 条文書いただけ・実体不在 / hook ブロック迂回 |
| E | git status 想定通り | xlsx・settings.local.json・`.obsidian/` 巻き込み |
| F | memory.md だけで再開可能 | plan file 参照前提 / 会話文脈にしかない決定 |

### NG 検知時の即時対応フロー

1. **作業即時停止**（コミット・追加 Edit 禁止）
2. **マスター報告**（NG パターン名 K1〜K5 / 検出区切り A〜F / 検出箇所 / 影響範囲）
3. **方針合意**（修正 / スコープ縮小 / revert のいずれか）
4. **修正実行**
5. **再検証**（同区切りの全項目を再実行）
6. **OK 確認後に作業再開**
7. **教訓を 2 周目調整事項 or 該当 SOP に記録**

**1 件 NG で全停止**（共通憲法 §5「混乱検知」と同規律）。「軽微だから進める」と自己判断するな。

## §3. NG 時修正シミュレーション（過去 5 ケース）

### K1: タグだけ進める（Session 221）
- **検出区切り:** D-5（タグ ≠ 中身の最終 grep 整合チェック）
- **検出例:** ドキュメント冒頭タグ（例: `checklist-version` / `sopVersion`）を更新したのに本文・参照先の実体が旧版のまま残存
- **修正手順:** 即停止 → Plan Mode で差分を全件特定 → ExitPlanMode 承認 → 機械更新（並列 Edit）→ 再 grep 整合確認 → 成果物目視

### K2: 書いてある ≠ 効いている（Session 222 T16 D4 runbook 全件不在）
- **検出区切り:** D-3
- **検出例:** `for f in products/*/runbook.md; do test -f "$f" || echo "MISSING: $f"; done` で全 8 件 MISSING
- **修正手順:** 「条文 OK・実体 NG」明示報告 → ✅ にせず × 据置 → `risk-registry.md` に横断パターン登録 → 次セッションで実体作成タスク化

### K3: 計画書スナップショット陳腐化（Session 216）
- **検出区切り:** B-2
- **検出例:** 計画書記述「v8.5→v8.6」vs 現状 product-cycle.md v9.1
- **修正手順:** マスターに「計画書記述ミス検出」報告 → 訂正方針合意 → 計画書を別コミットで訂正 → 着手継続

### K4: 純増（Session 218 T4 CL-10 #9 Refactor-on-Write 違反）
- **検出区切り:** C-3 / B-3
- **検出例:** 受入条件「CL-10 から参照」を「項目 #9 追加」と解釈して実装着手
- **修正手順:** Edit revert → 受入条件文言再読 → `**必読:**` 行追加で十分と判断 → 違和感を 2 周目調整事項に記録

### K5: 正本一本化漏れ（Session 220 二重正本）
- **検出区切り:** B-4（参照経路の生存確認・旧パス放置 grep）
- **検出例:** リソース移設・廃止後に旧パス参照が SOP / script / skill に残存（例: 廃止済テンプレへの参照が複数ファイルに残る）
- **修正手順:** Plan Mode で正本一本化スコープ再定義 → 旧パス参照ファイル全件特定 → SOP/script/skill を新パス統一 → 旧ファイル削除（マスター承認後）→ hook 発火確認
