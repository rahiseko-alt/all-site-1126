# 全エージェント共通ルール

> CLAUDE.md §6 SOP索引から参照される。全エージェントが該当作業前に読む義務あり。

## 思考原則

1. **読んでから書け** — ファイルを開かずにコードを書くな。記憶は嘘をつく
2. **1手目は観察** — 手を動かす前に「何が影響を受けるか」を挙げろ
3. **推測するな聞け** — 解釈が2通りあるなら作業より質問が先
4. **自分の出力を疑え** — 「完了」の前に壊れていないことを自分で確認しろ
5. **表面を直すな原因を直せ** — エラーを消すだけでなく、なぜ起きたかを追え

## 報告ラベル制度

判断・報告・完了申告にはラベルを付与せよ。無印は客観的事実のみ許容。

| ラベル | 意味 | 例 |
|--------|------|-----|
| **【実行済み】** | ツールで実行し結果を確認した | ファイル読み、grep、ビルド、本番確認 |
| **【推測】** | ソース未確認で述べている | API仕様、影響範囲、動作予測 |
| **【未実行】** | やるべきだがやっていない | テスト、検証、影響範囲調査 |

- ラベルなしで「確認しました」「OKです」「動作しています」と書くことは禁止
- 迷ったら【推測】を付けろ。外して怒られることはない。付け忘れたら怒られる

> エビデンス: ラベリングによりユーザーの正誤判別力が有意に向上する（Steyvers et al., Nature Machine Intelligence 2025; ICLR 2024/2025 verbalized confidence研究群）。CSS計測表提出制（v1.3）・CL-5表示内容検証で実績あり。調査品質ルール§信頼性ルール#4,#7も同原理。

## 進捗管理ルール（Plan Mode）

> PC 表（固定テンプレ配布）は 2026-06-06 廃止。進捗管理は Plan Mode（plan ファイル）で行う。

### 正本と形式
- **進捗の単一正本は Plan Mode の plan ファイル（`docs/ops/plans/` 配下・Git 管理）。** 各 product の `memory.md` P1 に「現フェーズ + 直近 plan path」を常駐させる
- **仮説テーブルの正本は `products/{product}/hypotheses.md`（永続独立ファイル）**

### 運用ルール
1. **照合義務:** 進捗に言及するときは必ず plan の受け入れ基準と実装を照合。照合なしに進捗を語ることは禁止
2. **実物確認必須:** 「未確認」「推定」で完了にするな。実物を確認してから記録
3. **他エージェントの完了報告は、自分で実物確認するまで信用するな**
4. **セッション開始時:** 直近 plan + 対象プロダクトの `memory.md` P1 を最初に読む（`/pc-checkin` STEP3）
5. **完了報告:** plan の受け入れ基準項目番号の指定が必須
6. **plan に無い作業を勝手に着手するな。** 抜けを発見したら受け入れ基準への追加を提案し、承認後に着手せよ
7. **plan 連動:** タスクの状態を変更したら、対応する plan / memory.md P1 を同一コミット内で更新せよ
8. **rationale記載基準:** rationale には**判断内容の実体**＋**検証可能な証跡**の両方を書け。どちらか片方だけでは不合格。
    - **判断内容の実体:** 何を決めた/何を確認した/何が見つかったかの要約
    - **禁止:** セッション番号だけ / 「OK」「確認済み」「PASS」だけ / 検証手段のない感想・推測
    - **形式:** `「判断内容の実体」— 証跡(Session N)` 。証跡が複数ある場合は列挙

## マスターへのテスト依頼条件

マスターに「テストしてください」と依頼する前に、以下4項目を全てクリアすること。1項目でも未達ならテスト依頼禁止。

1. **自分で全機能を試して100点の状態であること** — 「たぶん動く」は不可。全画面・全操作を自分で実行済み
2. **エラー発生時にエラーログが表示される or 拾える仕様になっていること** — マスターがエラーに遭遇した際、原因追跡できる状態
3. **plan の受け入れ基準と照合して差分0の状態であること** — 受け入れ基準の記載内容と実装が完全一致
4. **スマホで使える状態にしておくこと** — レスポンシブ対応済み。レイアウト崩れなし

## plan 乖離時の停止義務

エラー修正の過程で plan の記載内容（受け入れ基準・完了条件・リスク想定等）と実態が乖離した場合：

1. **開発を即座に停止する**
2. **司令塔（vibe-base）に乖離報告書を提出する**
   - 何が乖離したか（plan の記載 vs 実態）
   - なぜ乖離したか（どのエラー修正が原因か）
   - 修正案（plan をどう更新すべきか）
3. **司令塔の許可を得てから開発を再開する**

乖離を無視して開発を続行することは禁止。plan はプロダクト進捗の単一正本であり、これが壊れると全てのゲート判定・引き継ぎ・品質管理が根拠を失う。

## ⚠ 危険項目の警告義務

plan 冒頭の `## ⚠ 危険項目` ブロックに項目がある場合（`なし` でない場合）：

1. **plan を提示・進捗報告するたびに、⚠ 項目を目立つ形でマスターに警告する**（省略禁止）
2. **警告には未解決の具体的リスク項目（⚠ ブロックの内容）を含める**
3. **マスターが対処完了を確認するまで ⚠ 項目を解除しない**
4. **⚠ が存在するフェーズより先のタスクに着手する場合、⚠ 項目が未解決である旨をマスターに再確認してから進む**

## UI設計基礎哲学（全プロダクト・全エージェント・全セッション共通）

> マスター確立（2026-06-01）。エージェントが変わっても・セッションをまたいでも・別プロダクトに入っても必ずこの思想で設計せよ。

### 原則：カードベース独立設計

**「配置はカードで決め、中身はカードの中で決める。カードは独立しているから、何かを変えても何かが崩れない。」**

これは業界では **Component Encapsulation（コンポーネントエンカプスレーション）** と呼ばれる設計原則であり、BEM・Atomic Design・Web Components すべての基盤思想と一致する。

### 実装ルール（禁止と義務）

**禁止: 親コンテナのサイズを前提にしたピクセルハードコード**
```css
/* ❌ NG：372pxという数字を暗黙の前提にした絶対座標 */
.paw  { width: 372px }
.toe-1 { left: 12px; top: 44px }   /* → サイズ変更時に全座標が連動して崩れる */
```

**義務: コンテナを唯一の真実の源（Single Source of Truth）にする**
```css
/* ✅ OK：コンテナサイズだけが変数・内部は比率で自動追従 */
.paw  { width: var(--paw-size, 372px) }
.toe-1 { left: 3.23%; top: 11.83% }   /* → --paw-size 一箇所だけ変えれば全体追従 */
```

### 適用手段（優先順位順）

1. **`%` 単位**（親コンテナ相対。最小変更で既存資産を活かせる）
2. **CSS カスタムプロパティ（`--size` 変数）**（変数1箇所で全体を制御）
3. **`aspect-ratio` + `%`**（縦横比を保ちながらスケール）
4. **SVG `viewBox`**（有機的形状の完全スケーリング。将来の理想解）

### 違反パターンの識別

「何かを変えると何かが崩れる」と感じたら、それはこの原則に違反している証拠。その場合：
1. 崩れの原因が「ピクセル絶対値の連動」であることを確認する
2. 修正の前に「どのコンテナを Single Source of Truth にするか」を決める
3. 内部パーツをすべてそのコンテナ相対（`%`）に変換してから変更する

### 例外（この原則を適用しない場面）

- A4印刷・mm/cm要求（ピクセルパーフェクト必須）
- 複数コンポーネント間の意図的なグリッド整合（CSS Grid Subgrid）
- アニメーションのタイミング同期

## git worktree 運用（移行中・正本 ADR-0003）

> 毎セッションの git 詰まり（push 衝突・unstaged 混在・stash 綱渡り）の根治。**正本 → `docs/adr/0003-worktree-feature-branch-migration.md`。** 1個ずつ試す段階移行中（Step1 司令塔で実証済 → Step2 横展開 → Step3 pre-push master 拒否 hook）。

- **作業は feature ブランチ + 専用 worktree で分離する**（master 直 commit/push を避ける）。これにより他エージェントの未 commit 差分が見えず、push も衝突しない。
- **置き場所:** `vibe-base/.worktrees/<topic>`（本体配下）。本体の兄弟（`../vibe-base-<topic>`）は `outside-vibe-base-gate` hook に弾かれるため**不可**。`.git/info/exclude` に `.worktrees/` 登録済（本体 status から除外）。
- **ブランチ命名:** `feature/<topic>-<yyyymmdd>`。**起点:** `origin/master`（bot 最新含む・本体 ahead を含まないクリーン起点）。
- **作成→撤去（autoland 自動化）:** `node scripts/git-worktree-new.mjs <topic>` で worktree 生成 → 作業 → path-scoped commit → `node scripts/git-autoland.mjs`（fetch→rebase origin/master→機械検証→ff-only merge→push→feature 削除を自動）→ `git worktree remove .worktrees/<topic> && git worktree prune`。手動でやる場合は `git worktree add .worktrees/<topic> -b feature/<topic>-<date> origin/master`。正本 → ADR-0003「autoland 統合フロー」。
- **staging:** `git add -- <明示パス>` のみ（`-A`/`.`/`-a` 禁止・`pre-git-staging-gate` と整合）。
- **bot は対象外:** x-auto-post の GitHub Actions は master 直 push のまま（リモート完結・ローカル作業と非干渉）。

## 調査品質ルール

調査（Web検索・情報収集・比較分析等）を行う全エージェントに適用する。Opus・中級モデル・低コストモデルを問わない。

### 調査開始前
1. **目的を1文で書け:** 「何を判断するための調査か」を明記してから検索を開始
2. **スコープを宣言せよ:** 対象・除外・粒度を定義。定義なしの網羅的検索は禁止

### 信頼性ルール
1. **ソース併記強制:** 各事実に情報ソースのURLを併記すること。URL取得不可の場合は「出典未確認」と明記
2. **裏付けなし排除:** 裏付けURLのない事実は回答に含めないこと（含めるな）
3. **確信度の自己申告:** 各項目に確信度（高／中／低）を付記すること
4. **推測の明示分離:** 推測や補完を行った箇所は【推測】と明示。事実と推測を構造的に分けること
5. **市場規模は中央値・最頻値で記載**（平均値のみ禁止）
6. **比較表のセルに具体値を記載**（○×だけ禁止。不明なら「未確認」）
7. **調査できなかった項目は「未実施: [理由]」と記載**（空欄禁止・捏造禁止）

### ローリング抑制
1. **検索ステップ上限:** 調査前にWeb検索の上限回数を決めること（目安: 小規模5回、中規模10回、大規模15回）
2. **「足りなければ止まれ」:** 不足情報がある場合は追加調査せず、不足項目を一覧化して報告すること
3. **段階的アプローチ:** 検索上限10回以上が見込まれる調査は2段階に分割（概要調査→不足箇所のみ深掘り）

### 判断禁止（調査時）
- 調査で判断・推薦を行わないこと（「〜すべき」「おすすめ」「最適」禁止。事実のみ）

## プロダクト固有情報の記録場所（Session 197 マスター指示）

プロダクトに関する決定・学び・運用情報は、**そのプロダクトフォルダ**に書け。司令塔エージェントの記憶領域（vibe-base 配下の `~/.claude/projects/*/memory/`）に書くな。

### 書く場所
- プロダクト固有の決定事項・運用メモ・残タスク・出品情報・アカウント情報等 → `products/{product}/CLAUDE.md` の「運用メモ（司令塔からの戻し）」セクション
- そのプロダクトの詳細ドキュメントは該当 `products/{product}/` 配下に配置（例: `products/aiueo/docs/`）

### 書かない場所
- 司令塔の MEMORY.md
- `~/.claude/projects/*/memory/*.md`

### 根拠（Why）
司令塔がプロダクト作業を肩代わりすると、本来そのプロダクトフォルダに書くべき情報が司令塔の記憶に流入し、プロダクトエージェントからは見えなくなる。Session 197 で MEMORY.md 肥大（183/200行）が発覚し、30 件の「プロダクト固有」エントリを各プロダクトの CLAUDE.md に戻した。以降は発生源（プロダクトフォルダ）に直接書くことで再発を防ぐ。

### 例外（MEMORY.md 側に残してよいもの）
- 全プロダクト横断の戦略情報（マネタイズ大作戦 / 参入戦略 / 出品サイクル SOP 等）
- 司令塔だけが使う運用ルール（PC 表規律以外の貼り付け防止・トークン規律等）
- 全エージェント共通規範（思考原則・過失教訓・景品表示法等）
