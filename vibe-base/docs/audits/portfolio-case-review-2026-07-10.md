### 実コードで裏取り済み

| 指摘 | 検証結果 |
|---|---|
| DTD/XXE対策が明記されていない | `app/api/rss/index.js` / `app/api/cron/index.js` に `DOCTYPE`/`ENTITY`/`DTD` 対策のコードは見当たらず。正規表現ベースの自作パーサーで、XXE的な入力への耐性は未検証 |

- 「自作パーサー」をセールスポイントとして押し出す書き方をやめ、中立的な「RSS/Atom正規化処理」という表現に変更

## Case 07（AI開発ガバナンス基盤 / vibe-base自身）

### 評価
外部批評の核心は「AIへの指示ではなく実行権限・コードで強制されているか」。本セッション内で実際に体験した事実として：
- `ac-keyword-gate` フックが受け入れ基準の保存を実際にブロックした（プロンプトでなくhookによる機械停止）
- code-reviewer/security-reviewer等の検証エージェントはtool許可リストの時点でEdit/Write権限を持たない（役割の申告でなく権限設計）

この2点は実体験として裏付けあり。一方、サンドボックス・監査ログ・ロールバック・ポリシーのバージョン管理の有無は未検証。

### 文章側の修正（本日対応済み）
- 「並行作業の衝突を防ぐ」というタイトルは、実際には「他作業のステージング済み変更を誤って巻き込まない」ことしか保証しないため、範囲を正確にしたタイトルへ変更

### 実装側の再調査項目（未着手）

## Case 08（受注開発 記録カルテPWA / shiota-karte）

### 実コードで裏取り済み

| 指摘 | 検証結果 |
|---|---|
| 記録本体・一覧・indexの保存が整合しているか | `worker/src/index.js:handleAddReport` は3回の逐次 `await writeJSON()`（report→customer→index）。**トランザクションではない。** 途中で失敗すると一覧側の反映が遅れる可能性がある |
| 「更新時の重複を防ぐ」の実体 | 該当ロジックなし。`reportId` は毎回新規生成され、重複排除の仕組みは無い（そもそも「重複」が起きる設計ではないが、「防いでいる」という言い方は不正確） |
| 専用URLの認可 | URL文字列以外の追加認証は無い（確認済み） |
| 「実機で運用確認する」（タイトル）と「実機相当の環境」（本文）の表記矛盾 | Playwrightのモバイルビューポートエミュレーションであり、実機そのものではない。タイトルと本文で表現が食い違っていた |

### 文章側の修正（本日対応済み）
- 「記録と月別履歴を整合させて保存する」→ 事実に即した表現へ変更（整合性・重複防止を主張しない）
- 「専用URLへ安全に配信する」→ 「安全に」を外し、URL単体では追加のアクセス制御がないことを明記
- 「実機で運用確認する」→ 「実機相当の環境で運用確認する」に統一（概要文も含む）

### 実装側の再調査項目（未着手）
- [ ] report/customer/index保存の整合性保証（トランザクション化 or 補償処理）
- [ ] 専用URLへの追加アクセス制御（有効期限・認証等）の要否検討
- [ ] 実機（実デバイス）での検証実施

## Case 09（ブラウザ完結型 発声トレーニング / omotenashi-trainer）

### 実コードで裏取り済み・致命的誤りを確認

| 指摘 | 検証結果 |
|---|---|
| 「音声は一切サーバーに送らない」という言い切り | `products/omotenashi-trainer/index.html` に `processLocally` 等のオンデバイス強制設定は無く、標準の `webkitSpeechRecognition` をそのまま使用。**音声認識部分はブラウザの実装依存でクラウドへ送信されうる。** ピッチ解析（Web Audio API）はブラウザ内完結で正しいが、「音声は一切サーバーに送らない」という無条件の言い切りは事実誤認 |
| 非対応ブラウザでの「話速・ピッチの2軸採点に切り替わる」という説明 | **実装を確認したところ誤り。** `doScore()` は認識文字数（`recText`）が0のとき `cc < 3` で分岐し、話速スコアは常に0・「音声が認識できませんでした」表示になる。非対応ブラウザでは実質**ピッチのみ**が機能し、話速は機能しない |

この2点はポートフォリオの信頼性に直結する事実誤りだったため、最優先で修正した。

### 文章側の修正（本日対応済み）
- 概要文の「音声は一切サーバーに送らずその場で解析」→「声の高さの解析はブラウザ内の演算だけで完結し、音声データを自社サーバーには送信・保存しない」という、実装が保証する範囲だけの正確な表現へ変更
- 「非対応ブラウザでは自動的に話速・ピッチの2軸採点に切り替わる」→ 実際の挙動（話速は機能せず、対応ブラウザの利用を案内する）に即した表現へ変更

### 実装側の再調査項目（未着手・製品改善として）
- [ ] 非対応ブラウザでの話速採点フォールバック実装（フレーズ文字数＋発話時間からの推定等）
- [ ] 基準音を複数回録音して統計的に安定させる（現状3秒×1回のみ）
- [ ] Hz単純差でなく半音・セント単位でのピッチ比較への変更検討

## Case 10（X運用 自動投稿・分析基盤 / x-auto-post）

### 評価
Case中最も実運用に踏み込んだ内容という評価。一方で法務・信頼性に関わる指摘が複数あり、特に1点は要確認度が高い。

| 指摘 | 判定 |
|---|---|
| AI自動返信にX社の事前承認が必要では | **要確認・未検証。** `studio/reply_engine.py` に人間承認ゲートは無く、予算確認のみで自動送信される実装を確認。X社の自動化ポリシーに基づく事前承認取得の有無はコードから判定できないため、マスター確認が必要 |
| 「設定時刻に投稿する」の精度 | GitHub Actions `schedule` は高負荷時に遅延・破棄されうる（GitHub公式記載）。「設定時刻に」という言い切りはやや正確性を欠く |
| 「在庫監視と補充までを一気通貫で自動化」 | **概要が現状と食い違う。** 本セッション冒頭の引継ぎで確認済みの通り、補充の無人化は現在動作していない（承認済み再設計plan `~/.claude/plans/iridescent-honking-squid.md` が未実装）。ステップ側も監視のみで補充ステップの記載が無く、概要文とステップの記載が不整合だった |
| テンプレートfail-open（品質ゲート非経由でEXIT 0） | 製品CLAUDE.md/generate.pyのdocstringで明記された**意図的な設計判断**（止まらない設計）。批評は「fail-closedの方が安全では」という設計論点の指摘であり、記載自体に誤りは無い。ポートフォリオ文言はそのまま維持し、設計判断として次アクションへ記録 |
| Git状態管理はトランザクションでない／完全一致dedupは近似重複を検出しない | 既知の限界。前者は現在進行中の再設計plan（`iridescent-honking-squid.md`）の対象、後者は`memory.md`に既存の既知課題として記録済み。ポートフォリオ文言はいずれも「完全一致」「リトライ」等、実装範囲を超えた断定はしていないため文言修正は不要 |

### 文章側の修正（本日対応済み）

- 概要文から「在庫監視と補充までを一気通貫で自動化した」の「補充」を削除し、実態（監視まで）に合わせた
