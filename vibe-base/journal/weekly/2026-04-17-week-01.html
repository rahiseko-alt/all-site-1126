A-2. 顧客の困りごと × 提供できる解決（+ 理解の解像度をあげる為の、用語解説）

# 顧客の困りごと 技術手段 理解の解像度をあげる為の、用語解説
1 ポートフォリオサイトを自分のドメインで公開したい Cloudflare DNS + Vercel certs issue + OGPビルド時キャッシュ Cloudflare DNS = ドメイン名（例: kouheikosehira.com）とサーバーの住所（IPアドレス）を結ぶ電話帳。Vercel certs issue = ブラウザに「このサイトは本物」と証明する鍵（SSL証明書）を発行する手続き。OGPキャッシュ = SNSにリンクを貼った時のプレビュー画像を事前に作って保存する仕組み（毎回取りに行かないので表示が速い：32秒→数百ms）
2 AIチャットボットを複数言語に対応させたい navigator.language起点 → 入力言語動的検出 → 完全言語一貫性 navigator.language = ブラウザが持つ「ユーザーの言語設定」。日本語ブラウザなら ja-JP を返す。入力言語動的検出 = ブラウザ設定だけに頼らず、実際にユーザーが打った日本語/英語/中国語/韓国語を判定する仕組み。言語一貫性 = 途中で英語混じりにならず、全回答がユーザー言語で統一される仕組み
3 Excel業務で雑多なデータを自動整理したい 4シート統合マクロ + 再提出疑惑検出 + 冪等性設計 4シート統合 = 「受信→整形→確定→月次集計」の段階を別シートに分けて「途中経過」を人間が検証できる構造。再提出疑惑検出 = 同じ人が同じ申請を複数回出した時に自動で警告を出す仕組み。冪等性 = 同じボタンを何回押しても結果が壊れない設計（誰が押しても安心）
4 参考画像に似せた画像を量産したい flux-kontext-pro の input_image 活用 flux-kontext-pro = Replicate の画像生成AIのひとつ。input_image = テキストだけでなく「参考画像そのもの」を編集素材として受け取れるパラメータ。「テキストで全部説明する」のではなく「この絵をこう変えて」と命令できる
5 複数のAIツールを横断で使いたい（用途別に使い分け） NotebookLM MCP運用SOP（調査3分岐） MCP (Model Context Protocol) = Claude Code から外部ツール（NotebookLM, Gmail等）を直接呼べる仕組み。調査3分岐 = 「単発事実 → web_search」「複数ソース横断 → NotebookLM」「コード読解・実装方針 → deep-research」の使い分けルール
6 ココナラでサービスを出品したい（未経験） 13段階出品サイクル + 景品表示法チェック + ヒアリング型カスタム開発モデル 13段階出品サイクル = 市場調査→ひな形→分析→MVP→仮想やり取り→試用→文章→素材→出品→記録→販売分析の手順化。景品表示法チェック = 「必ず元が取れます」「黒字が出ます」等のNGワード一覧の自動照合（グレーもアウト）。ヒアリング型モデル = 購入→ヒアリング→カスタム開発→納品の流れ（ココナラ cat 230 の競合主流）
7 動画を自動生成したい（どのツールを選ぶか不明） Remotion + mulmocast-cli + Antigravity Nano Banana の使い分け Remotion = React で動画を作るツール（コード管理可能・再現性高）。mulmocast-cli = 音声+画像を組み合わせて動画を自動生成するCLI。Nano Banana = Antigravity ネイティブの画像生成
8 Excelファイルを Web経由で配布したい（社外) MOTW 回避設計 + ブロック解除ガイド MOTW (Mark of the Web) = Windows が「Webからダウンロードしたファイル」に貼る警告タグ。xlsm は MOTW が付くとマクロが実行できない。回避策はコード署名証明書（年¥20k）または手動ブロック解除（右クリック→プロパティ→ブロック解除）

B-2. 弱み（見落とし・判断ミス・運用不足）

悪いところも記載。強みの裏側にある見落とし傾向を直視する欄。

①【事前検証を飛ばして進行を許した】

  • シーン: Session 175 で .exe 配布の MOTW 問題が発覚→サンプルURL配布路線が崩壊
  • 事象: P0 フェーズで「xlsm 直渡し+サンプルURL試用」という差別化を技術検証なしに ○判定し通過させた
  • 結果: P1 実機検証で MOTW 問題露呈→サンプルURL配布全面廃止→出品文章4稿の手戻り

→ 見えた弱み: 「差別化アイデアの技術的実現性を P0 で検証する」手順が運用に組み込まれていない → 改善方針: P0 の技術検証フェーズに「配布技術のドン詰まり検証」を組み込む（Session 175 Check-out で既に指摘済み、SOP化未実施）

②【出品モデル確定を長期間先送りした】

  • シーン: Session 168 で私が納品物を作って提示するまで、納品モデル（汎用.exe即納 vs ヒアリング型）の方針が決まっていなかった
  • 事象: 作ってから「競合と違う土俵」と気づく構造。ヒアリング型は Session 169 で初めて確定
  • 結果: 汎用.exe路線で作ってきた成果物が方針転換で全て見直し対象に

→ 見えた弱み: 戦略判断（誰にどう売るか）を技術実装より先に確定する順序が弱い → 改善方針: 新プロダクト P0 に「納品モデル仮置き→競合と比較→確定」を必須ステップ化

③【AI系6商品が14日間売上0でも打ち手が出なかった】

  • シーン: cat 772 AIチャットボット6商品（業種特化3件含む）が出品後14日で販売0
  • 事象: 値下げ（dify-build ¥25k→¥10k、dify-dsl ¥5k→¥4k）と有料広告を試したが効果なし。記事内容の薄さが本丸という認識は Session 167 で持っていたが、次の具体手が Week 01 内に打てていない
  • 結果: eff-vba01 も出品しただけで、同じ失敗を繰り返すリスクが残存

→ 見えた弱み: 「何が売れない原因か」を認識してから「具体的に何を変えるか」に落とすサイクルが遅い → 改善方針: Session 183 で biz-efficiency エージェントに cat 230 競合レビュー分析タスクを指示済み。次週実行確認

④【振り返り周期の誤設計】

  • シーン: Session 183 私が「月次振り返りSOP」を提案した
  • 事象: 実際の運用速度（週1新規+毎日1本ヨコ展開=週8本）を踏まえない月次提案
  • 結果: あなたの指摘「週次じゃダメなの？」で即修正

→ 見えた弱み: 運用設計の際、実測速度を逆算する前に慣習値（月次）で提案する癖 → 改善方針: 運用提案前に「実運用の頻度・スループット」を必ず先確認する
