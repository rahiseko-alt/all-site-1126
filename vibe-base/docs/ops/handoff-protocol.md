# AI間引き継ぎプロトコル

> 本ファイルはルート CLAUDE.md の SOP索引から参照される運用手順書である。
> 単独では規範力を持たない。CLAUDE.md 本体の原則が常に優先される。

---

## 原則: memory.md だけで引き継ぐ

AI間の引き継ぎは **memory.md への書き込み・読み込みのみ** で完結させよ。

**禁止事項:**
- マスターに「このテキストを○○にコピペしてください」と依頼すること
- マスターに「○○に検証を依頼してください」等の仲介作業を求めること
- memory.md 以外の場所（チャット上の長文指示書等）で引き継ぎ情報を渡すこと

**マスターの役割はトリガーのみ:** マスターは一言で次のAIを起動する。AIは自分で memory.md を読んで状況を把握し、作業を開始する。

---

## Check-out フォーマット（全AI共通）

```markdown
## [AI名] Check-out: YYYY-MM-DD — [作業名]

- **変更ファイル:** `path/to/file-a.js`, `path/to/file-b.jsx`
- **実装概要:** [何を実装したかの要約]
- **判断根拠:** [なぜこう決めたか。設計判断・選定理由・却下した代替案を3行以内で]
- **次のステップ:** [次のAIまたは自分が何をすべきか]
- **エラー回数:** N回
```

> **判断根拠は必須。** 「何を作ったか」だけでは次のエージェントが意図を汲み取れず、設計の温度感が消失する（Session 94で実証済み）。

> **サブエージェント委託の場合:** 公式参照 https://code.claude.com/docs/en/sub-agents

---

## レビューについて

- 実装完了後のレビューは **任意**（マスターが必要と判断した場合のみ実施）
- 最終確認は、マスターがトリガーを出した場合に memory.md を読んで実施する

> **理由：** 引き継ぎのコストを最小化する。memory.md が唯一の情報ハブであり、マスターに仲介労働を発生させない。

## 外部製品の引き継ぎ（外部→vibe-base）

外部環境（エージェント等）で構築済みのコード・文書を vibe-base に取り込む場合の手順。
**原則: 外部文書はガバナンスに合わない前提で、そのまま使わず分解・再構築する。**

### ステップ1: 受領・通読

マスターから渡された外部ファイルを全て読む。この時点ではファイル作成・コード変更をしない。

### ステップ2: 構造検証（5点チェック）

| # | 検証項目 | 確認内容 |
|---|---------|---------|
| 1 | 命名規則 | kebab-case準拠か。日本語・スペース・大文字がないか |
| 2 | 配置先 | `products/` 配下のどこに置くか。既存プロダクトとの関係（独立 / 部署追加 / 営業ツール等） |
| 3 | 技術スタック | 承認済みサービスのみか。未承認サービスがあればマスター確認 |
| 4 | セキュリティ | APIキーのハードコード、シークレットの混入がないか |
| 5 | プロダクトサイクル上の位置 | P0未通過のまま実装が先行していないか。先行している場合、P0をどう扱うかマスターに確認 |

### ステップ3: P0フレームワークへの分解

外部文書の内容を以下の項目にマッピングする:

```
S1 ターゲット → 誰のどんな課題か（外部文書の記載をそのまま使わず、マスターとQAで1文化）
S1 差別化    → 何が独自価値か（同上）
S1 仮説      → 外部文書が暗黙に前提としていることを抽出し、仮説テーブルに列挙
S4 外部連携  → 使用API・サービスの一覧
S5 収益      → 収益モデル・コスト構造の素材
P1 技術情報  → フレームワーク・インフラ・DB等の決定事項
```

**重要: 外部文書の記載をそのままターゲット定義・差別化に転記しない。** マスターとのQAで正しい理解に基づいて1文化する。外部文書は「素材」であって「定義」ではない。

### ステップ4: スキャフォールド

`docs/ops/folder-lifecycle.md` シナリオ1 に従い:

1. `products/{product}/` ディレクトリ作成
2. コードファイルを配置（リネームが必要なら実施）
3. `CLAUDE.md` v1.0 作成（ステップ3の分解結果から構成）
4. `hypotheses.md` 作成（`docs/standards/templates/product-scaffold/hypotheses.md.template` を参照し、仮説テーブルを記載）

### ステップ5: memory.md記録

以下を含むmemory.mdエントリを作成する:

```markdown
## [AI名]: YYYY-MM-DD(Session) — {product} スキャフォールド+P0 S1確定

### プロダクト概要
[1-2文。このプロダクトが何で、誰のためのものか。単体プロダクトか営業ツールかも明記]

### 引き継ぎ元
[受領したファイルのパス]

### 技術スタック
[使用技術・外部サービスの一覧。セキュリティ上の要修正点も記載]

### 実施内容
[分解・構造検証・スキャフォールド・P0 QAの結果]

### P0確定内容
[S1#1ターゲット、S1#2差別化、仮説テーブルのサマリー]

### 次のアクション
[P0のどこから再開するか]
```

> **教訓（Session 38/41）:** 外部文書の記載を鵜呑みにすると構造破綻やコンセプト誤認が発生する。カテゴリレベルの構造検証を最初に実行し、マスターとのQAで正しい理解を確立してから作業に入ること。
