## §0. 設計思想

### 統合HTML方式

プロダクトのライフサイクルデータは独立した表の集合ではなく、相互参照のグラフである。
独立ファイルに分散すると手動同期が発生し、同期漏れが虚偽申告の温床になる。
これを防ぐため、S3（競合比較）とS4（実現性検証）の成果物を **1つのHTMLファイルにタブ切り替えで統合** する。

### 3原則

1. **作りながら広げる:** 最初から完全な統合を目指さない。まずS3+S4を統合し、運用しながらS5・S6・P1以降を段階的に追加する
2. **SOP常時更新:** 統合範囲が広がるたびに本SOPを改訂する。SOPが実態と乖離した状態を放置しない
3. **発明はひな形に組み込む:** 開発中に発見した「もっと良いやり方」は、そのプロダクト固有の改善に留めず、テンプレート（`docs/ops/comparison-template.html`）に反映して全プロダクトに波及させる

### 連動設計（段階的に実装）

データ間の自然な因果関係をHTML内のJSで自動反映する。目先の作業をクリアするだけでプロダクト全体が最適化される状態を目指す。

| Xを更新すると | → Yが自動反映される | 実装状態 |
|---|---|---|
| S3 機能比較で進捗を「稼働中」に変更 | → S4 #7の外部連携リストと整合チェック | 将来 |
| S4 全カテゴリの採用決定を記入 | → S4 Kill判定が自動算出 | 将来 |
| S4 フィルタ③「無料枠」に数値入力 | → S5 コスト発生マップに初期値反映 | 将来 |
| 仮説テーブルの結果を⏳→✅に変更 | → LP検証の照合対象が更新 | 将来 |

> 連動は「将来」のものも含め、本表で管理する。実装したら状態を更新せよ。

### エージェントの読み書き

HTML内に `<script type="application/json" id="product-state">` でJSON状態を埋め込む。
エージェントはJSON部分を読み書きし、HTMLはそのJSONをレンダリングするビューレイヤーとする。
（この仕様はテンプレート実装時に具体化する）

## §3. S3タブ: 機能比較

### 3.1. 競合選定

- **大手（業界の定番）** を含める
- **方向性が近い競合（規模不問）** を必ず含める。中堅・小規模でも、自社と似た方向性のサービスは調査対象
- 合計3〜5社を目安とする。列は増減可
- シェア率が不明・曖昧な業界の場合はマスターに判断を仰ぐ
- **教訓:** Aiueoで中堅業者が上位互換として既に存在していたことを見落とした。大手だけ見ていては隙間の有無を判断できない

### 3.2. 項目

- 自社 + 競合の全社が持つ機能を **全て** 羅列する（漏れ禁止）
- 料金項目（初期費用、月額、手数料等）も同じ表内に行として羅列する
- 料金項目は調査で得た情報を全て項目化する
- 月商500万円の店舗を想定したコスト試算を添える
- **マネタイズ動線カテゴリ:** 競合各社の実態を事実として記録する（無料プランの範囲/有料化トリガー/低額→上位プランの誘導要素/課金ゲート種別）。自社のマネタイズ設計はS5で行う

### 3.3. 必須列

| 列 | 内容 |
|---|---|
| # | 連番 |
| 機能 | 機能名 |
| 自社 | ○/△/× |
| 競合A〜C | ○/△/×（各社列） |
| 開発 | ☑チェックボックス |
| 進捗 | 稼働中/新規/改修/途中/除外/未着手 |
| 備考 | contenteditable |

※ 料金行・マネタイズ動線行は○/△/×ではなく実数値・事実記述を記入する

### 3.4. 必須セクション

- **開発の方向性（3指標）:** 表の上部に配置。①一言でどんな○○か ②狙うポジション ③意図vs実装の過不足
- **ポジショニング勢力図:** カテゴリ別スコアの分散から軸を自動導出しプロット（JS自動生成）
- スコア集計テーブル（JS自動計算）
- サマリーボックス3種: 致命的ギャップ / 独自強み / 差別化機会

### 3.5. ポジショニング勢力図

競合が「何を作り、何を作らなかったか」は市場調査に基づく戦略判断の結果。機能スコアの分散分析でその軸構造を逆算する。

- **軸の導出:** カテゴリ別に各社のスコアを算出し、分散が最も大きい上位2カテゴリをデフォルト軸として採用。手動で軸を変更して別視点も確認可能
- **使い方のフロー:**
  1. 勢力図を見る（競合だけの風景）
  2. 自社が狙うポジションをイメージし「開発の方向性」欄に言語化
  3. 機能表の項目を1つずつチェック（現状把握）
  4. 自社を含む勢力図で、意図したポジションに向かっているか確認
  5. ブレていたら開発計画を修正

### 3.6. 色分け

- 緑背景: 自社独自（競合全社に無い機能）
- 赤背景: 致命的ギャップ（競合全社にあり自社に無い）

### 3.7. 調査日・出典

- 表ヘッダーに調査日を記載する
- 料金・仕様の出典（公式URL等）を備考欄または表外に記録する

## §4. S4タブ: 実現性検証

### 4.1. 必須セクション（#7〜#12に対応）

| セクション | 対応タスク | 内容 |
|-----------|-----------|------|
| 外部連携洗い出し | #7 | カテゴリ（AI/DB/ホスティング/決済等）×用途×現採用×必須度 |
| 競合技術スタック比較 | #8 | S3の競合列と同じ社名で技術選択を並列比較。出典を記録 |
| カテゴリ別候補比較 | #9 | カテゴリごとに2つ以上の候補。採用/候補タグで区別。無料枠・特徴を記載 |
| フィルタ6項目評価 | #10 | 採用候補×6項目（端末互換/日本語JP/無料枠充足/障害時影響/代替手段/利用規約）の○△×表 |
| 競合との選択差異 | #11 | 自社の選択が競合と異なる点の理由+差別化可能性 |
| 採用決定+Kill判定 | #12 | カテゴリ×採用サービス×選定理由×移行トリガー。Kill条件の合否 |

### 4.2. 競合技術スタック比較のルール

- **S3タブと同じ競合列を使う。** 競合の追加・削除はS3タブで行い、S4タブに自動反映
- 調査ソースを記録する（求人票、技術ブログ、プレスリリース、BuiltWith等）
- 非公開の場合は「非公開」と記載し推測で埋めない

### 4.3. フィルタ6項目の定義

| # | 項目 | 評価基準 |
|---|------|---------|
| ① | 端末互換性 | 客の想定端末・ブラウザで動くか |
| ② | 日本語・日本リージョン | 日本語対応・日本リージョンで制限がないか |
| ③ | 無料枠充足度 | 無料枠の上限は客数に足りるか。超えたらいくらか |
| ④ | 障害時影響 | そのサービスが落ちたらうちはどうなるか |
| ⑤ | 代替手段 | 代わりの手段はあるか |
| ⑥ | 利用規約適合 | 利用規約でうちの使い方が禁止されてないか |

### 4.4. Kill条件の表示

- S4のKill条件をS4タブ末尾に表示
- フィルタ結果から自動判定が可能な場合はJS で PASS/FAIL を表示（将来）
