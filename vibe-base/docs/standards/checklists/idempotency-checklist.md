# 冪等性チェックリスト（vest1）

> **対象:** DB永続化・外部API・決済・通知を扱う全プロダクト
> **使用タイミング:** スキーマ + トランザクション設計着手時 / コア機能レビューで再確認
> **起源:** Qiita#16「トランザクション・冪等性確保」をチェックリスト化

---

## なぜ冪等性が必要か

冪等性 = 同じ操作を何回実行しても結果が同じになる性質。これがないと：

- ユーザーがダブルクリックで決済が2重に走る
- ネットワーク再送で通知が2回飛ぶ
- リトライで在庫が2回減る
- 障害復旧時のリプレイで状態が壊れる

**「ユーザーから見える結果」を1回に収束させる設計を、実装前に決めておく**のが本チェックリストの目的。

---

## §1. 冪等性が必要な処理（必須カテゴリ）

| カテゴリ | 例 | 二重実行時のダメージ |
|---|---|---|
| **決済** | Stripe Charge / 銀行振込 / ポイント消費 | 二重課金（クレーム+返金処理） |
| **通知** | メール送信 / SMS / Push通知 / Slack | 信用低下・スパム判定 |
| **DB書込** | 注文作成 / 在庫減算 / カウンタ加算 | データ不整合（在庫マイナス等） |
| **外部API呼出** | OpenAI生成 / GitHub Issue作成 / Twitter投稿 | API課金二重・重複コンテンツ |
| **ファイル生成** | PDF生成 / 画像処理 / レポート作成 | ストレージ無駄・命名衝突 |

**判定基準:** 「同じ処理を2回実行されたとき、ユーザー or システムに不具合が出るか？」がYesなら冪等性が必要。

---

## §2. 冪等キー設計

### キー生成パターン
| パターン | 用途 | 例 |
|---|---|---|
| **クライアント生成 UUID v4** | フォーム送信・ボタンクリック | フォーム表示時にUUID生成、submit時に送信 |
| **Idempotency-Key ヘッダー** | REST API（Stripe方式） | `Idempotency-Key: 7e1c...` をリクエストに付与 |
| **業務キー由来** | 注文・予約等の自然キー | `order:{userId}:{cartHash}:{ymd}` |
| **コンテンツハッシュ** | 通知・メール | `email:{recipient}:{sha256(body)}` |

### キーの永続化
- DBにユニーク制約（UNIQUE INDEX）で記録
- TTL（24時間〜30日）を設定して古いキーをクリーンアップ
- Redis等のキャッシュは「補助」止まり、最終的な冪等性保証はRDBで取る

### キー設計の禁忌
- タイムスタンプのみのキー（同一秒に2回来ると衝突）
- ユーザーIDのみ（同一ユーザーが別アクションを実行できなくなる）
- 自動採番のみ（クライアントから事前送信できないため再送リスク）

---

## §3. トランザクション境界の決定

### 境界判定の3問
1. **どこまでが「1単位」か？**（複数テーブル更新が1単位なら同一トランザクション内）
2. **失敗時にどこまで戻すか？**（全部 or 部分。ロールバック可能性で決める）
3. **外部API呼出を含めるか？**（含めない方が原則。詳細は次項）

### 外部API呼出を含むパターン（要注意）
- **DB書込 → 外部API → DB書込のサンドイッチ構造は避ける**（DB側で行ロックしたまま外部APIを待つことになる）
- **推奨パターン:** 外部API呼出は別ジョブ（キュー経由）に分離、結果はWebhookで反映
- **どうしても同期的に呼ぶ場合:** 短いタイムアウト（5秒以下）+ サーキットブレーカー必須

### Saga パターン（マイクロサービス・分散トランザクション）
- 複数サービスを跨ぐトランザクションは、各ステップに補償アクション（Compensation）を用意
- 例: 注文作成 → 在庫減算 → 決済。決済失敗時は「在庫戻し」「注文キャンセル」を逆順で実行

---

## §4. リトライポリシー（指数バックオフ）

### 基本方針
- リトライ前に**冪等キーが既に処理済みか確認**してから実行
- 1回目失敗 → 2回目実行 ではなく、1回目失敗 → 「これは2回目か?」確認 → 既処理なら結果返却 / 未処理なら実行

### バックオフパターン
```
初回失敗: 1秒待機
2回目失敗: 2秒待機
3回目失敗: 4秒待機
4回目失敗: 8秒待機（最大4回まで）
5回目以降: dead-letter queue へ送信、人手調査
```

### ライブラリ・サービス
- **クライアント側:** `axios-retry`, `p-retry`, `tenacity`(Python)
- **サーバー側キュー:** AWS SQS, Cloud Tasks, BullMQ, Sidekiq
- **Stripe:** 公式SDKが自動リトライ（Idempotency-Key前提）

### リトライしない場合
- 4xx エラー（400/401/403/404/422）はリトライ不要（クライアント起因）
- 5xx エラー（特に 500/502/503/504）と Network error はリトライ対象
- 429 Too Many Requests は `Retry-After` ヘッダーに従う

## §5. チェックリスト

実装前 / コア機能レビュー時に下記を全件確認。

- [ ] §1の必須カテゴリのうち、本プロダクトで該当する処理を洗い出した
- [ ] 各処理に冪等キーを設計した（クライアント生成UUID / Idempotency-Key / 業務キーのいずれか）
- [ ] 冪等キーの保存先を決定した（DBのUNIQUE INDEX 等。Redisのみは不可）
- [ ] 冪等キーのTTL（保持期間）を決定した（24時間〜30日のレンジで合意）
- [ ] トランザクション境界を明示した（どこまでが1単位か、失敗時の戻し方）
- [ ] 外部API呼出は同期的トランザクションに含めない設計にした（or 短タイムアウト+CB付き）
- [ ] リトライ戦略を定義した（指数バックオフ・最大回数・dead-letter送信）
- [ ] リトライ前に冪等キー確認を入れた（既処理なら過去結果を返す）
- [ ] 4xx/5xx/network エラーごとのリトライ判断を実装した
- [ ] 二重実行テストを書いた（同じキーで2回POST → 1回しか反映されないことを確認）
- [ ] 異常系（ネットワーク切断中の再送・タイムアウト後の重複送信）を再現テストした
- [ ] 監視: 冪等キー衝突発生数を Sentry / ログで観測できるようにした

**全項目クリアで設計レビュー通過。1項目でも未達ならコア機能実装に進めない。**

## §6. プロダクト別の必須対象（参考）

| プロダクト類型 | 冪等性必須の処理 |
|---|---|
| 決済を扱うEC・SaaS | Stripe Checkout / 注文作成 / ポイント付与 |
| AIサービス | OpenAI生成 / 画像生成 / クレジット消費 |
| メール配信 | 送信履歴・購読解除・ウェルカムメール |
| 予約・スケジュール | 予約確定 / キャンセル / リマインダー送信 |
| 在庫を扱う | 注文確定 / 在庫減算 / 入荷反映 |
