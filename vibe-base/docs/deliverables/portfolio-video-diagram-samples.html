動画編集自動化を、プロセスと結果で分けて見せる

現行ポートフォリオはそのまま残し、動画素材から見どころを抽出して編集・配布準備する仕組みだけを別表現にした判断用ページです。プロセスは「誰が何をするか」、結果は「手作業がどう減るか」に分けて確認します。

解決する課題

長尺動画の確認、文字起こし、見どころ探し、短尺候補づくり、字幕・縦横調整、配布前チェックまでを毎回人が行うと、編集前の下準備だけで時間が溶けます。この仕組みでは、AIが発話の読み取り、候補抽出、切り出し案、出力準備までを担当し、人は最初の条件決めと最後の採用判断に集中します。実測では、61分32秒の素材をGroq利用時に76秒で文字起こしし、7本のショート候補を生成、カバー率98.2%まで確認できました。

さらに、低解像度素材の無意味な拡大エンコードを止めたことで、レンダリング時間は924秒から303秒へ短縮しました。つまり、AIに任せるのは「公開判断」ではなく、確認前の下処理と候補づくりです。得られるものは、公開前に人が選べる短尺候補、字幕・縦横を整えた配布用素材、次回改善に使える運用ログです。

1. 統合プロセス図

4の運用ループ型をベースに、上から下へ進む工程図に整理。各工程は左が発注者向けの作業説明、右が対応する技術・実装要素です。

作業フロー 技術説明
  1. 素材と目的を渡す（ヒト）動画、用途、尺、NG条件を決める
    この工程は人の判断

    ここではまだ自動処理を始めない。人が、動画ファイル、使う媒体、目標尺、字幕の有無、縦横、避けたい表現、公開NG条件を決める。AIに任せる前に、何を作ってはいけないかを入力として揃える。

  2. 編集条件を固定する（AI）人が決めた条件を後続工程の共通ルールにする
    pipeline.mjs init / hooks / state.json

    pipeline.mjs init が、人の入力した編集モード、字幕有無、縦横、用途、NG条件を state.json に保存する。以後の transcribe、select、render はこの状態を参照し、工程ごとに条件がずれないようにする。

    • --mode、--sub、--orient 未指定なら停止し、決め打ち実行を防ぐ。
    • topic と digest を分け、話題単位カバーとAI編集エージェント型の用途を切り替える。
    • 実測素材は 61分32秒 のインスタライブ動画。処理開始前に編集モード、字幕有無、縦横を固定した。
  3. 発話と場面を読み取る（AI）長い動画を確認しやすい素材へ分解する
    FFmpeg 音声抽出 / faster-whisper / Groq whisper-large-v3-turbo

    FFmpeg で動画から音声を取り出し、ASRに渡す。ローカルは faster-whisper、クラウドは Groq whisper-large-v3-turbo を使い、鍵や速度要件に応じてフォールバックできる構成にする。word-level のタイムスタンプを保持し、後工程で切り出し位置へ戻せるようにする。

    • transcribe 工程で全文テキスト、単語時刻、発話区間を中間データ化する。
    • term-corrections.json で専門用語や固有名詞の補正を入れられる。
    • 実測では Groq 自動選択で 61分32秒 素材の文字起こしが 76秒。
    • 文字起こし精度の数値評価は未計測。医学用語・固有名詞は誤変換リスクがあるため term-corrections.json で補正する前提。
  4. 見どころ候補を作る（AI）使えそうな切り出しと構成を複数出す
    Claude / claude -p / LLM区間選定 / timestamp逆マッチング

    select 工程で文字起こし全文をLLMに渡し、話題単位またはダイジェスト用の候補区間を選ぶ。Claude や claude -p は、全体理解、台本再構成、候補批評、修正ループの判断役として使う。LLMの出した文章上の候補を、word-level timestampへ逆マッチングして実際の動画区間へ戻す。

    • topic は話題の切れ目ごとに時系列で候補化する。
    • digest は面白い箇所を選び、素材音声のまま台本再構成する。
    • 実測では 61分32秒 素材から 7本 のショート候補を生成し、カバー率は 98.2%。
    • 話題分割の調整では TOPIC_MIN_SEC 既定 180s、細切れ候補を 13本→7本 に整理した記録がある。
  5. 採用・修正を判断する（ヒト）公開してよい内容だけを選ぶ
    この工程は人の判断

    LLMが作った候補をそのまま公開しない。人がプレビューを見て、採用、破棄、修正の判断をする。技術は判断を代替せず、候補、開始秒、終了秒、選定理由を確認しやすく並べるだけに留める。

    • 明らかなNG、準備中、音声テスト、カット相談など本編でない箇所を落とす。
    • 採用・破棄の判断を出力対象と切り離し、誤公開を防ぐ。
    • 実測では ui/index.html?job=insta-live-herunia で 7本 の候補を確認する導線を用意した。
  6. 承認結果を出力対象にする（AI）人が選んだ候補だけを次工程へ渡す
    候補選別UI / レビューキュー / 承認ログ

    ui/index.html?job=<id> で人が選んだ候補だけを、レンダリング対象として確定する。候補一覧、開始秒、終了秒、選定理由、採用状態を分けて扱い、未承認の候補が出力工程へ流れないようにする。

    • 候補生成と出力対象を分離し、AIの提案と人の承認を別データとして扱う。
    • 承認済み候補だけを render 工程へ渡し、誤公開リスクを下げる。
  7. 配布できる形へ整える（AI）字幕、縦横、説明文、ファイル名を整える
    FFmpeg / ASS / libass / 縦横変換 / レンダリング

    render 工程で承認済み候補だけを動画化する。FFmpeg で切り出し、縦型なら render-vertical.mjs で 1080x1920 系のキャンバスへ変換し、字幕ありの場合は ASS / libass で字幕を焼き込む。低解像度素材では無意味な拡大エンコードを避けるガードも入れる。

    • ffprobe で素材解像度を確認し、拡大ガードや画質モードの判断に使う。
    • libx264、crf、preset などのエンコード条件を用途に合わせる。
    • 低解像度素材 432x766 では、拡大ガード実装後に render 924秒→303秒、3.05倍速 を確認。
    • 拡大ベンチは 1080x1920=9.6s、720x1280=5.0s、432x768=3.0s で、無意味な拡大が遅さの主因だった。
  8. 次回条件へ戻す（ヒト）採用理由や修正点を運用ルールに戻す
    この工程は人の判断

    納品して終わりにせず、どの候補が使いやすかったか、何を落としたか、字幕や尺で直したい点は何かを人が判断する。次回に反映したい好みやNG例を、運用ルールとして残す。

  9. ログを残して改善点を見える化する（AI）時間、候補数、失敗箇所を次回改善の材料にする
    timing.json / 運用ログ / ルール更新

    各工程の所要時間、採用された候補、不採用理由、字幕修正、尺の傾向をログとして残す。実走では transcribe、select、render の時間計測や timing.json を使い、遅い工程や品質課題を次の改善対象にする。

    • 採用傾向、NG例、修正履歴を次回の state.json や運用ルールへ戻す。
    • レンダリング時間、ASR時間、候補数を見て、ボトルネックを切り分ける。
    • 実走ログでは transcribe 76秒、旧 render 924秒、改善後 render 303秒 のように、改善前後を比較できる。
人の判断を消さずに、確認結果だけを次回条件へ戻す
