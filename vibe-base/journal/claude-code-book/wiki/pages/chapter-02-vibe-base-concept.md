# 第2章 vibe-base の構想

## この章で書くこと

第1章では、Claude Code を使い始めた日に私がコードを1行も書かず、
代わりに `CLAUDE.md` と `MISSION_LOG.md` とフォルダ構造を作った、という事実を書きました。
第2章で書くのは、その背後にあった考え方です。

- なぜ vibe-base という名前の「共通基盤」を立てる必要があったのか
- AI共通憲法 v1.0 に何を書き、何を書かなかったのか
- 「1フォルダ=1エージェント」というモデルはどこから出てきたのか
- MISSION_LOG を単なる作業日報ではなく「台帳」として設計した理由

このあたりを書いていきます。

---

## 先に警戒していたこと

Claude Code を本格導入する時点で、私が心配していたことは2つありました。

1つ目は、**セッションを跨いだ瞬間に記憶が消える**こと。
Claude Code は優秀なのですが、1セッション終わって次のセッションが立ち上がるとき、
そこにいる Claude は前回の Claude とは別人です。前回の判断理由も、途中で捨てた選択肢も、
やり残した問題もすべて忘れています。この「記憶の断絶」を前提にしないと、
「前はこうしたはずなのに」という事故が日常的に起きます。
私はプロローグで書いた1か月の経験からそれを知っていたので、最初に手を打とうと思いました。

2つ目は、**複数の AI が同時に同じコードを触ったら衝突する**こと。
当時の私はすでに、設計・実装・レビューを違う AI に振り分けようとしていました。
1つの作業場に複数の AI が並走する前提で動くなら、縄張りを切らないと
「どっちが最新か分からない」状態にすぐ落ちます。

この2つは、どちらも Claude Code のせいではありません。
AI をチームとして使おうとする瞬間に、どんな人間のチームでも発生する問題だと思います。
ただ、人間のチームなら Slack と GitHub と口頭引き継ぎで何とかします。
AI のチームはそのどれも使えない。だから、その穴を先に埋めておく基盤がいる。
それを置く場所として、私は `vibe-base` というフォルダを切りました。

名前の由来はいたって適当です。「vibe」は当時の私が気に入って使っていた曖昧な言葉で、
「base」は土台のつもりです。かっこいい語源の話はありません。
ただ、これが「プロダクトそのもの」ではなく「プロダクトを載せる基盤」だということだけは、
名前で分かるようにしておきたかった。

## CLAUDE.md v1.0 に書いたこと（と、書かなかったこと）

初版の `CLAUDE.md` に書いた条文は、ごく少なかったです。
今の v5.2 は §0 から §6 まで章立てされ、メタルールやセルフガバナンスの規定がぎっしり詰まっていますが、
v1.0 はもっとずっと薄かった。正直に言えば、骨格は3つしかありませんでした。

### ① 命名規則 ― kebab-case 必須

今の §4 にも生き残っている、たった1行のルールです。

> 命名: kebab-case必須。日本語・スペース・大文字（拡張子除く）禁止

この1行は、書いた翌日から効きました。
第1章で書いた通り、当時の私は旧環境から6本のプロジェクトを引き取ろうとしていて、
そのすべてに日本語フォルダ名や全角スペースが混じっていました。
`モバイルオーダー＆管理システム/` とか、`Wikipedia　自動生成bot/` とか。
`CLAUDE.md` にこの1行があるだけで、Claude は受け入れ前に必ずリネームするようになりました。
私はそのたびに「やって」としか言っていない。
ルールを書いておけば、ルールの説明をしなくていい。これが憲法を置く最大の効用だったと思います。

### ② 作業ディレクトリの分離 ― 各エージェントに縄張りを

当時のフォルダ構成はこうでした。

```
vibe-base/
├── CLAUDE.md
├── MISSION_LOG.md
├── agent-ag/          ← 別の AI エージェントの作業場
│   ├── mobile-order-system/
│   ├── shift-board-app/
│   ├── x-auto-post-bot/
│   ├── booking-app/
│   ├── review-analysis-bot/
│   └── wikipedia-draft-bot/
└── （Claude 自身の作業スペース）
```

`agent-ag/` というフォルダ名は、「AG」と呼んでいた別の AI エージェントの縄張りを
物理的に見えるようにしたものです。Claude は設計とレビューだけを担当して、
`agent-ag/` 配下のファイルには書き込まない。AG は `agent-ag/` の中だけで実装する。
同じ作業場だけど、触っていい場所が違う。

この「1フォルダ=1エージェント」というモデルは、v1.0 の条文には明記されていませんでした。
条文として明記されたのはもっと後の版です（現行の v5.2 §0 にようやく太字で書いてあります）。
それでも最初の Check-out ログに「各エージェント作業ディレクトリを整備した」と
はっきり書いてあるので、実装としては初日から存在していました。
条文化が遅れた理由は、たぶん「当たり前すぎて書くまでもなかった」からだと思います。
その「当たり前」が、後に複数プロダクトの並列運用を支える軸になるとは、この時点では想像していませんでした。

### ③ MISSION_LOG という「台帳」

v1.0 の憲法がやったことで、おそらく一番大きいのは
**MISSION_LOG.md を「作業日報」ではなく「台帳」として位置づけた**ことだと思います。

どう違うのか。日報は「その日やったこと」を書きます。
台帳は「その仕事を次に引き継ぐ人に必要な情報」を書きます。
似ているようで、役割が違います。

v1.0 の MISSION_LOG は、セッションの終わりごとにこういう情報を持っていました。

- **現状:** 今どこまで進んでいるか
- **次のステップ:** 次のセッションの Claude が何をすべきか
- **エラー回数:** 同じ場所で何回失敗したか
- **技術的負債:** 見つけたけどこのタイミングでは直さないもの

重要なのは、これらが全部「次の自分への手紙」の形で書かれていることです。
自分が明日忘れても、明日の Claude がこの1ファイルを読めば作業を再開できる。
そのために必要な情報だけを、毎回同じフォーマットで残す。

これが機能するのは、次に動く Claude が「読めと書いてある」からです。
`CLAUDE.md` の側に「セッション開始時に MISSION_LOG を読め」と書いておけば、
Claude は勝手にチェックインしてくれます。台帳と憲法は、2つ合わせて1つのシステムで、
どちらが欠けても引き継ぎは成立しない、ということに気づいたのはこの頃です。

ちなみに、v1.0 の MISSION_LOG は「全部のセッションを1つのファイルに書く」設計でした。
これは2日後の v1.1 で早速「直近5件制」に改訂されます。
容量がすぐ逼迫することが分かったからです。「アーカイブに流す」という運用は
このタイミングで生まれました。最初から正解を書けていたわけではありませんでした。

### v1.0 に「書かなかった」こと

一方で、v1.0 が敢えて書かなかった（もしくは、書く発想がまだなかった）こともあります。
これは改訂履歴を逆算すると分かります。

- **横断チェック必須ルール** ― v1.3（2月28日）で追加。バグを1箇所直すとき、同じパターンが
  他のファイルにも潜んでいないか全文検索してから直す、という作法。v1.0 にはありません
- **三打席ルール** ― 現行の形（「同一箇所3回失敗でコミット＆引き継ぎ」）は v1.8（3月5日）で精緻化されました。
  原始的な形は v1.0 〜 v1.7 のどこかで入った可能性がありますが、確証はありません
- **AIセルフガバナンス（§5）** ― v1.8 で新設。フェーズゲート、先行バリデーション、能力限界の事前申告など、
  「AI が自分で自分を縛る」ための条文群です。v1.0 にはまったく存在しませんでした
- **メタルール（Refactor-on-Write / Reference-over-Redundancy / Self-Correction Loop）** ― v3.0（3月9日）で新設。
  「ルール追加時は統合を先に検討せよ」「1箇所に定義し他は参照せよ」といった、憲法そのものの運用ルールです

v1.0 は、いわば「AI が暴走した時の対策条項」を一切持っていませんでした。
命名と縄張りと台帳。それだけです。
暴走対策は、実際に暴走が起きてから1条ずつ追加されました。これは次章で詳しく書きます。

## この憲法が2か月後の今、どう見えるか

現行の v5.2 は、改訂履歴を見れば分かる通り、
v1.0 → v1.1 → v1.8 → v2.2 → v3.0 → v4.0 → v4.9 → v5.2 と、
2か月で 25回以上改訂されています。450行あった時期もあれば、
v3.0 で120行に圧縮された時期もありました。
条文の数だけ見れば、v1.0 から別物になったと言っていいくらいです。

それでも、骨格は v1.0 のままだと思います。

- §0 に書かれている「1フォルダ=1エージェント」は、Session 1 の `agent-ag/` そのもの
- §4 の kebab-case は、v1.0 から一字一句変わっていない
- MISSION_LOG を「台帳」として読ませる仕組みは、直近5件制やアーカイブへの分割を経ても、
  本質は v1.0 から動いていない

追加されたのは規律であって、思想ではない。
v1.x で増えた条文（横断チェック・三打席・AIセルフガバナンス）も、
v3.0 で新設されたメタルールも、v4.0 のプロダクトサイクルも、
すべて「v1.0 で決めた3つの骨格を守らせるための工夫」だと見ることができます。

思想を先に書き、そのあと守らせるための規律を積み足していく。
この順番を逆にしていたら、たぶん今の vibe-base は存在していなかったと思います。
規律を先に積むと、そもそも何のための規律なのかが分からなくなって、
改訂のたびに整合が崩れます。骨格が先にあるから、あとからどんな条文を足しても
「これは骨格のどこに効くのか」を判定できる。

これが、vibe-base を `CLAUDE.md v1.0` からスタートさせた、最大の実感です。

## 次章予告

次章では、その v1.0 → v1.8 → v3.0 → v4.0 という改訂の流れを、
「実際にどういう事件が起きて、どの条文が増えたのか」という観点で追います。
憲法は机の上で書かれたものではありません。現場で Claude が転んだ回数だけ、条文が増えました。
その転倒記録と、追加された条文の対応関係を、具体的に並べていきます。
