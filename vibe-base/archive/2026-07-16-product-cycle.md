# プロダクトサイクル詳細（P0→P4）

> 本ファイルは CLAUDE.md §2 の詳細SOPである。フェーズ定義・ゲート条件の正規定義は CLAUDE.md §2 が優先。

## サイクルの基本原則

P0→P4 は **1周で終わりではない。** P4#5「Continue」判定でP0に戻り、次の周回を開始する。

```
P0 → P1 → P2 → P3 → P4
↑                        ↓
└──── Continue ──────────┘
```

- **ループ時:** 各フェーズのステータスを上書き。過去サイクルの記録はmemory.mdアーカイブに残る
- **スキップ:** 完了済みフェーズ・変更不要なタスクはスキップ可（例: 2周目のP2はデプロイ+動作確認のみ）
- **P4#5の判定:** Continue（→P0に戻る） / Pivot（コンセプト変更して再スタート） / Retire（撤退）

## P0: 企画

P0は **6段階のふるい落とし** で構成される。各段階で「ダメならここで止める」判定があり、死んだアイデアに後工程のコストをかけない。

```
S1 思い付きを言葉にする → S2 客がいるか調べる → S3 ライバルを調べる → S4 外部連携を選んで作れるか確かめる → S5 儲かるか確かめる → S6 やることを決める
         広い ──────────────── やめ判定で絞る ──────────────── 狭い
```

**やめ判定の運用ルール:**
- やめ判定はAIに委任。明白な場合のみ即マスターに報告し中断
- マスターが「続行」と判断すれば続行（リスクとして仮説テーブルに記録）
- 正式ゲートはS6#18の1箇所のみ

**仮説テーブル:**
- 保管: `products/{product}/hypotheses.md`（永続独立ファイル・仮説テーブルの単一正本）。plan から参照する
- 形式: `| ID | 致命度 | 仮説 | 発見 | 検証 | 結果 | 備考 |`
- 致命度: 即死（崩れたら商品不成立）/ 重要（崩れたら大幅修正）/ 補助（崩れても回避策あり）
- 結果: ✅確かめた / ❌ハズレ / ⏳まだ（検証予定記載） / — 手をつけてない
- 「これがウソなら商売成り立たない」を基準に全前提を列挙
- **即死→P1連動:** 致命度「即死」の仮説はP1#9a（即死仮説の実機検証）で実装ベースの検証を必須とする。⏳のままP1ゲートを通過できない
- 参照タイミング: P0#13（リスク予備フィルター）、P1#9a（即死仮説検証）、P1#12（壊れたらどうなるか）、P2#1（LP構成設計の入力情報）、P2#5-8（SEO入力ソース）、P2#19（LPに嘘がないか）、P2#20（客の環境で動くか）、P4（⏳の検証）

## §10. ★レビュー チェックリスト集

★レビュータスクで使用するチェックリスト。全項目クリアで合格。

> **CL 集約方針**: 5 項目以下の短い CL は §10 内集約、6 項目以上の長い CL は `docs/standards/checklists/` に分離。CL-14（12 項目）等の既存長い CL の別ファイル化は後続セッションで個別判断。新規 CL も項目数で分離判断する。

### CL-1: P1#5 コア機能、ちゃんと動くか？

> **必読:** `docs/ops/test-template-guide.md`（テストケースの構成・レスポンシブ検証ポイント）
> 冪等性は P1 テンプレ表「冪等性チェックリスト」(#3a, #5) で発火（CL-1 で重複参照しない）

1. 仮データ・ベタ書きの値が残ってないか
2. APIキーなどの秘密情報がコードに埋まってないか（.envに分離）
3. 壊れたとき、ユーザーにエラーが伝わるか
4. DBへの保存が途中で止まらないか
5. 障害が起きたとき原因を追えるログが出るか
6. 不正な入力をはじけるか。認証・認可は機能するか
7. 想定人数で使っても遅くならないか

### CL-2: P1#9 外部APIとの接続、大丈夫か？

1. 使ってるAPI全部が実在して、ドキュメント通りに動くか
2. APIキーやOAuthの認証が正しく組めているか
3. 無料枠の上限を把握して、超えたときの挙動を確認したか
4. データが大量に返ってきたとき（ページネーション）の処理は正しいか
5. APIがエラーを返したとき（4xx/5xx）、ちゃんと拾えているか
6. APIが応答しないとき、タイムアウトで止まるようになっているか
7. 返ってきたデータの形式チェック（パース・バリデーション）は正しいか

### CL-3: P1#12 壊れたらどうなる？

> **必読:** `docs/ops/failure-scenario-template.md`（7カテゴリの障害分析フレームワーク）

1. 似たサービスで実際に起きた障害を3件以上調べたか
2. お客さんが遭遇しそうなトラブルを3件以上洗い出したか
3. 上記から「再現テスト」を8件以上作ったか
4. 各テストで: エラーがユーザーに伝わるか
5. 各テストで: データが消えないか
6. 各テストで: 直し方があって、実際に直せるか
7. 結果をマスターに見せてOKをもらったか

### CL-4: P2#12 リンク・ボタン・フォーム、全部押して確認

1. サイト内のページ間リンクが全部ちゃんと飛ぶか
2. ページ内ジャンプ（アンカー）が正しい場所に行くか
3. 外部リンク（法令ページ・外部サービス）がリンク切れしてないか
4. CTAボタンを押したらフォームや決済画面がちゃんと開くか
5. フォーム: 入力→送信→確認メッセージ、全部動くか

### CL-12: P2#2 LPは売れるか？（品質レビュー）

> **必読:** `docs/ops/design-doc-templates.md` §4（ペルソナ+ジャーニーマップをLP設計と照合）

**コピー品質:**
1. **ファーストビュー3秒ルール**: 3秒以内に「誰向けの何で、使うとどうなるか」が伝わるか
2. **AI美辞麗句ゼロ**: 「革新的」「シームレス」「加速」等のAI臭い表現を使っていないか。ターゲットのリアルな言葉で書いているか
3. **PASONA要素の充足（順序固定ではない）**: Problem/Agitation/Solution/Offer/Narrow/Action の各**内容要素**が揃っているか。**縦の固定順序は問わず、骨格はスクロール・操作・次元を再発明しているか**（骨格パラダイム・`docs/standards/web-design-flow.md`）。全幅ブロックを定型順に縦通過するだけ＝金太郎飴で不合格
4. **検証可能な証明**: 数字・期間・固有名詞を伴う具体的根拠が配置されているか（曖昧な実績は不合格）
5. **CTA配置**: ファーストビュー+中間+末尾の最低3箇所にCTAがあるか。ボタンテキストは行動を具体的に書いているか
6. **競合差別化（コピー）**: 競合LP分析テーブルの「弱い点」を自社の強みとして打ち出しているか。競合と同じことを言っていないか
7. **不安払拭**: FAQ or 保証が明示され、「最悪でも損しない」と思えるか

**デザイン品質:**
8. **競合差別化（デザイン）**: 競合デザイン分析テーブルを踏まえ、視覚的に差別化できているか。競合と同じに見えないか
9. **Hero画像/動画**: 「何のアプリか」が画像で伝わるか。ストックフォト感がないか
10. **信頼要素のビジュアル**: 数字は大きく表示、顧客の声は顔写真+実名、ロゴは横並べ等、視覚的に信頼を構築しているか
11. **モバイル表示**: スマホで情報が潰れず、CTAがタップしやすいか。LCP 2.5秒以下か

> **詳細手順:** `docs/ops/lp-design-sop.md` を参照

### CL-14: P2#15 コードの品質は大丈夫か？

> **必読:** `docs/standards/checklists/library-verification-checklist.md`（ライブラリ実在性検証。AI hallucination + タイポスクワッティング検知）

1. 未使用のコード・コメントアウトされたコードが本番に残っていないか
2. `console.log` / デバッグコードが本番に残っていないか
3. エラーハンドリングが統一されているか（try-catch漏れ、エラーメッセージの一貫性）
4. 型定義（TypeScript）に `any` が多用されていないか
5. コンポーネント/関数の責務が明確か（1ファイルが肥大化していないか）
6. パフォーマンス上の問題がないか（不要な再レンダリング、N+1クエリ、未圧縮画像等）
7. 命名規則がプロジェクト内で統一されているか（kebab-case必須）
8. 画像/フォントが最適化されているか（WebP/AVIF・`next/image`・`font-display: swap`・不要ウェイト削除）
9. 新規追加された npm/pip パッケージが公式リポジトリに実在するか検証済みか（library-verification-checklist.md 全項目）
10. コードを行単位で説明できるか（AI生成の不要処理・意図不明なマジックナンバー・正規表現が残存していないか）
11. 認証不要エンドポイントに送信側レートリミットが実装されているか（`docs/ops/rate-limit-sop.md` §1の必須対象を全件カバー）
12. 本番環境で詳細エラーを返却していないか（スタックトレース・SQL・内部パスを露出していないか。`errorId` のみ返却＆ログ照合）

### CL-15: P1#9a 即死仮説、実機で成り立つか？

### CL-16: P2#27 運用準備、本番稼働できる状態か？
