# 第1章 Claude Code との出会い

## この章で書くこと

私が Claude Code を本格的に使い始めた 2026年2月下旬の数日間の記録です。
コードを書き始める前に何をしたか、そしてなぜそうしたかを残しておきます。

---

## 2月24日 ― コードより先にインフラを建てた

Claude Code を初めて真面目に触った日、私はコードを1行も書きませんでした。
代わりにやったのは、こういうことでした。

- `vibe-base/` というフォルダを切る
- `CLAUDE.md`（AI共通憲法 v1.0）を書く
- `MISSION_LOG.md`（引き継ぎ台帳）を空で置く
- 各エージェント用の作業フォルダを分ける
- `git init` して Initial コミット

たったこれだけです。機能はゼロ。動くものは何もありません。
それでも、この日の作業ログには「Vibe-Base インフラの初期構築完了」と書いてあります。

なぜ先にこういうものを作ったのか。
正直に言うと、「先にやっておかないとあとで困る」という予感があったからです。
Claude Code を「自分の代わりにコードを書いてくれる便利ツール」として使うなら、こんな準備はいらないと思います。
でも私がやろうとしていたのは、もう少し複雑なことでした。

必要になると思っていたのは3つです。

- 複数のセッションにまたがっても記憶が飛ばないための「台帳」
- どこまで触っていいか決めた「憲法」
- 他のエージェント（AIの別担当者、という意味です）と衝突しないための「縄張り」

これを最初に決めておかないと、2日目か3日目に必ず破綻する、と思いました。
そう思った根拠は、プロローグに書いた「日を跨ぐと後戻りする」という経験です。
先にルールを書いておけば、AI がそのルールを守って動いてくれる。そう信じることにしました。

結果的にこの判断は正しかったと思います。2か月後の今、作業ログは 160 回以上の記録を持っていて、
私がセッションを跨いでも、新しい Claude は前回の続きから作業を再開できています。

## 2月24日午後 ― 最初の「実戦」は命名規則の強制リフォーム

その日のうちに、2本目のセッションが始まりました。お題はこうでした。

> 持ち込んだ「モバイルオーダー＆管理システム」を kebab-case にリフォームせよ

kebab-case というのは、ファイル名の単語をハイフンでつなぐ書き方のことです（例: `my-file-name`）。
当時、私はすでにいくつかの個人開発の資産を別の場所で動かしていました。
Claude Code でそれを引き取るにあたって、Claude が最初にやったのは **機能の追加でも、バグの修正でもありませんでした**。
やったのは、日本語フォルダ名の英語化と、計18ファイルの名前の書き直しでした。

```
モバイルオーダー＆管理システム/  →  mobile-order-system/
```

一見、どうでもいい作業に見えます。機能的には何も変わっていません。
でも、CLAUDE.md v1.0 には「kebab-case 必須。日本語・スペース・大文字（拡張子除く）禁止」と書いてありました。
これは後続のすべての AI が「何をファイル名にしていいか」を迷わないために先に決めたルールです。
持ち込みプロジェクトがこのルールを破っているなら、受け入れる前に直す。

この日の作業ログに書かれたエラー回数は「1回」でした。
理由は「Windows ケース不感度問題」というもので、大文字小文字だけを変えるリネームが Windows では無視されるため、
一度別名にしてから本来の名前に戻す 2段階の手順で回避したそうです。
こういう小さな罠は、マニュアルには書いていません。踏んで、記録して、次に渡すしかないのだと分かりました。

## 2月25日 ― 持ち込み案件の連鎖リフォーム

翌日は、持ち込みリフォームが連続しました。

| プロダクト | 旧状態 | やったこと |
| --- | --- | --- |
| shift-board-app | 日本語ファイル名 | 全20ファイルをリネーム |
| x-auto-post-bot | 同上 | 同様にリフォーム |
| booking-app | 同上 | import パス（ファイル参照先）も修正 |
| review-analysis-bot | 同上 | 12ファイルリネーム + import 5箇所修正 |
| wikipedia-draft-bot | 同上 | 26ファイルリネーム + 設定ファイル修正 |

この5本を、ほぼ1日で片付けています。
リフォームしかしていないのに、なぜこんなに手応えがあったのか。
たぶん「AI に単純作業を任せる」ことの意味を、私がこの日初めて実感したからだと思います。

これらの作業は、人間がやれば丸一日かかる退屈な仕事です。
ファイル名を直し、参照パスを直し、ビルドが壊れていないか確認する。
Claude Code にそれを任せると、数分で片付きました。しかも、「1プロダクト終わったら作業ログに書け」というルールを憲法に書いておいたおかげで、
5本分の作業ログが自動的に残りました。

ルールを書いておけば、作業のたびにルールの説明はいらない。
この経験が、後の「AIセルフガバナンス」という考え方へとつながっていきます。

## 2月25日午後 ― 最初の開発サイクルが回り始める

持ち込みリフォームが一段落した頃、本格的な開発も並走し始めました。
題材は mobile-order-system（モバイルオーダーシステム）の最初のスプリント（開発の1サイクル）です。流れはこうでした。

1. **Claude が設計**: `PLAN.md` を書いて、スコープを確定
2. **別の AI エージェントが実装**: React（画面の枠組み）と PocketBase（データの保存先）で機能を組む
3. **Claude がレビュー**: 3件のバグを発見・修正
   - テーブルの列ずれ
   - 列の順番の入れ違い
   - エラー処理の欠落
4. **別の AI が再デプロイ**: 本番環境への公開

この時点で、すでに「設計担当 AI」と「実装担当 AI」と「レビュー担当 AI」が分業していました。
1人の人間がすべての役割を持つ必要はない、というモデルが最初の数日で自然に出てきたことは、
後から振り返ると驚きです。

そしてこのスプリントの最後に、Claude は技術的負債（すぐは直さないが将来問題になる箇所）を見逃しませんでした。

> **技術的負債:** ngrok URL が設定ファイルにハードコード（直書き）されている。

この一行は作業ログにそのまま記録され、1週間後のスプリントで別の仕組みへの移行という形で回収されます。
見つけた問題を、その場で直さずにログに書き残す。この作法は、この時点で早くも身についていました。

## なぜ最初の数日が重要なのか

本章のエピソードはどれも地味です。
新機能もバグ修正も、派手な技術選定も出てきません。
それでも、この最初の3日間で決めたことが、その後の2か月間すべての運用ルールの原型になっていると思います。

- **先にルールを書いてから動く**（後のメタルール「Refactor-on-Write」の原型）
- **持ち込み資産は憲法に合わせて矯正する**（後の統一フォーマット制度の原型）
- **作業ログにすべての判断を残す**（後のセッション復帰フローの原型）
- **AI同士の引き継ぎは台帳経由のみ**（後のハンドオフ・プロトコルの原型）

最初の数日間は、Claude Code の機能を試す期間ではありませんでした。
Claude Code を使って何を作るかではなく、Claude Code をどう使うかを決める期間だったのだと思います。
この順番を守れたのは、たぶん偶然ではなく、プロローグに書いた「日を跨ぐと後戻りする」という失敗が先にあったからです。
