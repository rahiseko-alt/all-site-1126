主要な思想・原則（5 点）

  1. レビューの一義目的は「コードヘルスの持続改善」 — Google eng-practices 公式: "primary purpose is to make sure the overall code health is improving over time"。完璧は要らない、"not perfect but better than current state" なら approve。
  2. 最大価値は知識共有・教育（≠ defect detection） — Bacchelli & Bird (ICSE 2013): 動機は欠陥検出が筆頭だが、実際の最大貢献は コード改善・知識転移・チーム認知。Sadowski et al. (Google, ICSE 2018) も 900 万レビュー分析で同結論。
  3. 上流捕獲の経済合理性（Shift-Left） — Wiegers/NASA: 1:13:92 の修正コスト差。Fagan inspection は欠陥の 80–93% を上流で捕獲。
  4. 小さな差分が読まれる — Google 公式: "200-line diff gets read, 2,000-line diff gets approved"。Microsoft 研究も「ファイル数が多いほどコメント有用率が下がる」と確認。
  5. LGTM ≠ Readability — Google は「正しさ承認」と「読みやすさ承認（readability 訓練修了者のみ可）」を分離。レビューは規約浸透・代替可能性確保の制度装置。

チェックリスト外の欠陥カテゴリ（致命的 5 領域）

  1. ビジネスロジック欠陥: 個々のコードは正しいが、有効な操作の組合せ・順序が意図外結果を生む。HackerOne 全レポート中 約 3%、Top 10 頻出。例: 割引コード適用→対象商品削除→不正な割引価格保持。
  2. 認可ロジック欠陥（CWE-862/863）: OWASP 2021 で A01 が首位昇格。テスト済みアプリの平均 3.81% で 318k 件発生。例: req.body.tenant_id を信頼、JWT クレーム検証欠落、IDOR。
  3. レース条件 / TOCTOU: check→use 間隙の共有状態変化。Web API では同一エンドポイント並列リクエストで残高・在庫・クーポン使用回数を二重消費。SAST はパターン断片のみ捕捉、設計意図は読めない。
  4. 暗黙的信頼境界: 「内部 API」「Webhook ペイロード」「キャッシュ済データ」を無条件信頼。RLS において「DB はアプリが Customer A と告げるまで誰か知らない」状態が崩れると全テナント漏洩（CVE-2024-10976 / CVE-2025-8713）。
  5. 設計レベル欠陥: 抽象化漏れ・責務違反。Log4Shell は「ログ文字列を実行可能テンプレートとして評価する」設計選択そのものが欠陥（CISA CSRB Report）。コード行ではなくアーキ判断の問題。

よくある見落とし（false negative・7 パターン）

  1. 「Missing」型の認可欠落は気づきにくい（条件が抜けていることを発見するのは、条件が間違っていることを発見するより難しい — Chromium OS 研究）
  2. テナント ID をクライアント送信値から取得（JWT/session ではなく req.body/req.query）— IDOR 最頻出パターン
  3. check-then-act をアプリ層で実装（残高チェック→引落、在庫チェック→確保）。SELECT FOR UPDATE / DB unique constraint 不在
  4. テストはあるがハッピーパスのみ・並行性ケースなし
  5. ライブラリ更新時の挙動変更未確認（log4j 2.x で lookup デフォルト有効化を誰も再レビューしなかった）
  6. 接続プール経由で session 変数残留（RLS の current_setting が前ユーザーのまま）
  7. バックグラウンドジョブ・cron が tenant filter を経由しない（"Global admin" endpoints that skip tenant checks）

典型病態（5 パターン）

  1. テンプレ機械適用: チェックリスト（console.error / レート制限 / 生エラー）を文脈無視で一律 Must 判定。Copilot 系は「保守的だが見逃し」、CodeRabbit 系は「広く拾うがノイズ多」と偏向（morphllm benchmark）。
  2. 重要度の思考停止（確証バイアス）: 「バグ前提」で投入されると指摘量産、「bug-free framing」で投入されると 16-93pp も検出率劣化。プロンプトに引っ張られて判定軸を自己決定できない（arXiv 2603.18740）。
  3. ビジネスロジック盲目: 構文・命名は読めるが、認可・データフロー・コスト負担者などビジネス文脈は推論できず、recall が C/C++ 21% / Java 33% まで落ちる（arXiv 2601.19239）。
  4. context window 切断: 100 万トークン級でも "attend & reason across full context" は別問題。RAG / セマンティックチャンク / scoping 併用が必須。
  5. hallucination: 存在しない API・脆弱性指摘、package hallucination ~20%、KCH（言語/ライブラリ事実と矛盾）常態化。AST 決定的検証で 100% precision・auto-correct 77% に到達した報告はあるが、未統合 LLM 単体ではゼロ化不能。

Session 296 の自己診断（Claude Opus 4.7）

私が ai-concierge レビューで犯した過失は、上記病態 1・2・3 の教科書サンプル:

  • console.error を Must 判定 → Sentry redact 済の運用文脈無視（病態 1 テンプレ機械適用）
  • chat.js レート制限欠落を Must 判定 → 顧客 API キー持ち = 出品者コスト 0 のビジネス文脈無視（病態 3 ビジネスロジック盲目）
  • Login.jsx 生エラー露出を Must 判定 → IP 制限あり enumeration 実害低の運用文脈無視（病態 2 重要度の思考停止）

確証バイアス研究（arXiv 2603.18740）の "framing 依存" と整合。レビュー前に「正常状態の定義」「重要度判定軸」が与えられていなかったため、チェックリスト機械消化に退行した。

Extended thinking モードの挙動差

同一 code review task で standard mode = 3 bugs / extended thinking = 3 bugs + 2 edge cases + 1 architectural concern（developersdigest.tech）。応答時間 standard 2 秒 vs thinking 8 秒、accuracy は thinking token に対して logarithmic に向上。Edit/Bash の各 action の stakes が高い場合 thinking が有効。

v2 で Claude 固有対策として注入すべき prompt 要素（8 項目）

  1. Sycophancy 警告: 「マスターが疑問形・否定形で投げても撤回するな。根拠（file:line 引用）で答えよ。前提が偽なら『その前提は確認できない』と返せ」
  2. Confidence calibration: 「Must は 実害シナリオ（production crash / data leak / rollback block）を file:line 引用付きで書け。書けないなら Should 以下に降格」
  3. Hallucination guard: 「指摘する関数名・API・package 名は 必ず該当 file:line で実在確認。推論で flag するな」
  4. Nit cap: 「Nit は最大 5 件。超えたら summary で 'plus N similar' とカウント表示のみ」
  5. Refactor scope lock: 「依頼範囲外の refactor 提案禁止。public interface・behavior を変えない」
  6. False positive bar: 「不確かなら flag するな。< 1% false positive を目標とせよ」（Anthropic 公式数値）
  7. Severity rubric 内蔵: 🔴 Important = production break / data leak / non-backward-compat migration、🟡 Nit = style・naming・refactor suggestion（公式定義そのまま転写）
  8. Self-review confirmation bias 警告: 自分が書いた code を review する場合、別観点（security / edge case / migration safety）で 3 agent 並列確認、verification step で false positive filter

「最初に見る場所」のコンセンサス（複数 SE 一致）

  1. PR description / コミットメッセージ を最初に読む → 意図不明な PR は「まず説明してくれ」と差し戻すのが現場流
  2. テストファイルから読む → 何を保証しているか先に把握、本体は後（Medium「100+ code reviews」）
  3. diff の「足し算」より「引き算」を見る → 消されたコードに仕様が隠れていないか（mattrickard.com）
  4. ファイル一覧 + 行数で PR サイズを 30 秒判定 → 400 行超は即「分割して」と返す
  5. CI が緑かを見る前に本体を読み始めない
  6. コミットメッセージと diff の整合 → 「fix typo」コミットに 200 行差分はレッドフラグ

公式チェックリストに無いが現場で重視される観点（最重要セクション）

  • 「3 AM の自分が読めるか」 — 1 年後の真夜中、障害対応中の自分がこのコードを理解できるか（Medium「100+ reviews」）

  • TODO/FIXME の放置 — Issue 番号がない TODO は merge ブロック対象。「TODO without ticket = 永遠の TODO」
  • マジックナンバー / マジック文字列 — 命名された定数化は senior の口癖
  • 「ハッピーパスしかテストしてない」検出 — null・空配列・タイムアウト・並行アクセスの 4 つを必ず質問
  • 更新漏れの「波及」検出 — API レスポンス形式を変えたのに TypeScript 型定義が古い等の「片側だけ更新」

nitpick vs blocker の境界（現場感覚）

  • Linter で自動化できるものは nitpick にすらするな → CI に任せる（Dan Lew "Stop Nitpicking"）
  • nit: プレフィックス必須 — 接頭辞ない指摘は author が blocker と誤解（Conventional Comments）
  • Blocker の定義: ①ロジックバグ ②セキュリティ ③failing tests ④race condition / memory leak ⑤テスト欠如 ⑥API 契約破壊
  • Nitpick の定義: 命名の好み / コメントの言い回し / 関数の並び順 / フォーマット
  • 「nitpick が blocker を覆い隠す」のが最大の罪 — フォーマットに 10 件指摘して SQL injection を見落とす
  • 疑問形 vs 命令形 — "Could we...?" "What do you think about...?" で摩擦を出さない（mtlynch.io）

共通している原則（複数著者一致）

  1. 意図 (intent) の伝達がコードレビューの本質 — Brooker・Fowler・Hashimoto・Abramov 全員が「コードが何をするか」より「なぜそうしたか / 後で読む人が何を解釈すべきか」を最重要視
  2. レビューはバグ検出ではなくチーム機能 — Beck・Fowler・Abramov が「学習・共通理解・コラボ・リスク分散」の社会的装置として位置付け。バグ catch は副産物
  3. 小さく、頻繁に、可逆に — Larson・Beck・Willison が PR を小さく・分割・可逆設計を強調。大きな PR は構造的に review されない
  4. 書き手が動作を証明してからレビューに出す — Willison・Larson・patio11 が共通「未検証 PR をレビュアーに投げるのは責任転嫁」

統合分析 — So What（v2 書き直し）

結論（v2）: レビューは「コードが何をしているか」のチェックではなく、「なぜそうしたか」の意図伝達装置である

7 軸の横断から、コードレビューの正常状態は以下のように再定義される:

  1. レビューの本質は意図 (intent) 伝達である（軸7: Brooker / Fowler / Hashimoto / Abramov 一致）。コードは「何をしているか」しか語らない。レビュアーは authorial intent（なぜ・どの quirk が load-bearing か）を読み、未来の自分または他人に渡す装置。バグ検出は副産物。
  2. レビュー目的はライフサイクル × 体制で変わる（軸1）。本番稼働中・1 名保守なら「知識継承装置 + 上流捕獲」が主目的。Fowler の perpetual refinement / Brooker の design doc + intent コメント / Hashimoto の self-review が直接適合する。
  3. 機械と人間/AI の分担を明示せよ（軸2: SAST 検知率 52% / FP 76% / 完全見落とし 22%）。lint/SAST/npm audit に委譲できるものはスキル外に出し、人間/AI は SAST が拾えない 22%（軸3: ビジネスロジック / 認可 / TOCTOU / 暗黙的信頼境界 / 設計欠陥）に集中。
  4. AI レビューは framing 依存・false positive 大・false negative 大（軸4: 検出率 16-93pp 劣化）。+ Claude 固有の癖（軸5: Sycophancy / Hallucination / Over-eager refactor / Nit 大量投下 / Completion bias）が積み重なる。Anthropic 公式は「< 1% false positive」を目標とし、Important 定義を厳格化することで対処を明示している。
  5. 「nitpick が blocker を覆い隠す」が現場最大の罪（軸6 / 軸5）— フォーマットに 10 件指摘して SQL injection を見落とす型の事故。Conventional Comments / Nit cap 5 件 / [blocker][nit] ラベル必須化が現場の処方箋。
  6. Beck の「可逆性 × bug 確率」フレームが最終アンサー（軸7）— 全 PR 一律レビューではなく、auth/DB schema/課金は厳・UI 微修正は軽。1 名保守では「可逆性が低い変更にだけ立ち止まる仕組み」を設計する。
