## 1. モデル使い分けガイドライン（Opus 4.7 時代対応）

### 1-1. 前提（Opus 4.7 公式仕様）

- Opus 4.7 デフォルト effort は **`xhigh`**（全プラン・全プロバイダー共通。出典: Claude Code公式 Model Config）
- 新トークナイザーで前モデル比 **1.0〜1.35倍** のトークン消費増（ワークロード形状依存）
- `/model opusplan` コマンドで「Plan中Opus・実装中Sonnet自動切替」のハイブリッドモードが存在する（※採用方針は運用ルール側で規定する。下記 §1-2 原則参照）

### 1-2. モデル選定表（タスク複雑度 5段階）

| Level | タスク種別 | 推奨モデル | 推奨 effort |
|-------|-----------|-----------|------------|
| L1 | 機械作業（リネーム・フォーマット・単純置換） | Sonnet（Haiku導入見送り中） | low/medium |
| L2 | 日常タスク（明確なバグ修正・テスト追加・コピー修正） | Sonnet 4.6 | medium |
| L3 | 標準コーディング（複数ファイル・定型実装） | Sonnet 4.6 | high |
| L4 | 複雑な実装（曖昧仕様・統合作業・難所デバッグ） | Opus 4.7 | high |
| L5 | 設計・難問（アーキテクチャ・深デバッグ・思考の深さが必要） | Opus 4.7 | xhigh |

> **原則:** 手動運用ルールは `memory/feedback_opus-manual-operation.md` に従う（Sonnet + Plan Mode 基本、難所のみ手動 Opus 切替。`/model opusplan` 自動切替は不採用。Session 183 マスター確定判断）。

### 1-3. 判定プロトコル（タスク受領時）

1. マスター指示を L1-L5 に内部分類
2. 現在の `/model` 設定と照合
3. ズレ検出時は以下形式でマスターに提案:
   ```
   【モデル選定提案】
   タスク分類: L{N}
   現在: {現在の model/effort}
   推奨: {推奨 model/effort}
   根拠: {1-2行}
   切替指示: /model {名} または /effort {レベル}
   ```
4. 判断迷う場合は **Sonnet 4.6 + medium で開始**。作業中に L4-L5 相当の難所に遭遇したら、**作業を停止して**上位モデルへの切替を提案。

### 1-4. セッション中切替の注意

- セッション中の `/model` 切替は会話履歴全体を再処理するためトークン消費が増える
- 長い会話でモデル変更する場合は `/clear` または `/compact` 後に切替が推奨
- モデル切替頻度が1セッション3回超は `/clear` を検討せよ

### 1-5. 既存 PC表 model 列との対応

PC表の `model` 列（`Opus` / `中級` / `最低能` / `手動`）は以下と対応:

| PC表 model 列 | Level | 実モデル |
|--------------|-------|---------|
| Opus | L4-L5 | Opus 4.7 |
| 中級 | L2-L3 | Sonnet 4.6 |
| 最低能 | L1 | Sonnet 4.6 low/medium（Haiku 不採用） |
| 手動 | — | マスター手動実行 |

> **理由:** Sonnet で判断を伴う修正を行うと見落としが発生しやすく、手戻りでかえってトークンを浪費する。「正確に1回で終わらせる」方がトータルコストは低い。ただし Opus 4.7 は xhigh デフォルトでコストが大きいため、Sonnet + Plan Mode を基本とし、難所のみ手動で Opus に切り替える（`memory/feedback_opus-manual-operation.md` 準拠）。

## 4. パス解決ルール（クロスディレクトリ参照）

エージェント/Sonnet は `products/{product}/` で開かれる。MISSION_LOG の指示書でそのディレクトリ外のファイルを参照する場合、**絶対パスを使え。** 相対パス（`docs/foo.md`）はエージェントの作業ディレクトリ起点で解決されるため、vibe-base ルートのファイルは見つからない。

**正:** `C:\Users\user\Desktop\vibe-base\docs\pos-checkout-ui-research.md`
**誤:** `docs/pos-checkout-ui-research.md`（エージェント から見ると `products/aiueo/app/docs/pos-checkout-ui-research.md` を探す）

> **理由:** 2026-03-14 にUI刷新モック指示書で参照ドキュメントが見つからない事故が発生。エージェントは「存在しない」と判断し、競合UIを参照せずにモックを作成 → 品質不足で手戻り。

## 8. 調査委任（Research Delegation）v2.0

> **設計原則:** 方法論ガイド（調査指示テンプレート5セクション+ハルシネーション対策+ローリング抑制）をプロトコルに内包。低能モデルでもOpus同等の品質を構造で担保する。

### 8-0. 概要

**目的:** 調査タスクを低コストモデルのエージェントに委任し、Opusのトークンを判断・実装に集中させる。
**品質担保の手段:** 「嘘をつくな」ではなく、行動レベルの制約で品質を強制する。

| 問題 | 対策 | 実装箇所 |
|------|------|---------|
| ハルシネーション（嘘） | ソース併記強制+確信度自己申告+推測分離 | §8-4 信頼性ルール |
| 調査ローリング（無限検索） | ステップ上限+「足りなければ止まれ」 | §8-4 制約 |
| スコープ逸脱 | 除外対象の明示+触るなリスト | §8-4 スコープ |
| 品質のバラつき | 固定テンプレート+固定出力フォーマット | §8-4, §8-5 |
| 事後検証の漏れ | 5点検証+再依頼は不合格箇所のみ | §8-6 |

### 8-1. 命令体制

```
マスター
  │
  ├─ 指示（プロダクト名+調査種別を口頭で指定）
  │
  ▼
Opus（司令塔）
  │
  ├─ ① 調査指示書を作成（§8-4テンプレート準拠）
  ├─ ② MISSION_LOG に記載
  ├─ ③ エージェントの出力を受入検証（§8-6）
  ├─ ④ 不合格箇所のみ再依頼（最大2回。3回目は自力補完）
  └─ ⑤ 合格後、判断タスクに進む（戦略分析・リスク評価等）
  │
  ▼
エージェント（低コストモデル）
  │
  ├─ 調査指示書を受け取る
  ├─ §8-4 の制約に従って調査実行
  ├─ §8-5 のフォーマットでファイル保存
  └─ Check-out（§6準拠）
```

**鉄則:**
- エージェントは**事実収集のみ**。判断・評価・推薦は禁止
- エージェントが「おすすめ」「〜すべき」と書いたら不合格
- 判断はすべて Opus が行う

### 8-4. 調査指示書テンプレート（Opus → MISSION_LOG）

**全5セクション必須。** エージェントはこの指示書とシステム原則（§8-4a）のみに従って動く。

```markdown
## Research Task: [プロダクト名] [調査種別]

**モデル推奨:** 推奨: Flash Fast / 妥協: GPT-OSS Fast / 回避: Pro/Opus

> あなたは調査アシスタントです。以下の原則に従ってください：
> - 裏付けURLのない事実は回答に含めない
> - 推測は【推測】と明示する
> - 調査指示書のスコープ外の情報は報告しない
> - 指定ステップ数を超えたら、取得済み情報で回答を構成し、不足点を列挙する
> - 判断・推薦・評価は行わない。事実の収集のみ

### 1. 調査目的
（一文で。「何を判断するための調査か」を明記）
例：「AI Answer のココナラ出品にあたり、同カテゴリ上位5出品者の価格・機能・評価を把握する」

### 2. 調査スコープ
- **対象:** [企業名、サービス名、カテゴリ、地域、期間など]
- **除外:** [調べなくてよいもの。明示必須]
- **粒度:** [概要レベル / 詳細比較レベル]
- **PC表タスク:** [対応するPC表番号。例: P0 #4, #5]

### 3. 出力フォーマット
- **出力ファイル:** `products/{product}/tmp/ag-research-{type}.md`
- **フォーマット:** §8-5の[該当テンプレート名]に従うこと
- **出力ファイル以外の作成禁止**

### 4. 信頼性ルール
- 各事実に情報ソースのURLを併記すること
- **URL取得不可の場合は「出典未確認」と明記すること**
- **推測や補完を行った箇所は【推測】と明示すること**
- **裏付けURLのない事実は回答に含めないこと**（含めるな）
- 各項目に確信度（高／中／低）を付記すること
- 市場規模は中央値・最頻値で記載（平均値のみ禁止）
- 比較表のセルに具体値を記載（○×だけ禁止）
- 調査できなかった項目は「未実施: [理由]」と記載（空欄禁止・捏造禁止）

### 5. 制約
- **Web検索は最大N回以内**に収めること（Opusが調査規模に応じてN=5〜15で指定）
- **不足情報がある場合は追加調査せず、不足項目を一覧化して報告すること**
- 調査で判断・推薦を行わないこと（「〜すべき」「おすすめ」禁止。事実のみ）
- 仮説テーブルの判定（✅/❌）を付与しないこと（Opusが行う）
- PC表・CLAUDE.mdを変更しないこと

**参照SOP:**
- `C:\Users\user\Desktop\vibe-base\docs\ops\agent-task-protocol.md` §8
- [タスク固有のSOP絶対パス]

**前提情報:**
- ターゲット: [1文定義]
- 差別化: [1文定義]
- 仮説（検証すべきもの）: [S1#3から抜粋。なければ省略]
```

### 8-6. 受入検証（Opus側）

エージェントの出力を受け取った後、Opusは以下7点を検証する。全項目再調査は禁止。

| # | 検証項目 | 不合格時 |
|---|---------|---------|
| 1 | **フォーマット準拠:** §8-5の全セクション見出しが存在するか | 欠落セクションのみ再依頼 |
| 2 | **出典の存在:** 全データ項目に出典URLがあるか。**出典のない事実は受理しない** | 出典なし箇所のみ再依頼 |
| 3 | **確信度の記載:** 全データ項目に確信度（高/中/低）があるか | 欠落箇所のみ再依頼 |
| 4 | **推測の分離:** 【推測】タグが使われているか。「未確認・推定事項」セクションと整合するか | 矛盾箇所を指摘し修正再依頼 |
| 5 | **「未実施」の整合性:** 他セクションの空欄・出典欠落と「未実施項目」セクションの記載を突合。空欄があるのに「なし」は虚偽申告 | 矛盾箇所を指摘し修正再依頼 |
| 6 | **検索回数の記載:** 「Web検索回数: N/上限M」が記載されているか | 記載を追加させる |
| 7 | **判断の混入:** 「〜すべき」「おすすめ」「最適」等の判断表現がないか | 該当箇所を事実記述に修正させる |

**再依頼ルール:**
- 不合格箇所のみ再依頼。全やり直し禁止
- **再依頼は最大2回まで。** 3回目の不合格はOpusが自力補完し、MISSION_LOGに品質懸念を記録
- 合格後、Opusは判断タスク（#6, #10-13, #14-15等）に進む

### 8-7. 運用ルール

#### 段階的アプローチ（大規模調査）

1調査指示書で完結しない大規模調査は2段階に分ける。

| 段階 | エージェント行動 | Opus行動 |
|------|--------|---------|
| **第1段階** | 概要調査 + 不足項目の洗い出し | 出力を確認し、深掘り箇所を特定 |
| **第2段階** | 第1段階で特定された不足箇所のみ深掘り | 統合して判断タスクへ |

**判断基準:** Web検索上限10回以上が見込まれる調査は2段階に分割せよ。

#### PC表での調査タスク表記

PC表の調査委任タスクには以下の情報を含める。

| 列 | 値 | 例 |
|----|---|---|
| model | `Flash Fast` | エージェント委任であることが一目でわかる |
| status | `×`→エージェント作業中は`△`→Opus検証合格で`○` | 3段階遷移 |
| note | `エージェント委任: ag-research-{type}.md` | 出力ファイルへのポインタ |

#### 品質事故時の対応

| 事象 | 対応 |
|------|------|
| エージェントが出典なしの数値を大量に含む出力を提出 | 全却下。「出典のない事実は含めるな」を太字で再指示 |
| エージェントが判断・推薦を混入（「〜すべき」） | 該当箇所削除+事実記述への書き換えを再依頼 |
| エージェントが検索上限を超過して延々と調査 | セッションを停止。取得済み情報で出力を構成させる |
| 3回再依頼しても品質が出ない | モデルを1段階上げる（Flash→Pro）。それでもダメならOpus自力実施 |
| 同一調査種別で品質事故が2回連続 | 該当調査種別を委任不可に昇格。MISSION_LOGに記録 |
