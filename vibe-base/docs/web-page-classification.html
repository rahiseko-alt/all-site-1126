1. インターネットの階層

インターネット = 地球 ├── プロトコル = 物理法則（地球全体に適用） │ ├── HTTP/HTTPS → ウェブを実現 │ ├── SMTP → メールを実現 │ ├── FTP → ファイル転送を実現 │ └── WebSocket → リアルタイム通信を実現 │ └── サービス = 法則に基づいて成立した社会基盤 ├── ウェブ = 居住するために整えられたエリア（HTTP上に構築） │ ├── ウェブサイト = マンション │ │ └── ウェブページ = マンションの中の1部屋 │ └── URL = 住所 ├── メール = 郵便制度（SMTP上に構築） └── ファイル転送 = 物流網（FTP上に構築） ────────────────────────────────────────── ブラウザ = インターネット（主にウェブ）を見るためのメガネ Chrome、Safari、Edge、Firefox など ※ 本来はウェブを見るメガネ。現在はほぼ全サービスを吸収

未着手: DNS / SSH / P2P / VoIP / ストリーミング / TCP-IP物理層 / VPN / IoT

2. 客の動機 → 提供すべきWEBサービス

客がインターネットに来る理由は3つしかない。それぞれに対して用意すべきサービスが決まる。

#客の動機サービス種別具体例
1知りたい組織サイト（コーポレート）Toyota、Sony、中小企業HP、学校HP
ポートフォリオ / プロフィールDribbble作家ページ、GitHub Profile、名刺サイト
メディア / ニュース日経、TechCrunch、SmartNews、foodee
ブログ / 個人発信note、Zenn、はてなブログ、WordPress
マニュアル / ドキュメントMDN、Stripe Docs、Notion Help、行政FAQ
2「場」に行きたいコミュニティ / SNSX、Reddit、Discord、食べログ口コミ
マーケットプレイスメルカリ、Airbnb、ランサーズ、ココナラ
エンタメ / ゲームYouTube、Spotify、Netflix、ブラウザゲーム
3買いたいEC（物販）Amazon、楽天、Shopify店舗、BASE
デジタル販売Steam、App Store、Gumroad、Kindle
予約 / サービス購入ホットペッパー、一休、Booking.com
--- 以下、動機ではなく部品 ---
—機能（部品）チェックアウト、ダッシュボード、フォーム、アンケート、FAQ、ヘルプ、プライバシーポリシー、特商法 — サイト内に組み込まれる構成要素であり、単独の動機ではない
  • 1〜3は単体でも合体形態でも成立する（例: Amazon = 1+2+3、食べログ = 1+2+3）
  • LP（ランディングページ）は動機でもサービスでもなく「着地点」。1〜3のどれにでもなり得る形式

3. サイトを構成するページ種別

どのサービスを作るにしても、サイトは以下のページ種別の組み合わせで構成される。

入口ページ — 客が最初に見る

種別役割典型レイアウト例
トップページサイト全体の入口。ナビゲーションハブ。ブランド印象を決定ヒーロー+セクションapple.com、各社コーポレートトップ
LP（ランディング）1つのCTAに集中。スクロール完結。広告からの着地点シングルカラムSaaS登録LP、キャンペーンLP

コンテンツページ — 情報を届ける

種別役割典型レイアウト例
一覧（リスト/グリッド）同種アイテムの列挙。フィルター・ソート・ページンググリッド/カード商品一覧、記事一覧、検索結果
詳細（シングル）1アイテムの全情報。一覧からの遷移先シングルカラム or 2カラム商品詳細、記事本文、店舗ページ
比較 / 料金プラン・機能の比較表。意思決定を促すテーブルPricing Page、機能比較表

アクションページ — 客に行動させる

種別役割典型レイアウト例
フォーム / 入力データを受け取る。問い合わせ、登録、アンケートシングルカラムお問い合わせ、会員登録
認証（ログイン/登録）アクセス制御の入口中央寄せカードログイン画面、OAuth同意画面
チェックアウト / 決済購入フローの最終段階ウィザード/ステップカート確認、支払い入力

管理ページ — ログイン後の内部

種別役割典型レイアウト例
ダッシュボードデータの可視化・KPI監視グリッド（ウィジェット）GA4、Vercel Dashboard
設定 / プロフィールユーザー自身の情報・環境を編集シングルカラム or タブアカウント設定、通知設定

補助ページ — サイトの信頼性・安全性

種別役割典型レイアウト例
ヘルプ / FAQ疑問解消。検索+アコーディオン構成が多い2カラム（サイドナビ）Stripe Docs、よくある質問
法的ページプライバシーポリシー、特商法、利用規約シングルカラム（長文）各サービスの法的ページ
エラー / ステータス404、500、メンテナンス中、完了画面中央寄せメッセージGitHub 404、購入完了

4. 集客ファネル

サービスを作っても客が来なければ意味がない。客を連れてきて買わせるまでの流れ。

#ステップ内容使うもの
1誰に売るかターゲット定義。ペルソナ・課題・予算感ペルソナシート、インタビュー
2どこにいるかターゲットが集まっているチャネルを特定SNS、検索、業界メディア、口コミ
3どうやって知ってもらうか認知を取る手段。無料（SEO/SNS/口コミ）or 有料（広告）ブログ、X投稿、Google広告、紹介
4どんなLPにするか着地先の種類・形式を決定LP、サービスサイト、EC直結
5LPの中身をどうするかコピー、デザイン、動画、社会的証明、CTA配置ヒーローコピー、デモ動画、口コミ
6どう課金するか決済導線。カート→支払い→確認→完了Stripe、PayPal、銀行振込
7何を届けるか提供・オンボーディング。初回体験が継続を決めるウェルカムメール、セットアップ画面
  • 3→4は状況で組み合わせが変わる（SNS→LP、ブログ→EC直結 等）
  • 5→6は固定ペア。LPは常に課金直前の「最後の説得」
  • LP = Last Punch（トドメの一撃） — 一撃で決まるなら直接LP、決まらないならジャブ（ブログ、事例、SNS投稿）で温めてからLPで仕留める

5. レイアウトパターン

ページ種別ごとに最適なレイアウトが決まる。模写で覚えるべき「型」の一覧。

パターン構造使うページ種別
シングルカラム1列で上から下へ流れる。集中させたいときの基本形LP、記事詳細、フォーム、法的ページ
2カラム（サイド+メイン）サイドバーにナビや目次。メインにコンテンツドキュメント、ヘルプ、ブログ（PC）、管理画面
グリッド / カード同種アイテムの繰り返し。画像主体で一覧性が高い商品一覧、記事一覧、ポートフォリオ、ダッシュボード
テーブル（表）行×列の構造化データ。比較・管理向き料金比較、管理画面リスト、スプレッドシート
タイムライン / フィード時系列でアイテムが流れる。新しいものが上SNSフィード、チャット、更新履歴、通知
ヒーロー + セクション大きなビジュアル冒頭 → セクション繰り返しトップページ、LP、プロダクトサイト
マスター / ディテール左に一覧、右に選択したアイテムの詳細を表示メールクライアント、チャットUI、ファイル管理
ウィザード / ステップ段階的に入力を進める。進捗バー付き会員登録、チェックアウト、セットアップ
中央寄せカード画面中央に1つのカード。周囲は余白ログイン画面、エラーページ、完了画面

6. 技術選定

6-1. 画面の作り方（レンダリング方式）

方式仕組み向いている場面代表技術
静的サイト（SSG）ビルド時にHTML生成。CDN配信で高速ブログ、ドキュメント、LP、ポートフォリオAstro、Hugo、Next.js static
SSR（サーバー描画）リクエストごとにサーバーでHTML生成EC商品ページ、SEO重要なページNext.js SSR、Nuxt、Rails
SPA（クライアント描画）初回ロード後はJSがDOM操作。APIで通信ダッシュボード、管理画面、ログイン後React SPA、Vue SPA
MPA（従来型）ページ遷移ごとにサーバーからHTML取得行政サイト、WordPress、シンプルなサイトWordPress、PHP、静的HTML
ハイブリッドページ単位でSSG/SSR/SPAを選択大規模サイト（トップはSSG、管理画面はSPA）Next.js App Router、Remix
エッジレンダリングCDNエッジで動的処理。低レイテンシパーソナライズ、A/Bテスト、地域別表示Cloudflare Workers、Vercel Edge

6-2. アプリケーションの分類

アプリケーション ├── Webアプリ（ブラウザ上で動作。インストール不要） │ └── Notion、Gmail、GA4、foodee ├── ネイティブアプリ（端末にインストール） │ ├── モバイルアプリ（iOS / Android） │ └── デスクトップアプリ（Windows / Mac） ├── PWA（Webアプリだがインストールも可能） │ └── X、Starbucks └── ハイブリッドアプリ（Web技術でネイティブの殻をかぶせたもの） └── Slack(デスクトップ版)、VS Code
  • 動作場所 — ローカル / ブラウザ（どこで動くか）
  • 売り方 — SaaS（月額課金）/ パッケージ（買い切り）

7. 収益モデル

サービスの種類によって取れる収益モデルが決まる。逆に、収益モデルからサービス設計を逆算することもできる。

モデル仕組み主要KPI典型サービス
広告収入トラフィック × 広告単価。大量PVが必要PV、CTR、CPMニュースメディア、ブログ、YouTube
サブスクリプション月額/年額の定額課金。継続率が命MRR、Churn率Netflix、Notion、日経電子版
フリーミアム基本無料+上位機能で課金。無料→有料の転換率が勝負CVR、ARPUSpotify、Canva、Slack
EC（物販）商品販売。仕入れ→販売の差額が利益AOV、LTV、在庫回転Amazon、楽天、Shopify店舗
リード獲得見込み客情報を取得→営業チームに渡すCPA、リード数、商談化率BtoB LP、資料請求、無料相談
SaaS利用料機能利用に対する従量 or 定額課金MRR、NRR、CACAWS、Stripe、freee
マッチング手数料成約ごとに片方 or 両方から徴収GMV、テイクレートAirbnb、メルカリ、ランサーズ
寄付 / 公共予算非営利・行政。収益は目的でない—Wikipedia、省庁サイト、NPO
