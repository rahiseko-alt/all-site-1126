# 共有資産化SOP v1.0

> **適用範囲: vibe-base司令塔のみ。** プロダクト側エージェントは本SOPの対象外。
> 本ファイルはルート CLAUDE.md の SOP索引から参照される運用手順書である。

---

## 目的

プロダクト内に閉じている有用な手法・知見・判断基準を発掘し、全エージェントが参照できる共有資産に昇格させる。散財（分散・埋没した成果物）を防ぎ、再発明を防止する。

---

## トリガー

以下のいずれかに該当するとき、本SOPを実行する。

1. **セッション中に発見:** プロダクト作業中、他プロダクトにも適用できる手法に気づいた
2. **Check-in時に発見:** memory.mdを読む過程で、プロダクト固有に閉じた汎用知見を見つけた
3. **マスター指示:** 「共有化しろ」「全体に適用しろ」等の指示があった
4. **パトロール時:** 定期巡回でtmpに放置された成果物や未昇格の知見を発見した

---

## 手順

### Step 1: 発掘

走査対象:
- `products/*/memory.md`（各プロダクトのセッション記録）
- `products/*/CLAUDE.md`（自治憲法に独自ルールとして書かれた汎用知見）
- `tmp/`（下書き・断片ファイル）
- `SESSION_JOURNAL.md`（セッション単位の教訓）

### Step 2: 判定

以下の**いずれかに該当**すれば共有資産候補:

| 基準 | 例 |
|------|----|
| 2つ以上のプロダクトで使える | CSS計測表提出制、APIコスト監査手法 |
| マスターが全体方針として言及済み | A番号あり（例: A267「WEBページ全般に適用」） |
| 失敗から得た教訓で再発防止が必要 | 二重構成事故、課金見落とし |
| 法的判断を含み統一基準が必要 | RSS配信権、著作権、特商法 |

**該当しないもの:** プロダクト固有の実装詳細、一時的なデバッグ記録、git logで追えるもの

### Step 3: 抽出

1. プロダクト固有の実装詳細（ファイルパス、API名、変数名等）を剥がす
2. 汎用フレームワーク部分だけ取り出す
3. 元のプロダクト文脈を「出典」として記録する（例: `出典: foodee Session 62-63`）

### Step 4: 配置

| 性質 | 配置先 | 形式 |
|------|--------|------|
| 手順・ルール | `docs/ops/` に新規SOP or 既存SOPに統合 | Markdown |
| 知識体系・分類・参照資料 | `docs/` | HTML or Markdown |
| 判断基準・チェックリスト | `docs/ops/` 内の該当SOPに追記 | Markdown |

- **既存SOPに統合できるなら統合が先。** 新規ファイルは最終手段（§1 Refactor-on-Write）
- **元プロダクトからは参照パスだけ残す**（§1 Reference-over-Redundancy）

### Step 5: 索引更新

1. `CLAUDE.md` §3 SOP索引 — 新規SOPの場合のみ追加
2. `docs/ops/product-cycle.md` フェーズ別テンプレート索引 — テンプレートが特定タスクで使われる場合、該当フェーズの索引に追加
3. `docs/md-inventory.md` — エントリ追加
4. `memory/MEMORY.md` — 必要なら参照先を追加

### Step 6: 片付け

- 統合済みのtmpファイルを削除
- プロダクト自治憲法内の重複記述を参照パスに置換

### Step 7: 通電テスト

共有資産は全エージェントに影響するため、コミット前に必ず実施:
- 整合性検証（パス・クロスリファレンス・バージョン）
- 運用シミュレーション（担当AIになりきり手順実行）
- マスター承認後にコミット

---

## やってはいけないこと

- **プロダクトの自治を侵害しない。** プロダクト固有の判断・実装をdocs/ops/に持ち出さない
- **二重書き込みしない。** 正本は1箇所。プロダクト側にコピーを残さない
- **勝手に共有化しない。** マスター承認なしにコミットしない
