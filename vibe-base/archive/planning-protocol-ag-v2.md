# 計画立案・作業指示書 作成プロトコル v2.0

> **目的**: このプロトコルに従えば、どのモデルでも「高解像度の計画」と「コピペで実行可能な指示書」を作成できる。
> v1.0からの変更: 「何を考えるか」に加え「どう考え、どう判断するか」の基準を追加。

---

## フェーズ0: 前提確認

以下を実行してから計画に入る。

- [ ] プロジェクトの憲法・ルールファイルを読んだか
- [ ] 引き継ぎログで前回の未解決事項を把握したか
- [ ] ユーザーの要望を「**何が変わるか**」で1文に言い換えられるか

> [!CAUTION]
> 1つでも「いいえ」なら、計画に進むな。まずそこを埋めろ。

---

## フェーズ1: 要件の解像度を上げる

### 1-1. 要望の分解

ユーザーの発言を以下の3軸に分解する。**3つ全て埋まるまで計画に進まない。**

| 軸 | 問い | 埋まらない場合 |
|-----|------|--------------|
| **What** | 完成後、画面やデータに何が起きているか？ | ユーザーに聞く |
| **Why** | なぜそれが必要か？今何が困っているか？ | ユーザーに聞く |
| **Scope** | 何は**やらないのか**？ | 自分で仮定を立て、計画書に明記してユーザーに確認させる |

### 1-2. 変更対象の特定

**記憶でコードを書くな。必ず実ファイルを読め。**

1. 変更対象の関数・HTML・CSSを開き、**行番号を正確にメモ**する
2. その関数/要素の**呼び出し元・参照元**を検索で全て洗い出す
3. メモすべき情報: **関数名、引数、行番号範囲、呼び出し箇所の行番号**

### 1-3. 影響範囲の洗い出し

変更対象ごとに以下の5問を自問する。**1つでもYesなら、その箇所も変更対象に加える。**

1. この関数の**引数を変えたら**、呼び出し元は壊れるか？ → Yes: 呼び出し元も変更対象
2. このHTML要素を変えたら、**CSSの見た目**は壊れるか？ → Yes: CSSも変更対象
3. このHTML要素を変えたら、**JSのイベントハンドラ**は壊れるか？ → Yes: JSも変更対象
4. この変更で**データ構造**（DB、API、ストレージ）は影響を受けるか？ → Yes: 保存/読出ロジックも変更対象
5. この変更は**他の画面やページ**にも波及するか？ → Yes: 波及先も変更対象

## フェーズ2: 計画書の作成

### 構造テンプレート

```markdown
# [ゴールを1文で]

## 概要
[What + Why を2〜3文]

## 現状
[今のコードがどうなっているか。行番号付き]

## 修正方針
対象ファイル: `[パス]`
変更箇所: **N箇所**

### 変更1: [何をするか]（L[行番号]付近）
[1〜2文で概要]

### 変更2: ...

## 設計判断（ユーザー確認事項）
> [!IMPORTANT]
> [自分が暗黙に決めた判断があれば、ここに書いて確認を仰ぐ]

## 検証手順
[デプロイ後に何を見て何が正解か]
```

### 品質判定ルール

計画書を書き終えたら、以下を順に判定する。**NGなら修正してから提出。**

| # | 判定 | NGの場合 |
|---|------|---------|
| 1 | ユーザーがこれだけ読んで「何が起きるか」分かるか？ | 概要を書き直せ |
| 2 | 変更箇所の数は明示されているか？ | 数えて冒頭に書け |
| 3 | 各変更に行番号があるか？ | ファイルを読み直して特定しろ |
| 4 | 自分が勝手に決めた判断はないか？ | 「設計判断」セクションに移動させろ |
| 5 | 検証手順は「何を見て何が正解か」まで書いているか？ | 具体化しろ |

## フェーズ3: 実行指示書の作成

### 3つの絶対原則

1. **beforeは現在のコードと完全一致させる** — ファイルを開いて `Ctrl+F` で見つかる粒度
2. **afterはそのままコピペで動く完成品にする** — インデント・改行・セミコロンまで正確に
3. **曖昧語を使わない** — 「適切に」「必要に応じて」「〜のあたり」は全て禁止

### beforeの切り出しルール

| 状況 | 切り出し範囲 |
|------|------------|
| 1行だけ変える | その1行のみ（ただし前後の文脈で一意に特定できること） |
| 複数行を変える | 変更開始行〜変更終了行を含む最小のブロック |
| 同じ文字列が複数箇所にある | 行番号を明示し、前後の文脈行を含めて一意にする |
| 関数全体を変える | 関数定義の開始行（`function ...`）〜閉じ `}` まで |
| **原則** | **beforeは短ければ短いほど良い。ただし一意性を担保できる最小単位** |

### 指示書の構造テンプレート

```markdown
# [タイトル] — 実行手順書

対象ファイル: `[パス]`
変更箇所: **N箇所**

---

## 手順N: [何をするか]（L[開始]〜L[終了]）

[なぜこの変更が必要かを1文で]

**before（L[開始]〜L[終了]）:**
```[言語]
[現在のコード]
```

**after:**
```[言語]
[差し替え後のコード]
```

---

## 最終手順: デプロイと検証
[コマンドと確認項目]
```

### 品質判定ルール

| # | 判定 | NGの場合 |
|---|------|---------|
| 1 | 変更箇所の総数が冒頭にあるか？ | 数えて書け |
| 2 | 全手順にbefore/afterの**両方**があるか？ | 抜けを埋めろ |
| 3 | beforeはファイル内で**完全一致**で見つかるか？ | ファイルを再度開いてコピペし直せ |
| 4 | afterは**構文エラーなく**そのまま動くか？ | 括弧・クォート・セミコロンを目視確認しろ |
| 5 | 「適切に」「必要に応じて」が**一切ない**か？ | 具体的な値・行番号に書き換えろ |
| 6 | 手順1の変更で行数が増減する場合、手順2以降への影響を注記したか？ | 注記を追加しろ |

## フェーズ4: セルフレビュー

提出前に、**自分を「コードの文脈を一切理解していないコピペマシン」と仮定**して指示書を読み返す。

### 3つの検証質問

1. **この指示書だけで、判断なしに変更を完了できるか？**
   → 「ここは状況に応じて…」が1箇所でもあったら不合格。具体化しろ。

2. **beforeのコードは本当に今のファイルに存在するか？**
   → 記憶で書いた可能性が1%でもあれば、ファイルを開いて再確認しろ。

3. **手順間で矛盾はないか？**
   → 手順Aで追加した引数を手順Bで使っているか？型は合っているか？

## アンチパターン早見表

| ❌ これをやったら失敗する | ✅ 代わりにこうする |
|---|---|
| 記憶でbeforeを書く | ファイルを開いてコピペする |
| 「L100付近を修正」 | 「L100〜L115を以下に置換」 |
| 「CSSを適切に追加」 | 「L299の `}` の直後に以下を挿入」 |
| 1手順で3箇所変更 | 1手順1箇所に分ける |
| 変更理由を省略 | 各手順に「なぜ」を1文で書く |
| 暗黙の設計判断 | 計画書の「設計判断」セクションに書いて確認を仰ぐ |
