---
description: plan ファイルの固定見出し構造の雛形を生成する。Plan Mode 中に実行し、出力をベースに plan を埋める。
---

以下の固定見出し構造で plan ファイルの雛形を出力してください。各セクションのプレースホルダは具体的な内容で埋めず、フォーマットだけを示してください。実際の plan 作成は、この雛形をベースにユーザー（マスター）と対話しながら埋めていきます。

```markdown
# Plan: $ARGUMENTS

## ⚠ 危険項目（毎回マスター警告・解除までマスター確認必須）

[本 plan の実走中に毎回マスターへ警告すべき危険項目。⚠ がある間は plan 提示・進捗報告のたびにマスターへ明示し、マスターが解除を確認するまで先のフェーズに進まない。危険項目がなければ `なし` と記載]

| ⚠ 項目 | 未解決リスク | 解除条件 |
|--------|-------------|---------|
| [項目] | [具体リスク] | [マスター確認事項] |

## Context
[任意。背景・関連 Issue・関連 PR 等]

## 大義との整合

[本 plan がどの大義を満たすか。`照合先:` は roadmap-state.json に実在するマイルストーン id（整数）。ロードマップを持たない H1 継続型の作業は `N/A`。`整合:` はその大義をどう満たすかを一文。**plan-daigi-gate hook が `照合先:` の id 実在を機械検査し、満たさない plan は ExitPlanMode で deny される。** docs/standards/plan-mode.md §大義との整合 参照]

- 照合先: [整数 id または N/A]
- 整合: [その大義をどう満たすかを一文]

## 上位 plan からの constraint 変更

[上位 plan (参照元 plan / memory.md P1 持ち越し項目 / 関連 plan セクション) から本 plan で scope / constraint / 完遂基準を変更した場合、その差分を表形式で明示する。新規 plan で上位なしの場合は `N/A` と記載してもよい。docs/standards/plan-mode.md §plan の固定見出し構造 §上位 plan からの constraint 変更 参照]

| 項目 | 上位 plan の扱い | 本 plan での扱い |
|------|------------------|------------------|
| [項目名] | [格下げ/scope 外/持ち越し等] | [格上げ/削除/範囲外/新規 scope 等] |

## 影響範囲
- 新規作成:
  - [path]
- 修正:
  - [path]
- 削除:
  - [path]

Glob 照合結果:
- [path: 0 件 / 既存 / 要確認]

## サブエージェント割り振り方針

[各 Step をどの agent にどのモデル（haiku / sonnet / opus）で割り当てるかの基準と、subagent へ実体ファイルを `@パス` で注入する原則。docs/standards/plan-mode.md §サブエージェント割り振り方針 参照]

| 区分 | モデル | 根拠 |
|------|--------|------|
| [Step 群] | [haiku / sonnet / opus] | [既定からの上書き根拠 / 既定どおり] |
| @注入 | [注入する実体ファイル path / 不要] | [subagent はコンテキスト非継承のため必要ファイルを明示注入] |

## 実装ステップ

| Step | 内容 | 担当 agent | モデル | @注入ファイル | 検証 |
|------|------|-----------|--------|--------------|------|
| 0 | 着手前 Glob 照合 | orchestrator | opus | — | test -f で全 path 確認 |
| 1 | [内容] | implement-agent | sonnet | @[参照ファイル path] | Step N で検証 |
| 2 | [内容] | implement-agent | sonnet | @[参照ファイル path] | Step N で検証 |
| N-1 | テスト実行・受け入れ基準照合 | verify-agent | haiku | @[plan path] | Glob 結果 / EXIT 0 |
| N | 最終 Glob 照合 | orchestrator | opus | — | 全 path 存在確認 |

## リスク・トラブル想定とリカバリープラン

[表形式（想定トラブル / 検知 / リカバリー）。リカバリーは .claude/rules/orchestration-discipline.md 規律 2「4 原則」を起草時に先回りで紐付ける。docs/standards/plan-mode.md §リスク・トラブル想定とリカバリープランの書き方 参照]

| 想定トラブル | 検知 | リカバリー（4 原則のどれか） |
|--------------|------|------------------------------|
| [トラブル内容] | [検知コマンドまたは観測点] | [原則 N: 対応手順] |

## テスト方針

1. [検証手段] → 受け入れ基準 N と対応
2. [検証手段] → 受け入れ基準 N と対応

## 受け入れ基準

### 意図（EARS 形式）
- WHEN [trigger] THE SYSTEM SHALL [response]

### 機械検証可能条件
- [ ] Glob: [path pattern] → N 件存在
- [ ] [コマンド] → EXIT 0
- [ ] git diff --stat → 影響範囲セクション記載と一致

## 承認後モード
[acceptEdits / default のいずれか]（理由: [判定軸に基づく根拠]）
```

雛形出力後、ユーザーに以下を確認してください:
1. 影響範囲の path 候補
2. 実装ステップの分割粒度
3. 受け入れ基準の EARS 意図文の方向性
