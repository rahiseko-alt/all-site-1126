受託開発の保守範囲・検収・漏洩責任 出典付き調査

再利用用途: 受託/保守契約の線引き条文設計・検収/受け入れ基準の合意フロー・UX改善の課金設計・個人情報/DB漏洩の責任分界説明
エグゼクティブ・サマリー（4論点の結論）
  • ① 保守範囲：バグが法的に「契約不適合（瑕疵）」になるのは「仕様不一致 かつ 稼働に重大な支障 かつ 迅速に補修できない」場合のみ（東京地判平9.2.18）。実務はIPAモデル契約に倣い「開発段階の契約不適合責任」と「検収後の保守契約」を分離し、保守はバグ修正=限定列挙／改善・追加=除外列挙で書く。
  • ② 検収・線引き：非技術な顧客が判定できる鍵は「プロトタイプ先行合意 → 顧客の言葉の受け入れ基準(AC) → UAT(受入テスト) → 検収」。ACはGiven-When-Then＝業務シナリオで書き、技術仕様や数字では書かない。「感じが悪い」を不合格理由にしないため定量/シナリオ基準を着手前に合意。
  • ③ UX改善の課金：使い心地調整はバグでも新機能でもない第3類型。大多数は「都度見積（タイムチャージ/個別見積）」で対応＝着手前に金額を提示し顧客承認。月額リテイナー(伴走)は sonicgarden 等の少数派モデルで受託の大多数はやらない。実勢は時給3,000〜10,000円、伴走を持つ場合は月5〜30万円。際限ない要望は「タダではやらない＝都度見積」で止まり、伴走がある場合のみ「月◯時間の工数上限」で制御。
  • ④ 漏洩責任：「DB内部が漏れたらDBベンダー責任」はほぼ成立しない。責任共有モデルで設定・アクセス制御・暗号化は利用者(開発側)責任、ベンダーSLAは損害をほぼ全額免責（上限=直近12ヶ月の利用料）。個人情報保護法では委託しても委託元の安全管理・監督義務(法25条)は残る。実事例(Capital One/WelcomeHR)もアプリ側設定ミスでベンダー免責。
So What（カルテアプリ等の小規模受託への落とし込み）
  • 線引きは「読めない仕様書」でなく「着手前デモ＋顧客の言葉のAC」で引く。例：「対象を選ぶ→記録画面が開く→書いて保存→後で見ると残っている」が目視でできれば完成（=バグなし）。非技術な顧客自身が判定できる。
  • 3区分を契約に明記：バグ修正（保守）／UX改善（別軸）／新機能（別途見積）。標準は都度見積（着手前に金額提示→承認）。月額の伴走契約を持つ場合のみ「月◯時間まで」の工数上限で吸収する（伴走は少数派モデル）。
  • 漏洩責任は「ベンダーに丸投げ」と書かない。基盤起因=ベンダー／実装の穴=開発側／運用(PW・端末)=店舗、の3分界を契約に書く。顧客の個人情報をDB保存する以上、無認証方針は撤回が前提。
  • 検収条項に「みなし検収」を入れるなら受け入れ基準とセット。基準なき「沈黙＝合格」は最大の紛争源。

論点① 保守範囲 — バグ修正と改善要望の線引き

結論

  • バグ＝裁判所基準は「仕様不一致＋稼働に軽微でない支障＋遅滞なく補修できない」。速やかに補修・代替すれば瑕疵(契約不適合)と認定されない（東京地判平9.2.18）[S7][S12]。
  • 2020年民法改正で「引渡から1年」→「不適合を知った時から1年以内通知」に変更。発見が数年後でも追及可となり、保守契約で開発段階責任を切り分ける条文が必須に[S4][S6]。
  • IPAモデル契約は「開発=契約不適合責任／検収後=保守契約」の二段構造。これが「バグ修正(無償期間内)→改善・追加(別途有償)」慣行の法的土台[S1][S2]。
  • 保守契約は含む業務(エラーパッチ・回避策提供)を限定列挙＋含まない業務(機能改善・拡張・第三者製品更新対応)を除外列挙するのが標準[S8][S9][S11]。
  • 非機能要件(速度等)が未定義なら、遅さはバグに当たらない（東京高判令6.1.31）[S14]。

紛争の典型と予防

  • 典型：仕様書に無い挙動の是正要求／「動くが業務に合わない」をバグと主張／非機能要件未定義の速度問題[S5][S13][S14]。
  • 予防：要件・設計の文書化と双方署名／変更管理手続きの契約明記／不具合報告と改善要望の受付経路を分ける[S13][S15]。

論点② 検収・受け入れ基準 — 顧客が判定できる線引き

結論

  • 受け入れ基準(AC)はユーザーストーリーごとの合格条件。技術仕様でなくユーザー視点で書く。Definition of Done(DoD)とは別物[S2][S3][S4]。
  • 記述形式はGiven-When-Then(Gherkin)が普及。前提・操作・期待結果の3要素で非技術者も読める[S1][S5]。
  • UATは発注者/エンドユーザーが本番近似で行う最終確認。合格基準の事前合意が最大の成功要因。「感じが悪い」を不合格にしないため定量/シナリオ基準を契約前に合意[S8][S9][S10]。
  • 仕様書は非技術顧客に伝わらない→プロトタイプ・デモ先行で「見て触って合意」。デジタル庁の調達でもプロトタイプ検証が標準[S13][S16]。
  • 請負では検収＝完成確認かつ報酬請求権の起点。検収後も契約不適合責任は残る。「みなし検収」は受け入れ基準の明文化とセットで使う[S19][S24][S25]。

論点③ UX改善・継続改善の課金モデルと相場

結論

  • 使い心地調整はバグでも新機能でもない第3類型。標準は都度見積（タイムチャージ/個別見積）＝改善要望ごとに着手前に金額を提示し顧客承認を得る。月額リテイナー(伴走)は継続関係前提の少数派モデル(sonicgarden/mofmof等)で、受託の大多数は採らない[S-b1][S-b8]。
  • 「際限ない要望」の根本対処は、都度見積なら「着手前に金額提示→承認」（タダではやらないので止まる）。伴走契約がある場合のみ月◯時間の工数上限で制御する[S-b8][S-b11]。
  • バグ修正(請負)／UX改善(準委任・月額工数)／新機能(別途請負)の3区分を契約に明示するのがトラブル防止の最善[S-b8]。

論点④ 漏洩時の責任分界（責任共有モデル・SLA免責・個人情報保護法）

結論

  • 「DB内部が漏れたらDBベンダー責任」はほぼ成立しない。AWS/Google/Supabase/Cloudflare とも、データ内容・アクセス制御・暗号化設定は利用者(開発側)責任と明文化[L1][L2][L3][L4]。
  • ベンダーSLAはデータ漏洩損害をほぼ全額免責。賠償上限=直近12ヶ月の利用料[L5][L6]。
  • 個人情報保護法：委託しても委託元の安全管理措置(法23条)・委託先監督義務(法25条)は残る。委託先で漏洩しても委託元が処分対象[L7][L8][L9]。
  • クラウド事業者が個人データを「取り扱わない」場合でも、漏洩報告義務者は利用事業者(法26条)[L10][L11]。
  • 実事例：Capital One($190M+$80M, AWS免責)・WelcomeHR(アクセス権限誤設定で運営会社責任)。いずれもアプリ側起因[L12][L13]。
