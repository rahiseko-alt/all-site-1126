# 障害対応SOP — 本番障害対応プロトコル

> **対象:** 全プロダクト（「運用Runbook整備」時に参照必須）
> **起源:** catnose#5「障害分析と公表」+ Qiita#20「停止・記録・告知」を統合
> **関連SOP:** `failure-scenario-template.md`（事前分析）/ `mission-log-ops.md`（開発進捗記録）

---

## §0. 自動注入

このSOPの要点は `.claude/rules/incident.md` で `products/*/runbook.md` 編集時に自動注入される。各プロダクトは `runbook.md` を作成し、本SOPの§7テンプレに従って初期化すること（「運用Runbook整備」完了条件）。

---

## §1. 検知

### アラート種別と発火源
| 種別 | 発火源 | 重大度初期判定 |
|------|--------|--------------|
| **致命: サービス全停止** | UptimeRobot 5xx連続3回 / ユーザー通報 / Vercel Status RED | P0（即時対応） |
| **重大: 機能局所停止** | Sentry エラー率 >5% / Stripe Webhook 失敗連続 / DB接続エラー | P1（30分以内） |
| **軽微: パフォーマンス劣化** | Vercel Analytics LCP >4s / API応答 >5s | P2（営業時間内） |

### エスカレーション基準
- **P0:** マスター即時通知（電話 + メール + ダッシュボード掲示）
- **P1:** 30分以内にマスター通知（メール + Slackなど）
- **P2:** 翌営業日朝の定期報告に含める

### 実施タイミング
- 監視ツール（UptimeRobot / Sentry等）導入はインフラ決定で確定
- アラートチャンネル設定は「運用Runbook整備」完了条件
- 検知漏れ発生時は本SOP §5「再発防止」に基づく再設計

## §2. 即時対応

### 停止判断フロー
```
① 影響範囲を特定（全ユーザー / 特定機能 / 特定リージョン）
   ↓
② 課金処理・決済が走っているか確認（はい→即停止優先 / いいえ→次へ）
   ↓
③ ロールバック可能か確認
   - 直前デプロイが原因 → Vercel rollback（30秒で復旧）
   - DB変更が原因 → migration rollback or 手動修正
   - 外部API障害が原因 → サーキットブレーカー発動 or 機能停止
   ↓
④ ロールバック実行 or maintenance modeへ
```

### 影響範囲特定の調査3点
1. **エラーログ:** Sentry / Vercel logs で発生時刻・エンドポイント・ユーザーID特定
2. **DB状態:** 不整合データ（中途半端な決済記録等）の有無を SELECT で確認
3. **外部依存:** Stripe / OpenAI / Twilio 等の status page を全て確認

### 実施タイミング
- P0障害: 検知から **15分以内**に①〜③完了、**30分以内**にロールバック or maintenance mode

---

## §3. ユーザー告知

### 告知チャネル
1. **status page**（推奨: Statuspage.io 無料枠 / Vercel Statusのプロジェクト連動 / 自前 `/status` ページ）
2. **メール**（影響ユーザーリスト宛て、P0のみ即時送信）
3. **SNS**（X等の公式アカウント、必要時のみ）

### 告知テンプレート（P0障害発生時 第1報）
```
件名: 【障害発生】{プロダクト名} のサービス停止について

平素より{プロダクト名}をご利用いただきありがとうございます。
{YYYY-MM-DD HH:MM}頃より、以下の障害が発生しております。

■ 発生事象
{1〜2文で障害現象を記述}

■ 影響範囲
{影響を受けるユーザー / 機能 / 期間}

■ 現在の対応状況
{復旧作業中 / 原因調査中 / 暫定対応済み 等}

■ 復旧見込み
{確定: HH:MMまで復旧予定 / 未定: 続報を本ページで随時更新}

ご迷惑をおかけし誠に申し訳ございません。
{プロダクト名} 運営: 小齊平 恒平
```

### 告知タイミング
- 第1報: 検知から **30分以内**（情報未確定でも「現在調査中」で出す）
- 第2報以降: 状況変化時、または1時間ごとに必ず更新
- 復旧報: 復旧確認後 **1時間以内**

### 実施タイミング
- 第1報テンプレートは「運用Runbook整備」完了条件として `runbook.md` に予め記載
- 復旧前にテンプレ準備を始めるのは時間ロス

## §4. 原因究明

### タイムライン作成
復旧後 24時間以内に以下を埋める:
| 時刻 | 事象 | 検知者 | 対応者 |
|------|------|--------|--------|
| HH:MM | 障害発生（ユーザー影響開始） | — | — |
| HH:MM | 検知（アラート発火） | UptimeRobot | — |
| HH:MM | エスカレーション | システム | マスター |
| HH:MM | 一次対応開始 | — | 担当AI |
| HH:MM | 復旧 | — | 担当AI |

### 5whys（根本原因究明）
障害現象から「なぜ?」を5回繰り返し、コード/プロセス/設計のいずれに根本原因があるか特定。
- 例: ユーザー決済失敗 → なぜ? Stripe API 500 → なぜ? Stripe側障害 → なぜ? 自前のリトライロジックなし → なぜ? セキュリティレビューで見落とし → なぜ? rate-limit-sop と連携してなかった

### 実施タイミング
- 復旧から **24時間以内**にタイムライン + 5whys 完成
- マスター報告は復旧確認直後（速報）+ 24時間以内に詳細

## §5. 再発防止

### コードレベル
- 該当バグ修正 + 単体テスト追加
- 横断チェック: 同パターンのバグが他箇所にないか grep で全件検索（共通憲法 §4「横断チェック」）
- リグレッションテスト追加

### プロセスレベル
- SOP更新（本SOP / `failure-scenario-template.md` / `agent-rules.md` 等）
- アラート閾値見直し（誤検知 or 検知漏れがあった場合）
- runbook 改訂（手順が不明瞭だった場合）

### dead-end-registry への記録
- 同種障害を他プロダクトでも防ぐため、`docs/ops/dead-end-registry.md` に追加
- 記録項目: 障害現象 / 根本原因 / 再発防止策 / 影響プロダクト範囲

### 実施タイミング
- コード修正: 復旧から **48時間以内**
- SOP更新: 復旧から **1週間以内**
- 共有レジストリ追記: マスター承認後、同セッション内

## §6. 公表ポリシー

### 公表する/しない判断基準
| 条件 | 判定 |
|------|------|
| ユーザーデータ漏洩あり | **公表必須**（個人情報保護法に基づく報告義務） |
| 課金・決済不整合あり | **公表必須**（影響ユーザーへの個別連絡 + 公開postmortem） |
| サービス全停止 30分以上 | **公表推奨**（status page + ブログ） |
| 一部機能の短時間停止 | 影響ユーザーへの個別告知のみ可 |
| 開発環境のみ・ユーザー影響なし | 内部記録のみ |

### 外向きpostmortemテンプレート
```markdown
# {YYYY-MM-DD} {プロダクト名} 障害報告

## 概要
{1段落で障害内容と影響を記述}

## タイムライン
{§4のタイムライン表をそのまま掲載}

## 根本原因
{5whysの結論を平易な日本語で}

## 影響範囲
- 影響ユーザー数: {N人 / 全ユーザー}
- 影響機能: {決済 / ログイン / 表示等}
- 影響期間: {HH:MM〜HH:MM、合計X分}

## 対応内容
{即時対応で行ったこと}

## 再発防止策
1. {コードレベルの修正}
2. {プロセスレベルの改善}
3. {監視強化}

## ご迷惑をおかけしたお客様へ
{謝罪文 + 補償有無 + 連絡先}
```

### 実施タイミング
- 公表必須案件: 復旧から **72時間以内**にpostmortem公開
- 公表推奨案件: 1週間以内
- 公表しない案件: 内部 memory.md にのみ記録

## §7. 各プロダクトの runbook.md テンプレ

`products/{product}/runbook.md` として以下を初期化（「運用Runbook整備」完了条件）:

```markdown
# {product} Runbook

## 監視・アラート
- UptimeRobot: {URL}
- Sentry: {プロジェクト名}
- アラート通知先: マスターメール / SMS

## エスカレーション基準
- P0: 即時電話通知
- P1: 30分以内メール通知
- P2: 翌朝定期報告

## ロールバック手順
- Vercel: `vercel rollback {deployment-url}`
- DB migration: `{ツール} migrate down`
- 緊急 maintenance mode: `{エンドポイント}`

## 告知チャネル
- status page: {URL}
- 影響ユーザー連絡: {DBクエリ or メールリスト所在}
- 公式SNS: {アカウントURL}

## 復旧確認チェックリスト
- [ ] トップページ表示
- [ ] 認証フロー
- [ ] 主要API応答
- [ ] DB読み書き
- [ ] 課金フロー（決済プロダクトのみ）

## 過去の障害履歴
（発生時に追記）
```

### 実施タイミング
- 「運用Runbook整備」着手時に本テンプレで初期化
- 障害発生ごとに「過去の障害履歴」へタイムライン + 根本原因を追記
