# Mission Tree Management Method Report

## 1. 目的

このレポートは、このディレクトリで運用しているツリー図管理手法を、別のAIや別プロジェクトへ移植できるように説明するものである。

対象は、現在のMissionがAIエージェント開発であるかどうかに依存しない。教育、研究、営業、制作、資格取得、業務改善、個人プロジェクトなど、全く異なるミッションでも、同じ本質で管理構造を作れることを目的にする。

この手法の本質は、作業を時系列の予定表として並べることではない。最上位目的から、必要な成果状態、獲得すべき能力、能力差を埋める施策、独立して閉じられる成果、実行単位、検証証拠までを一本の追跡線でつなぐことである。

```text
Mission
└─ Goal
   └─ Capability
      └─ Initiative
         └─ Issue
            └─ Task
```

この階層を運用することで、AIは「いま何をやるか」だけでなく、「それが何の能力を証明し、どのGoalを進め、最終Missionにどう寄与するか」を毎回復元できる。

### 運用衝突時の扱い

このレポートは、既存の開発基盤、チケット管理、ドキュメント体系、承認フローを無条件に置き換えるものではない。

移植先にすでに確立した運用があり、このレポートの推奨構成、ファイル名、checkin/checkout、進捗台帳、承認境界、検証方式と衝突する場合、AIは実装や置き換えを先に進めない。衝突している既存運用、衝突する理由、採用できる選択肢、推奨、影響をマスターへ説明し、判断を得てから反映する。

`要マスター確認`: 既存基盤がある環境では、このレポートのファイル構成をそのまま追加するか、既存の計画書、Issue管理、CI、ナレッジベースへ対応付けるかを先に決める。

## 2. この手法で解く問題

AIを使った継続プロジェクトでは、次の問題が起きやすい。

- セッションをまたぐと、目的、現在地、未完了作業、承認境界が失われる。
- 作業は増えるが、何のための成果物か分からなくなる。
- 完了した気分はあるが、Evidenceがなく、後から説明できない。
- ユーザーの新しい指示に反応し続け、上位Missionとの対応が崩れる。
- AI用の長い正本を人間へそのまま見せ、判断しにくい資料になる。
- 未コミット差分、外部操作、有料操作、破壊的操作の扱いが曖昧になる。

この管理手法は、これらを次の仕組みで抑える。

まず、問題をツリー図上の要素へ対応させる。

| 問題 | 対応するツリー要素 | 抑え方 |
|---|---|---|
| 目的が失われる | Mission | 存在目的、受益者、対象外、成立判定を1つの正本へ固定する |
| 何のための成果物か分からなくなる | Goal | Mission成立に必要な成果状態と指標へ対応させる |
| 能力として説明できない | Capability | 単発成果物ではなく、反復可能性、性能基準、証明方法を持たせる |
| 作業が散らばる | Initiative | 能力差、開始状態、終了状態、Deliverableへ束ねる |
| 完了が曖昧になる | Issue | Acceptance Criteria、Verification Method、Evidenceを持たせる |
| 実行単位が大きすぎる | Task | 一操作または一確認へ分け、独立管理が必要ならIssueへ昇格する |
| 証拠が残らない | Evidence | Verificationを実施した版、条件、結果、保存先を記録する |

Git管理、checkin/checkout、進捗台帳、memory、マスター向けブリーフ、Cost gateは、上のツリーを実運用で崩さないための運用層である。これらは重要だが、MissionからTaskまでの親子関係そのものとは分けて扱う。

## 3. 中核思想

### 3.1 ツリー図は予定表ではなく追跡構造である

このツリーは「月曜にA、火曜にBをやる」という予定表ではない。

Missionを成立させるにはどんなGoalが必要か。Goalを成立させるにはどんなCapabilityが必要か。Capabilityを獲得するにはどんなInitiativeが必要か。Initiativeを進めるにはどんなIssueを独立して閉じる必要があるか。Issueを閉じるにはどんなTaskとEvidenceが必要か。

この因果関係を記録するのがツリー図である。

### 3.2 親子関係は「含まれる」ではなく「成立させる」

単に作業を細かく分けるだけでは、ツリー管理にはならない。

```text
悪い分解:
動画制作
└─ 台本
   └─ 1章
      └─ 文章を書く
```

これはフォルダ分解に近い。親がなぜ成立するのか、何を検証すればよいのかが弱い。

```text
良い分解:
Mission: 視聴者が商品価値を理解し、問い合わせできる状態を作る
└─ Goal: 主要な購買不安を動画内で解消できている
   └─ Capability: 制作者が顧客の不安を構造化して説明できる
      └─ Initiative: 顧客不安と回答根拠を整理する
         └─ Issue: FAQ根拠表を受入可能な状態にする
            └─ Task: FAQ根拠表を作成する
```

この形なら、Taskの完了がIssueへ、IssueのEvidenceがInitiativeへ、Initiativeの成果がCapabilityへつながる。

### 3.3 完了は子要素の消化だけでは判定しない

子Taskが全部終わっても、親IssueのAcceptance Criteriaを満たしていなければIssueは閉じない。Issueが全部閉じても、Initiativeの能力差が解消していなければInitiativeは完了しない。

つまり、この手法では「やった」ではなく「受け入れられる状態になり、証拠が残った」を完了とする。

### 3.4 AI用正本と人間向け資料を分ける

Missionツリー正本は、AIが整合性、親子関係、ID、Evidence、進捗台帳を処理するための資料である。人間が毎回全文を読む資料ではない。

人間へ提示する時は、次の順で要約する。

```text
目的
現在地
今日決めること
選択肢
推奨
影響
次アクション
正本
Git状態
```

AIは正本を読む。人間には判断材料を出す。この分離が、運用を重くしすぎないための重要な設計である。

## 4. 推奨ファイル構成

他ミッションへ移植する場合、次のファイル構成を推奨する。

ただし、すでに基盤が確立している環境では、この構成をそのまま新設しない。既存の計画書、チケット管理、ナレッジベース、CI、運用手順へ対応付けるか、新規ファイルとして分離するかをマスター確認項目にする。

```text
AGENTS.md
docs/planning/mission-initiative-map.md
docs/strategy/operating-model.md
docs/strategy/master-facing-communication.md
docs/strategy/session-handoff-template.md
memory.md
scripts/validate-session-lifecycle.ps1
```

| ファイル | 役割 |
|---|---|
| `AGENTS.md` | AIが最初に読む入口。正本、判断順序、承認境界、checkin/checkoutを定義する |
| `docs/planning/mission-initiative-map.md` | Missionツリー、階層定義、進捗台帳、監査結果の正本 |
| `docs/strategy/operating-model.md` | セッション運用、ロードマップ、情報の置き場、承認境界 |
| `docs/strategy/master-facing-communication.md` | AI用正本を人間向けに変換する提示ルール |
| `docs/strategy/session-handoff-template.md` | checkout時に何を残すかのテンプレート |
| `memory.md` | 現在地、承認状態、次アクションだけを短く残す |
| `scripts/validate-session-lifecycle.ps1` | 正本、進捗台帳、memory、Skillなどの最低整合性を検証する |

`要マスター確認`: 既存基盤がある移植先では、上記を必須ファイルとして増やすのではなく、既存ドキュメントまたは既存ツール上の対応先を先に決める。

`要マスター確認`: 移植先でPowerShell以外を標準にする場合、検証スクリプトはShell、Python、Node.jsなどへ置き換えてよい。ただし「検証スクリプトを置く」という層は残す。

## 5. Missionツリー正本の作り方

### 5.1 Step 1: Missionを1つだけ置く

Missionは、プロジェクトの存在目的と最終到達状態である。作業名、成果物名、期限ではない。

Missionには次を書く。

| 欄 | 内容 |
|---|---|
| 中核目的 | なぜこのプロジェクトが存在するか |
| 受益者 | 誰のためのMissionか |
| 対象領域 | どの領域を扱うか |
| 最終到達状態 | どんな状態になればMissionが成立するか |
| 対象外 | 何をやらないか、何を誇張しないか |
| 成立判定 | 何の証拠が揃えば成立と言えるか |

Missionの文型は次を基本にする。

```text
<受益者>が<価値・目的>を実現できる状態になる
```

例:

```text
個人事業主が、証拠付きの制作実績を提示して高単価案件へ応募できる状態になる
```

避ける例:

```text
ポートフォリオを作る
```

これは成果物名であり、Missionとしては狭すぎる。ポートフォリオを作って何を実現するのかまで書く。

### 5.2 Step 2: GoalをMission成立に必要な成果状態として置く

Goalは、Mission成立に必要な成果状態である。手順や技術選定ではない。

Goalには次を書く。

| 欄 | 内容 |
|---|---|
| ID | `G1`、`G2` のように一意にする |
| 目標状態 | 達成・維持すべき状態 |
| Missionへの寄与 | Missionのどの部分を成立させるか |
| 対象範囲 | 扱う範囲 |
| 指標 | 達成を測る観点 |
| 目標値 | どこまで達すればよいか |
| 期限または見直し条件 | いつ、何が変わったら見直すか |
| 達成証拠 | 達成を示すEvidence |

Goalの文型は次を基本にする。

```text
<対象領域>で<成果状態>を実現している
```

Goalは3個前後から始めると扱いやすい。多すぎる場合、Missionが広すぎるか、GoalではなくCapabilityやInitiativeが混ざっている可能性がある。

`要マスター確認`: 最適なGoal数はミッションの規模で変わる。このディレクトリでは3 Goalだが、移植先では2から5程度を初期目安にする。

### 5.3 Step 3: Capabilityを反復可能な能力として置く

Capabilityは、単発成果物ではなく、条件が変わっても再利用できる能力である。

Capabilityには次を書く。

| 欄 | 内容 |
|---|---|
| ID | `G1-C1` のように親Goalを含める |
| 親Goal | どのGoalへ寄与するか |
| 能力主体 | 誰ができるようになるのか |
| できること | 何を実行できる能力か |
| 利用条件 | どんな前提なら使えるか |
| 対象 | 能力を適用する対象 |
| 性能基準 | どの品質なら能力ありと言えるか |
| 反復可能性 | 別条件でも使えるか |
| 維持条件 | どう維持・更新するか |
| 証明方法 | 何で能力を証明するか |

Capabilityの文型は次を基本にする。

```text
<主体>が<条件下で><行為>できる
```

Capabilityを設計する時の判定質問:

- これは一回限りの成果物ではないか。
- 別の入力、別の顧客、別の条件でも同じ手順を使えるか。
- この能力があると主張するには、どんなEvidenceが必要か。

### 5.4 Step 4: Initiativeを能力差解消施策として置く

Initiativeは、Capabilityの現在状態と必要状態の差を埋める施策である。開始と終了がある。

Initiativeには次を書く。

| 欄 | 内容 |
|---|---|
| ID | `G1-C1-I1` のように親Capabilityを含める |
| 主要Capability | どのCapabilityの能力差を埋めるか |
| 能力差 | 何が足りないのか |
| 開始状態 | いま何があるか |
| 終了状態 | 何ができれば終わるか |
| 対象／対象外 | 扱う範囲と扱わない範囲 |
| Deliverable | 合意成果物 |
| Acceptance Criteria | 受入条件 |
| 制約 | 実行上の制約、禁止事項 |
| 依存関係 | 先に必要なもの |
| 証拠計画 | Evidenceをどこへ残すか |

Initiativeの文型は次を基本にする。

```text
<具体的変化または成果>を<一つの動詞>する
```

悪いInitiative:

```text
設計能力を確立する
```

これはCapabilityの言い換えで、開始状態、終了状態、成果物が弱い。

良いInitiative:

```text
入力、出力、停止条件、対象外を定義した実行契約を作成する
```

この形なら、何を作り、何を検証すればよいか分かる。

### 5.5 Step 5: Issueを独立成果単位として置く

Issueは、独立して計画、議論、受入判定できる成果単位である。GitHub Issueへ移す候補として扱える粒度にする。

Issueには次を書く。

| 欄 | 内容 |
|---|---|
| ID | `G1-C1-I1-ISS1` のように親Initiativeを含める |
| 親Initiative | どのInitiativeを進めるか |
| 解決対象 | 何の不足や曖昧さを解くか |
| 期待成果 | どんな状態になればよいか |
| 対象／対象外 | Issueの範囲 |
| Requirement | 必要条件 |
| Deliverable | 成果物 |
| Acceptance Criteria | 受入条件 |
| Verification Method | 検証方法 |
| 依存関係 | 先行Issueや成果物 |
| Evidence | 検証証拠の保存先 |

Issueの文型は次を基本にする。

```text
<独立成果>を<受入可能な状態>にする
```

Issueは「作るもの」だけでなく、受入条件と検証方法まで持つ。これがTaskとの違いである。

### 5.6 Step 6: Taskを単一実行単位として置く

Taskは、Issueを閉じるための一操作または一確認である。独立管理が必要ならTaskではなくIssueへ昇格する。

Taskには次を書く。

| 欄 | 内容 |
|---|---|
| 親Issue | どのIssueに属するか |
| 実行動詞 | 作成する、確認する、検証記録するなど |
| 操作対象 | 何を操作するか |
| 入力・前提 | 何を前提にするか |
| 完了確認 | 何を見れば完了と分かるか |
| 生成物または作業記録 | どこに記録が残るか |

このディレクトリでは、各Issueへ原則2 Taskを置いている。

```text
T1: Deliverableを作成する
T2: Acceptance Criteriaの検証結果を記録する
```

この2 Task方式の利点は、成果物作成と検証記録を分離できることである。AIが「作ったから完了」と言い切る事故を減らす。

`要マスター確認`: 移植先でレビューが重い場合、T3として「マスター確認を反映する」を追加してもよい。ただしTaskが増えすぎると運用が重くなる。

## 6. 階層外に置く関連要素

Requirement、Deliverable、Acceptance Criteria、Verification Method、Evidence、Definition of Doneは、MissionからTaskまでの階層に混ぜない。各階層、特にIssueやInitiativeへ関連付ける。

| 要素 | 役割 |
|---|---|
| Requirement | 達成要件。何が必要か |
| Deliverable | 合意成果物。何を作るか |
| Acceptance Criteria | 受入条件。何を満たせばよいか |
| Verification Method | 検証方法。どう判定するか |
| Evidence | 検証証拠。何を見れば後から確認できるか |
| Definition of Done | 共通完了基準。同種の成果物に共通する条件 |

分離の順序は次を使う。

```text
Deliverable: 何を作るか
Acceptance Criteria: 何を満たせば受け入れるか
Verification Method: どう判定するか
Evidence: いつ、どの版・条件で判定し、結果がどうだったか
Definition of Done: 同種の成果物に共通する完了条件
```

この分離を守ると、成果物はあるが受入不能、受入条件はあるが検証不能、検証したが証拠がない、という状態を発見できる。

## 7. ID設計

IDは親子関係をそのまま表す。

```text
G1
G1-C1
G1-C1-I1
G1-C1-I1-ISS1
G1-C1-I1-ISS1-T1
```

ID設計の原則:

- Missionは1件だけなのでIDを省略してよい。
- Goalは `G1`、`G2` のように連番にする。
- Capabilityは `G1-C1` のように親Goalを含める。
- Initiativeは `G1-C1-I1` のように親Capabilityを含める。
- Issueは `G1-C1-I1-ISS1` のように親Initiativeを含める。
- Taskは `G1-C1-I1-ISS1-T1` のように親Issueを含める。

このIDは、見た瞬間に「どのMission系統の、どの能力の、どの施策の作業か」を復元するためのものだ。

注意点:

- IDを意味のある短文にしない。
- 途中で親を変えた場合、IDも変えるか、移動履歴を残す。
- IDが深すぎると読みにくくなるので、表示時は必要な範囲だけ出す。

`要マスター確認`: 完了後のID変更をどこまで許すかは、移植先の監査強度で決める。厳密な監査が必要な場合、ID変更は原則禁止し、廃止と新規作成で扱う。

## 8. Missionツリー正本の構成テンプレート

新しいミッションへ移植する場合、正本は次の章立てで作る。

```markdown
# ツリー図

> Mission-tree-status: `drafting`
>
> 状態: <現在の定義状態>
>
> この資料は、外部リソース、課金操作、Issue作成などを実行しない。

## 1. この資料の目的
## 2. 全体構造
## 3. 用語の根拠と採用定義
## 4. 階層に入れない関連要素
## 5. 階層記載仕様
## 6. Mission
## 7. Goal
## 8. Capability
## 9. Initiative
## 10. Issue
## 11. Task
## 12. Goal別のRequirement・成果物・Evidence
## 13. 現在の確定範囲と次の段階
### 13.1 進捗記録
### 13.2 進捗集計
## 14. 調査根拠
## 15. 検証チェックリスト
## 16. 記載仕様適合監査
```

必要に応じて、見積や価格概算などの章を追加してよい。ただし追加章はMissionツリーの成立条件とは分ける。

`Mission-tree-status` は次のように使う。

| 状態 | 意味 |
|---|---|
| `drafting` | ツリー構造を作成中。毎セッションでAIが全文を読み、人間へブリーフを提示する |
| `complete` | 文書上のMissionツリー定義が完成。進捗台帳が現在地の入口になる |

`complete` は、Missionそのものが達成済みという意味ではない。あくまで「管理図として完成した」という意味である。

## 9. 運用モデルの作り方

### 9.1 判断順序を固定する

全AI、全セッションで次の判断順序を使う。

```text
Missionツリー ＞ ロードマップ ＞ プラン ＞ アクション
```

意味:

- Missionツリーに合わない作業は、原則として実行しない。
- ロードマップに合わない作業は、次の段階として妥当か確認する。
- 承認済みプランにない作業は、追加理由と影響を確認する。
- アクションは最後に決める。

この順序は、AIが目先の作業へ飛びつかないための骨格である。

### 9.2 セッション標準フローを固定する

標準フローは次にする。

```text
チェックイン
→ プラン作成
→ サブ検証
→ マスター提示
→ マスター承認
→ アクション
→ プラン完遂
→ チェックアウト
```

各工程の役割:

| 工程 | 役割 |
|---|---|
| チェックイン | 正本、現在地、進捗、承認境界、作業ツリーを復元する |
| プラン作成 | 今回のセッションで完遂できる範囲を決める |
| サブ検証 | Mission、ロードマップ、承認境界、検証可能性に照らしてプランを点検する |
| マスター提示 | 人間が判断しやすい形で計画を出す |
| マスター承認 | 実行前に合意を取る |
| アクション | 承認済み範囲だけ実行する |
| プラン完遂 | 成果物と検証を揃える |
| チェックアウト | 進捗台帳、memory、検証、コミット、次アクションを整える |

このフローは重く見えるが、毎回長文で実施する必要はない。重要なのは、AIが「現在地復元なしに作業開始しない」「承認前に危険操作へ進まない」「完了時にEvidenceと次アクションを残す」ことである。

### 9.3 1セッションの量を制限する

1セッションは、1つの承認済みプランを完遂、検証、checkoutできる量にする。

初期目安:

- 文書作成中心: 2から3 Issue
- 実装とテスト中心: 1から2 Issue
- 外部操作、有料操作、破壊的操作を含む: 1 Issue以下
- 不確定な設計議論: 1判断点に絞る

このディレクトリでは、プランは最大3マイルストーン、各マイルストーンは独立検証可能にする。

`要マスター確認`: 移植先でチーム人数やレビュー密度が違う場合、1セッション量は調整する。基準は時間ではなく「完遂、検証、checkoutできるか」である。

## 10. checkinの運用

checkinは、AIが作業を始める前に現在地を復元する工程である。

最低限読むもの:

```text
AGENTS.md
docs/planning/mission-initiative-map.md
docs/strategy/operating-model.md
memory.md
```

読み取り確認するもの:

```text
git branch --show-current
git status --short
git log -1 --format="%h %ad %s" --date=short -- docs/planning/mission-initiative-map.md
```

checkinで報告するもの:

```text
判断順序
Mission
進捗記録
現在地
次工程
費用・承認状態
作業ツリー
```

Missionツリーが `drafting` の間は、AIは正本全文を読む。ただし人間へは全文ではなく、マスター確認用ブリーフを出す。

Missionツリーが `complete` になった後は、進捗記録と進捗集計を現在地の入口にする。

## 11. planの運用

プランは、単なる作業リストではない。Missionツリー上のどのIssueを閉じ、どのEvidenceを作るかを明示する。

プランに最低限含めるもの:

| 項目 | 内容 |
|---|---|
| 先行必須 | 着手前に完了しているべきIssue、成果物、承認 |
| 並列可能 | 同時に進められる調査、レビュー、実装 |
| 後続 | 今回の成果に依存する次Issue |
| ブロッカー | 費用、外部操作、権限、未コミット差分、仕様未確定 |
| 実行順 | 直列作業、並列作業、合流検証 |
| 検証 | 何をもって完了確認するか |

AIがプランを作る時は、次を確認する。

- 今回の作業はMissionツリーのどのIssueに対応するか。
- IssueのAcceptance Criteriaは何か。
- Verification Methodは実行可能か。
- Evidenceはどこへ残るか。
- Cost gateや承認境界を越えないか。
- 既存の未コミット差分に触れないか。

## 12. actionの運用

アクションは、承認済みプランに沿って実行する。

アクション中の原則:

- 無関係なリファクタや資料整理を混ぜない。
- 既存の未コミット差分を勝手に戻さない。
- secret、token、接続文字列、API keyを保存しない。
- 有料操作、外部リソース作成、破壊的操作は承認境界を先に確認する。
- 作業中に新しい問題を見つけたら、現在プランで扱うか次Issueに送るかを分ける。

作業がMissionツリーに対応しない場合は、即実行せずに次を書く。

```text
この作業は現在のMissionツリーに未対応である。
対応させるには、<Goal/Capability/Initiative/Issue> の追加または変更が必要である。
```

## 13. checkoutの運用

checkoutは、次のAIや次回セッションが迷わず再開できるようにする工程である。

checkoutで行うこと:

1. 実施した変更に対応する検証を実行する。
2. Missionツリー正本の `13.1 進捗記録` を更新する。
3. Missionツリー正本の `13.2 進捗集計` を更新する。
4. `memory.md` の現在地と次アクションを短く更新する。
5. lifecycle validation、Markdown差分確認、Git状態確認を行う。
6. 意図した変更だけコミットする。
7. 完了、検証、未解決、次アクションを報告する。

進捗台帳には次を記録する。

| 欄 | 内容 |
|---|---|
| 日時 | 完了または記録した日時 |
| commit | 成果物または管理コミット |
| 完了ID | 完了したIssue ID |
| 進捗量 | `1 Issue / 2 Task相当` など |
| 計画工数対象 | どのCapability工数の範囲か |
| 実作業時間 | 実作業の概算 |
| 成果物 | 作成・変更した成果物 |
| Evidence | 検証証拠 |
| 検証 | 何を確認したか |

重要な運用ルール:

- 進捗履歴は `memory.md` に増やさない。
- `memory.md` には現在地と次アクションだけ置く。
- 進捗記録だけを更新するコミットは、直前の対象コミットを記録する管理コミットとして扱う。
- 空コミットは作らない。
- 無関係な差分をコミットしない。

## 14. memoryの運用

`memory.md` は長い履歴の置き場ではない。次回再開に必要な動的状態だけを置く。

推奨形式:

```markdown
## 現在地と次アクション

- 完了と証拠: <完了内容。コミット、テスト、確認結果など>
- 現在の状態: <ブランチ、未コミット差分、対象環境>
- 承認・ブロッカー: <必要な承認、未解決事項>
- 次アクション: <次に行う一つの具体的な作業>
```

memoryに入れないもの:

- 長い進捗履歴
- Missionツリー定義の複製
- ロードマップ全文
- 完了済み成果物一覧の増殖
- 未検証の教訓

memoryに入れるもの:

- 次回の入口
- 未承認操作
- ブロッカー
- 現在のブランチや環境状態
- 再利用価値が高い失敗の短い要約

## 15. マスター向け提示の運用

AI用正本は詳細でよい。しかし人間向け提示は、判断に必要な情報を先に出す。

標準ブリーフ:

```text
目的:
現在地:
今日決めること:
選択肢:
推奨:
影響:
次アクション:
正本:
Git状態:
```

変更提案時:

```text
変更したい理由:
変更前の問題:
変更案:
採用理由:
影響範囲:
保留点:
承認後に編集するファイル:
```

提示原則:

- AI用正本をそのまま貼らない。
- 重要な判断を先に置く。
- 未コミット差分やこれから反映する差分は、未確定として扱う。
- コミット済みの確定事項と未確定事項を混ぜない。
- 利用者が全文提示を明示した時だけ正本全文を出す。

`要マスター確認`: 「赤字で示す」などの表現規則は、利用環境によって実現方法が異なる。Markdown上では `[未確定]`、HTML上では赤字など、媒体に合わせて決める。

## 16. 承認境界の設計

どのミッションでも、AIが勝手に進んではいけない境界を明文化する。

このディレクトリでは、Azure、有料API、モデル呼び出し、外部契約、削除操作、dev/prod作成などを承認境界にしている。

他ミッションでは、次の観点で置き換える。

| 分野 | 承認境界の例 |
|---|---|
| 開発 | 本番デプロイ、DB migration、秘密情報変更、外部API呼び出し |
| 研究 | 有料論文購入、外部データ利用、個人情報を含む分析 |
| 営業 | 顧客への送信、価格提示、契約条件提示 |
| 制作 | 公開投稿、広告出稿、商用素材購入 |
| 学習 | 有料講座購入、試験申込、外部アカウント作成 |

承認境界の書き方:

```text
<操作> は、<影響> があるため、実行前に <提示すべき判断材料> を示し、マスターの明示承認を得る。
```

費用が発生し得る場合は、最低限次を提示する。

```text
A 無料: できる範囲と制約
B 低額: できる範囲と制約
C 推奨構成: 月額見込みと理由
推奨案
A/Bのトレードオフ
```

## 17. 検証設計

この管理手法では、検証は最後のおまけではない。Issueを定義する時点で、Verification MethodとEvidenceを置く。

検証の種類:

| 種類 | 例 |
|---|---|
| 文書検証 | 必須欄が埋まっている、根拠がある、未証明が明示されている |
| 実装検証 | unit test、integration test、lint、compile |
| 運用検証 | health check、ログ確認、復旧手順確認 |
| 説明検証 | 主張とEvidenceが対応している、誇張がない |
| 安全検証 | secret非混入、権限境界、費用境界 |

検証結果は、結果だけでなく条件も残す。

```text
何を検証したか
どの版で検証したか
どのコマンドまたはレビューで検証したか
結果はどうだったか
未実行の理由は何か
```

未実行の検証は、失敗ではなく状態として記録する。

```text
Not run: <理由>
```

例:

```text
Not run: 有料API呼び出しに該当するため、Cost gate承認前には実行しない。
```

## 18. 監査チェックリスト

Missionツリーを `complete` にする前に、次を確認する。

- Missionが1つだけ定義されている。
- GoalがMissionの繰り返しではなく、独立した成果領域を持つ。
- Capabilityが単発成果物ではなく、反復可能な能力になっている。
- InitiativeがCapabilityの言い換えではなく、開始状態、終了状態、成果物、終了条件を持つ。
- Issueが独立して受入判定できる。
- Taskが一操作または一確認に収まっている。
- Mission以外の全項目に有効な親が1つある。
- 子要素の集合が、親のDeliverableとAcceptance Criteriaをカバーしている。
- 各Acceptance CriteriaにVerification MethodとEvidenceがある。
- Requirement、Deliverable、Acceptance Criteria、Verification Method、Evidenceが混同されていない。
- `N/A`には適用外理由がある。
- 有料操作、外部作成、破壊的操作を文書作成中に実行していない。
- `complete` がツリー定義の完成であり、Mission達成済みを意味しないことが明記されている。

監査結果は数表にする。

```markdown
| 区分 | 対象数 | 適合 | 不足 | 不適合 |
|---|---:|---:|---:|---:|
| Mission | 1 | 1 | 0 | 0 |
| Goal | <数> | <数> | <数> | <数> |
| Capability | <数> | <数> | <数> | <数> |
| Initiative | <数> | <数> | <数> | <数> |
| Issue | <数> | <数> | <数> | <数> |
| Task | <数> | <数> | <数> | <数> |
```

## 19. 他AIへ渡す作成指示テンプレート

他のAIに全く別ミッションのツリーを作らせる場合、次の指示を渡す。

```text
あなたは、次のミッションをMission Treeとして設計する。

ミッション候補:
<ここにミッションを書く>

目的:
このMissionを、Goal、Capability、Initiative、Issue、Taskへ分解し、各IssueにAcceptance Criteria、Verification Method、Evidenceを持たせる。

必須方針:
- Missionは1つだけ置く。
- GoalはMission成立に必要な成果状態にする。
- Capabilityは反復可能な能力にする。
- InitiativeはCapabilityの能力差を埋める、開始と終了がある施策にする。
- Issueは独立して受入判定できる成果単位にする。
- Taskは一操作または一確認にする。
- Requirement、Deliverable、Acceptance Criteria、Verification Method、Evidenceを混同しない。
- 不確実な箇所は `要マスター確認` と書く。
- 外部リソース作成、有料操作、送信、削除、公開は実行しない。

出力:
1. Mission定義
2. Goal表
3. Capability表
4. Initiative表
5. Issue表
6. Task表
7. 進捗台帳テンプレート
8. 運用ルール
9. 監査チェックリスト
```

補足情報が少ない場合、AIは仮説で埋めすぎず、次のように書く。

```text
要マスター確認: 受益者が本人か、顧客か、組織か未確定。
要マスター確認: 成果証拠として公開実績が必要か、非公開資料で足りるか未確定。
要マスター確認: 費用発生操作の承認境界が未確定。
```

## 20. 導入手順

新しいプロジェクトへ導入する時は、次の順で進める。

### Phase 1: 最小骨格を作る

1. `AGENTS.md` を作る。
2. `docs/planning/mission-initiative-map.md` を作る。
3. `docs/strategy/operating-model.md` を作る。
4. `memory.md` を作る。
5. Mission、Goal、Capabilityまで仮定義する。
6. 不確かな箇所へ `要マスター確認` を付ける。

この段階では、IssueやTaskを急いで埋めすぎない。上位構造がずれていると、下位作業が全部ずれる。

### Phase 2: 施策と独立成果へ落とす

1. Capabilityごとに能力差を出す。
2. 能力差ごとにInitiativeを作る。
3. InitiativeごとにIssueを作る。
4. IssueごとにAcceptance Criteria、Verification Method、Evidenceを置く。
5. IssueごとにTaskを置く。

この段階で、子要素が親の成立条件を本当にカバーしているか確認する。

### Phase 3: 運用ルールを固定する

1. checkinの読む順序を決める。
2. checkoutの更新順序を決める。
3. 進捗台帳の列を決める。
4. 承認境界を決める。
5. 検証スクリプトを作る。
6. マスター向け提示形式を決める。

### Phase 4: draftingからcompleteへ移す

1. 監査チェックリストを実行する。
2. 不足、不適合を直す。
3. `要マスター確認` が残っている箇所を分類する。
4. 残してよい未確定と、complete前に解消すべき未確定を分ける。
5. マスターが完成を承認したら `Mission-tree-status` を `complete` にする。

`要マスター確認`: `要マスター確認` が残った状態で `complete` にしてよいかは、プロジェクトの性質で決める。安全、費用、契約、公開に関わる未確定は原則として残したまま実行フェーズへ進めない。

## 21. よくある失敗と修正

| 失敗 | 症状 | 修正 |
|---|---|---|
| Missionが作業名になる | 「アプリを作る」「資料を作る」だけになる | 誰が何を実現できる状態かへ書き換える |
| Goalが手順になる | 「Azureを学ぶ」「動画を撮る」になる | 成果状態と指標へ書き換える |
| Capabilityが成果物になる | 「設計書」「LP」「コード」になる | 反復可能な能力へ書き換える |
| InitiativeがCapabilityの言い換えになる | 「運用能力を確立する」になる | 能力差、開始状態、終了状態、Deliverableを足す |
| IssueがTaskになる | 「ファイルを作る」だけになる | 受入条件と検証方法を持つ独立成果へ直す |
| Taskが大きすぎる | 担当、議論、期限、Evidenceが必要になる | Issueへ昇格する |
| Evidenceがない | 完了したが後から証明できない | Issue定義時にEvidence保存先を決める |
| memoryが肥大化する | 次回AIが長い履歴を読まされる | 進捗は正本、memoryは現在地だけに戻す |
| 正本を人間へ貼る | 判断が重くなる | ブリーフ形式へ変換する |

## 22. このディレクトリ固有の要素と移植時の差し替え

このディレクトリでは、AIエージェント開発、Azure、Bicep、Cost gate、sandbox/dev/prod、GitHub Issue候補が具体要素になっている。

移植時は、次を差し替える。

| このディレクトリ | 移植先で差し替えるもの |
|---|---|
| AIエージェント開発案件への応募 | 移植先の最終Mission |
| Azure環境構築 | 移植先の実行基盤、制作環境、業務環境 |
| Bicep、Functions、Application Insights | 移植先の技術、ツール、成果物 |
| Cost gate | 移植先の費用承認ルール |
| sandbox/dev/prod | 移植先の検証、本番、公開、納品などの環境段階 |
| GitHub Issue候補 | 移植先のチケット、タスク管理、文書内Issue |
| Evidenceとしてのテストログ | 移植先のレビュー記録、成果物、実演、測定結果 |

差し替えてはいけない本質:

- Missionを1つ置くこと。
- Goalを成果状態にすること。
- Capabilityを反復可能な能力にすること。
- Initiativeを能力差解消にすること。
- Issueへ受入条件、検証方法、Evidenceを置くこと。
- Taskを一操作または一確認にすること。
- 進捗台帳を正本へ置くこと。
- memoryを現在地だけにすること。
- checkinとcheckoutを運用の入口と出口にすること。
- AI用正本と人間向け提示を分けること。

## 23. 最小テンプレート

小さいプロジェクトでは、最初から全44 Issueのような大きな表を作る必要はない。次の最小形から始める。

```text
Mission: 1
Goal: 2から3
Capability: 各Goalに2から4
Initiative: 各Capabilityに1から3
Issue: 各Initiativeに1
Task: 各Issueに2
```

これでも十分に追跡構造として機能する。

最初の1サイクル:

1. MissionとGoalを作る。
2. 最重要GoalのCapabilityだけ作る。
3. 最初のCapabilityにInitiativeを1つ作る。
4. InitiativeにIssueを1つ作る。
5. T1で成果物を作る。
6. T2で検証記録を作る。
7. 進捗台帳へ記録する。
8. memoryへ次アクションを残す。

小さく回して、Evidenceが残ることを確認してから広げる。

## 24. 完了判定

この管理手法を導入できたと言える条件は次の通り。

- 正本が1つ決まっている。
- AIがセッション開始時に読む順序が決まっている。
- MissionからTaskまでの階層定義がある。
- IssueにAcceptance Criteria、Verification Method、Evidenceがある。
- 進捗記録と進捗集計が正本にある。
- memoryが現在地と次アクションに限定されている。
- checkinとcheckoutの手順がある。
- 承認境界が明文化されている。
- 人間向け提示ルールがある。
- 検証スクリプトまたは検証チェックリストがある。

この条件を満たせば、ミッションの中身が全く違っても、同じ本質のMission Tree管理を再現できる。

## 25. 要マスター確認一覧

このレポート内で、補足説明または判断が必要な箇所をまとめる。

- `要マスター確認`: 移植先でPowerShell以外を標準にする場合、検証スクリプトの実装言語をどうするか。
- `要マスター確認`: 既存運用とこのレポートの推奨構成が衝突する場合、既存基盤へ対応付けるか、新規ファイルとして分離するか。
- `要マスター確認`: 移植先の初期Goal数の目安を2から5程度としてよいか。
- `要マスター確認`: レビューが重い案件で、IssueごとのTaskをT1/T2に加えてT3まで標準化するか。
- `要マスター確認`: 完了後のID変更を許すか、廃止と新規作成で扱うか。
- `要マスター確認`: 未確定差分を赤字で示すルールを、Markdown、HTML、チャット表示でどう実装するか。
- `要マスター確認`: `要マスター確認` が残った状態で `Mission-tree-status: complete` にしてよい条件をどう定めるか。
